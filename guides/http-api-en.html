The protocol

6 topics

Most API questions are really HTTP questions wearing a costume. If you can say precisely what a method guarantees and what a status code promises the client, the design answers follow from there.

Request and response anatomy

A request is a method, a target, headers, and an optional body. A response is a status line, headers, and an optional body. Everything else — REST, GraphQL, webhooks — is a convention layered on those four parts.

POST /v1/payments HTTP/1.1
Host: api.example.com
Content-Type: application/json
Idempotency-Key: 0f9c1b2e-6d31-4a55-9f0b-2b7a1c8e4d33
Authorization: Bearer eyJhbGciOiJSUzI1NiIsImtpZCI6ImsxIn0...

{"amount": 1500, "currency": "HUF"}
HTTP/1.1 201 Created
Location: /v1/payments/pay_8127
Content-Type: application/json
ETag: "3f1c9a"
Cache-Control: no-store

{"id": "pay_8127", "status": "succeeded", "amount": 1500}

Two properties are worth naming out loud because they explain most of the protocol: HTTP is stateless (the server keeps no client context between requests — anything it needs must be in the request), and headers are metadata about the message, not about the resource. HTTP/2 and HTTP/3 change the transport (binary framing, multiplexing, no head-of-line blocking on QUIC) but not this semantic model.

Asked as — “HTTP is stateless, so how do logins work?” The state lives in a cookie or token that the client re-sends on every request; the server may keep a session store, but the protocol still carries no memory between requests. That is exactly why load balancing across FPM workers works at all.

  3. Headers are metadata about what?

Methods and the three properties

Safe means “no intended side effects”. Idempotent means “N identical requests leave the same server state as one”. Cacheable means “a response may be reused without asking again”. These are contracts you promise to clients, not observations about your controller.

MethodSafeIdempotentCacheableBody
GETYesYesYesNo
HEADYesYesYesNo
OPTIONSYesYesNoNo
POSTNoNoRarely (needs explicit freshness)Yes
PUTNoYesNoYes
PATCHNoNo (unless you design it so)NoYes
DELETENoYesNoOptional

PUT

  • Full replacement of the resource at that URI
  • Client chooses the URI; may create it
  • Idempotent by definition
  • Missing fields mean “unset”, not “leave alone”

PATCH

  • Partial modification, described by a patch document
  • application/merge-patch+json (RFC 7386) or application/json-patch+json (RFC 6902)
  • Not idempotent in general — {"op":"add","path":"/tags/-"} appends every time
  • null in a merge patch deletes the member
The one that catches people. DELETE is idempotent even though the second call returns 404. Idempotency is about resulting state, not about identical responses. The same logic makes PUT idempotent while a POST /orders that mints a new order every time is not.

Asked as — “Is POST ever idempotent?” Not by the protocol, so a client may not retry it blindly. You can make a specific endpoint idempotent with an Idempotency-Key — see the reliability section — but that is your contract, not HTTP's.

  1. DELETE is idempotent even though a second call returns 404. Why?

    N identical requests leave the same state as one. The resource is gone either way. The same reasoning makes PUT idempotent and a POST /orders that mints a new order every time not.

  2. What is the practical difference between PUT and a merge patch?

    The omitted-field rule is the trap. Clients that send a partial document to PUT silently wipe everything they left out. Note too that PATCH is not idempotent in general — a JSON Patch {"op":"add","path":"/tags/-"} appends on every replay.

  3. Is POST ever idempotent?

    Safe, idempotent and cacheable are promises to clients, not observations about your controller. A generic client only knows what the method guarantees, which is why the key has to be explicit and documented.

The status codes that actually get asked

Nobody is checking whether you memorised 226 IM Used. They are checking the pairs that are easy to confuse, because each pair encodes a design decision.

Asked as — “401 or 403 for an expired token?” 401 with WWW-Authenticate, because re-authenticating fixes it. 403 means the credentials were fine and the answer is still no. The follow-up is usually “what about a valid token missing a scope?” — 403.

  1. A request body parsed fine but failed your business rules — “end date before start date”. Which status?

    400 means the parser choked; 422 means the document was understood and rejected. Standardising on 400 for both is defensible — but say so deliberately rather than by accident.

Content negotiation

The client states preferences in Accept, Accept-Language and Accept-Encoding; the server picks a representation and reports it in Content-Type and Content-Language. Quality values order the preferences.

Accept: application/vnd.example.order+json;version=2, application/json;q=0.8, */*;q=0.1
Accept-Language: hu-HU, hu;q=0.9, en;q=0.5
Accept-Encoding: br, gzip

Two rules that matter in review: return 406 only if you genuinely cannot satisfy any acceptable type (in practice most APIs just serve JSON), and always send Vary naming every request header the representation depended on — otherwise a shared cache serves the Hungarian body to an English client.

Vary: Accept, Accept-Language, Authorization

Asked as — “Where does versioning fit into content negotiation?” A custom media type (application/vnd.example.order+json;version=2) versions the representation rather than the URI space. It is the purist answer; the versioning topic covers why most teams still put /v1 in the path.

  1. Why must a negotiated response send a Vary header?

    Vary names every request header the representation depended on. Forget it and the CDN happily reuses one client's negotiated response for everyone — the same class of bug as caching an authenticated response publicly.

  2. When is 406 Not Acceptable the right response?

    406 is rarer than people think. A wrong request body type is 415 Unsupported Media Type, which is the code that actually comes up. Serving your one format is friendlier than refusing.

  3. How does a custom media type version an API?

    It is the purist answer, and correct by HTTP semantics: the resource kept its identity, only its representation changed. Most teams still put /v1 in the path because it is greppable in logs and testable with a curl one-liner.

Conditional requests: ETag and Last-Modified

A validator lets the client ask “has this changed?” without transferring the body, and lets the server ask “is your copy still current?” before accepting a write. ETag is an opaque version token; Last-Modified has one-second resolution, so prefer ETag.

GET /v1/orders/8127
If-None-Match: "3f1c9a"

HTTP/1.1 304 Not Modified
ETag: "3f1c9a"
// Strong ETag from the row version; weak (W/"...") if the body may vary cosmetically.
$etag = '"' . $order->version . '-' . $order->updatedAt->format('U') . '"';

$response = $response->withHeader('ETag', $etag);

$ifNoneMatch = $request->getHeaderLine('If-None-Match');
if ($ifNoneMatch !== '' && in_array($etag, array_map('trim', explode(',', $ifNoneMatch)), true)) {
    return $response->withStatus(304)->withBody($emptyStream);   // no body on 304
}
Strong vs weak. W/"abc" means “semantically equivalent”, and weak validators may not be used for range requests or for If-Match on writes. If your ETag is a hash of the serialised body, it is strong; if it ignores whitespace or generated timestamps, mark it weak.

Asked as — “How do you avoid sending the same payload again?” ETag plus If-None-Match gives you 304s that cost one round trip and no body. Mention that the same validator does double duty for optimistic locking on writes — that is the answer that sounds senior.

  1. Why prefer ETag over Last-Modified?

    Resolution is the practical reason. A validator that cannot tell two versions apart is worse than useless on a write path, where it would let a lost update through.

  2. What does W/"abc" mean, and where may it not be used?

    Weak means “close enough to reuse the body”, not “the same version”. A hash of the serialised body is strong; one that ignores whitespace or a generated timestamp must be marked weak — and therefore cannot carry the optimistic-locking job.

  3. What is the best answer to “how do you avoid sending the same payload again”?

    The double duty is the part that sounds senior. One token serves both revalidation (If-None-Match → 304) and optimistic concurrency (If-Match → 412).

Cache headers, and who is caching

Three actors: the browser (private cache), a shared cache (CDN, Varnish, reverse proxy) and your application cache. Cache-Control is the instruction set; getting it wrong on an authenticated endpoint leaks one user's data to another.

DirectiveEffect
no-storeDo not write this anywhere. The correct header for tokens, payment bodies, anything secret
no-cacheYou may store it, but revalidate before every reuse. Not the same as no-store
private / publicBrowser only / shared caches allowed too
max-age=NFresh for N seconds in any cache
s-maxage=NOverrides max-age for shared caches only
must-revalidateOnce stale, never serve without checking — no “serve stale on error”
stale-while-revalidate=NServe stale for N seconds while refreshing in the background
stale-if-error=NServe stale for N seconds if the origin is failing
immutableNever revalidate during freshness — for fingerprinted asset URLs
 
Cache-Control: public, max-age=60, s-maxage=600, stale-while-revalidate=30
Vary: Accept, Accept-Encoding
The leak. A response to an authenticated request must be private (or no-store), and if a shared cache is in front of it you must Vary: Authorization — or better, mark it uncacheable. “We put a CDN in front and users started seeing each other's dashboards” is a real incident class, and interviewers know it.

Asked as — “Difference between no-cache and no-store?” no-cache stores but always revalidates; no-store forbids writing the response to disk or memory at all. Cache invalidation strategies beyond that: short TTL + ETag revalidation, or surrogate keys / tag-based purging at the CDN.

  1. What is the difference between no-cache and no-store?

    no-store is the one for secrets — tokens, payment bodies. no-cache is a freshness instruction and is perfectly compatible with an ETag-based revalidation strategy.

  2. A CDN sits in front of an authenticated endpoint. What must be true?

    “We put a CDN in front and users started seeing each other's dashboards” is a real incident class. Mark authenticated responses private, or uncacheable — the safest default — and treat Vary: Authorization as the minimum if you deliberately cache them.

  3. What does stale-while-revalidate=60 buy you?

    Latency hiding, not freshness. Its sibling stale-if-error serves stale content while the origin is failing, and must-revalidate is the opposite instruction: once stale, never serve without checking.

Resource design

4 topics

The protocol gives you nouns, verbs and status. Design is deciding which nouns exist, how big they are, and how a client walks between them.

Resources, not RPC

URIs name things; methods say what to do to them. Verbs in the path (/getUser?id=3, /createOrder) mean the method is decorative and every cache and proxy in the chain loses its ability to help you.

RPC-shaped

  • POST /getOrder
  • POST /cancelOrder
  • POST /listOrdersForUser
  • Nothing cacheable, nothing safely retryable

Resource-shaped

  • GET /orders/8127
  • POST /orders/8127/cancellation
  • GET /users/42/orders
  • GETs cache and retry for free

Conventions worth stating because reviewers look for consistency: plural collection nouns (/orders), lowercase kebab-case for multi-word segments (/purchase-orders), identifiers in the path, filters in the query string, no trailing slash, no file extensions. Nest at most one level — /users/42/orders is fine, /users/42/orders/8127/lines/3/discounts is a maintenance problem; hang the deep resource off its own root instead.

Actions that are not CRUD. Real domains have “cancel”, “publish”, “refund”. Three honest options: model the action as a resource (POST /orders/8127/cancellation), model it as a state transition (PATCH /orders/8127 with {"status":"cancelled"}), or admit it is an RPC-style command and keep it in a clearly marked corner. The first is usually best because the action itself gets an identity, a timestamp and an audit trail.

Asked as — “How would you model ‘cancel order’ in REST?” Answer with the resource-as-action option first, then say why: it gives the cancellation an id you can retry against, reference in support tickets and audit — which a PATCH of a status field does not.

Collections: filtering, sorting, pagination

Every collection endpoint eventually meets a client that wants page 4000. Offset pagination is easy and degrades badly; cursor (keyset) pagination is slightly harder and stays constant-time.

Offset / limit

  • ?page=3&per_page=25
  • Can jump to an arbitrary page; total count is natural
  • OFFSET 100000 makes the database count and discard rows
  • Drifts: an insert during paging shows a row twice or skips one

Cursor / keyset

  • ?limit=25&after=eyJpZCI6ODEyN30
  • Uses an index seek — same cost on page 1 and page 4000
  • Stable under concurrent writes
  • No “jump to page 12”, and total counts get expensive
// Keyset pagination over a stable, unique sort key.
// The tie-breaker on id is what makes it correct when created_at repeats.
$sql = 'SELECT id, created_at, total
        FROM orders
        WHERE (created_at, id) < (:cursorTime, :cursorId)
        ORDER BY created_at DESC, id DESC
        LIMIT :limit';

$rows = $pdo->prepare($sql);
// ... bind, fetch $limit + 1 rows; the extra row tells you whether a next page exists.

$next = count($rows) > $limit
    ? base64_encode(json_encode(['t' => $rows[$limit - 1]['created_at'], 'id' => $rows[$limit - 1]['id']]))
    : null;

Return the paging state in the body ({"data": [...], "next_cursor": "..."}) or in Link headers (rel="next", rel="prev") — pick one and apply it everywhere. Filters belong in the query string with predictable names (?status=paid&created_after=2026-01-01), sorting in a single ?sort=-created_at,id parameter with - meaning descending. Always cap limit server-side; an uncapped per_page is a denial-of-service parameter.

Asked as — “Your list endpoint got slow at page 500. What now?” Keyset pagination, an index matching the sort key exactly, and dropping the exact total (estimate it, or return “has more”). Naming the (created_at, id) tie-breaker is what separates a memorised answer from a used-in-anger one.

    OFFSET 100000 makes the database walk and discard 100,000 rows. Naming the (created_at, id) tie-breaker is what separates a memorised answer from a used-in-anger one — without it, rows with equal timestamps shuffle between pages.

    One request asking for a million rows is enough. The rest of the collection house style: filters as predictable query parameters, sorting in a single ?sort=-created_at,id with - for descending, and paging state either in the body or in Link headers — pick one and apply it everywhere.

Relationships and payload shape

The two failure modes are the chatty API (a hundred requests to render one screen) and the fat API (one endpoint returning everything anyone ever needed). The tools between them: sub-resources, expansion, and sparse fieldsets.

GET /v1/orders/8127                      → the order, with customer as a reference
GET /v1/orders/8127?expand=customer,lines → embedded representations
GET /v1/orders?fields=id,total,status     → sparse fieldset, smaller payload
GET /v1/orders/8127/lines                 → the collection on its own URI
{
  "id": "ord_8127",
  "status": "paid",
  "total": {"amount": 1500, "currency": "HUF"},
  "customer": {"id": "cus_42", "href": "/v1/customers/42"},
  "created_at": "2026-09-10T08:14:22Z"
}

Conventions that save arguments later: one casing style for all keys (snake_case is the common REST choice, camelCase if your consumers are all JS), RFC 3339 UTC timestamps with a Z, money as integer minor units plus a currency code (never a float), enums as lowercase strings rather than integers, and null reserved for “known to be absent” rather than “not loaded”. Do not wrap single resources in a redundant envelope; do use one for collections, because that is where paging metadata has to live.

Asked as — “When would you reach for GraphQL instead?” When clients genuinely need arbitrary shapes and you can afford the cost: query complexity limits, N+1 batching, per-field authorization and much weaker HTTP caching. For a handful of known consumers, expansion and sparse fieldsets solve the same problem with none of that.

The Richardson maturity model, and HATEOAS honestly

LevelWhat it meansIn practice
0One URI, one verb — HTTP as a tunnelSOAP-style POST /api
1Resources get their own URIsStill POST for everything
2Methods and status codes used correctlyWhere nearly every real API lives
3Hypermedia controls in the representationHAL, JSON:API links, Link headers

Level 3 means the client discovers what it can do next from links in the response rather than from hardcoded URI templates. It is Fielding's actual definition of REST — an API without hypermedia is, strictly, not REST. It also rarely pays off between a backend and its own SPA, where the client is deployed with knowledge of the API anyway. Where it does pay: long-lived public APIs, state machines (which transitions are legal right now), and paging.

Reliability

4 topics

Networks retry, clients double-click, and two users edit the same row. These four topics are where senior interviews spend the most time, because they are where money gets charged twice.

Idempotency keys

A client sends POST /payments, the connection drops after the charge but before the response. The client cannot know whether it happened. The fix is a client-generated key that the server remembers.

final class IdempotentPayments
{
    public function __construct(private PDO $db, private Payments $payments) {}

    public function handle(string $key, array $payload): array
    {
        $fingerprint = hash('sha256', json_encode($payload, JSON_THROW_ON_ERROR));

        // Claim the key first. The unique index is the concurrency control:
        // two simultaneous retries race here, and exactly one wins.
        try {
            $stmt = $this->db->prepare(
                'INSERT INTO idempotency_keys (key_id, fingerprint, state, created_at)
                 VALUES (:k, :f, \'in_progress\', NOW())'
            );
            $stmt->execute(['k' => $key, 'f' => $fingerprint]);
        } catch (PDOException $e) {
            if (!$this->isUniqueViolation($e)) {
                throw $e;
            }
            $row = $this->load($key);

            // Same key, different body: the client has a bug. Do not silently replay.
            if (!hash_equals($row['fingerprint'], $fingerprint)) {
                throw new IdempotencyConflict();       // → 422, or 409
            }
            if ($row['state'] === 'in_progress') {
                throw new RequestInFlight();           // → 409 + Retry-After
            }
            return json_decode($row['response'], true); // → replay the stored 201
        }

        $result = $this->payments->charge($payload);
        $this->store($key, $result);
        return $result;
    }
}

Design notes an interviewer will fish for: the key is client-generated (a UUID per logical operation, not per retry), scoped per API key or per user so keys cannot collide across tenants, stored with the response so a replay returns the original 201 rather than re-executing, expired after 24 hours or so, and only applied to unsafe non-idempotent methods. Stripe's implementation is the reference everyone borrows from.

Asked as — “How do you make a payment endpoint safe to retry?” Idempotency key, unique index, stored response, fingerprint check on mismatch. If you only say “check whether a payment with the same amount exists in the last minute”, expect a follow-up about two legitimate identical charges.

  1. What problem does an idempotency key solve?

    It is about the ambiguous failure, not about concurrency. The server stores the key with the original response, so a replay returns the same 201 rather than charging again.

    The amount-and-time heuristic invites the obvious follow-up: two legitimate identical charges. The fingerprint check matters too — a client reusing a key with a different payload is a bug, and should get a 422 rather than the old response.

Optimistic concurrency: lost updates

Two clients GET the same order, both edit, both PUT. Without a precondition the second silently overwrites the first — the classic lost update. HTTP has a built-in answer.

PUT /v1/orders/8127
If-Match: "3f1c9a"

→ 200 OK          the version matched, write applied, new ETag returned
→ 412             someone else changed it since you read it
→ 428             you sent no If-Match and this endpoint requires one
// The database side of the same idea: a version column and a conditional UPDATE.
$stmt = $pdo->prepare(
    'UPDATE orders SET total = :total, version = version + 1
     WHERE id = :id AND version = :expected'
);
$stmt->execute(['total' => $total, 'id' => $id, 'expected' => $expectedVersion]);

if ($stmt->rowCount() === 0) {
    throw new PreconditionFailed();   // → 412, tell the client to re-read and retry
}
Optimistic vs pessimistic. Optimistic (version check, no lock held between read and write) suits HTTP, because a client may never come back. Pessimistic (SELECT ... FOR UPDATE) holds a database lock and only works inside one short transaction — you cannot hold it across a user's think time without building your own lock-expiry machinery.

Asked as — “Two users edit the same record. What happens?” Name the lost update, then give both layers: If-Match/412 at the API boundary and a version column with a conditional UPDATE underneath, so a client that bypasses the header still cannot clobber a row.

// Token bucket in Redis. The Lua script makes read-modify-write atomic —
// doing this in three PHP round trips is the bug interviewers look for.
const SCRIPT = <<<'LUA'
local tokens_key = KEYS[1]
local rate, capacity, now, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local data = redis.call('HMGET', tokens_key, 'tokens', 'ts')
local tokens = tonumber(data[1]) or capacity
local ts = tonumber(data[2]) or now
tokens = math.min(capacity, tokens + (now - ts) * rate)
local allowed = tokens >= cost
if allowed then tokens = tokens - cost end
redis.call('HSET', tokens_key, 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', tokens_key, math.ceil(capacity / rate) * 2)
return { allowed and 1 or 0, tokens }
LUA;

One error format: RFC 9457 problem details

Every API invents an error envelope. There is a standard one — application/problem+json, RFC 9457 (which obsoleted RFC 7807) — and using it costs nothing.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json
{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Your request parameters didn't validate.",
  "status": 422,
  "detail": "The order must contain at least one line item.",
  "instance": "/v1/orders",
  "trace_id": "01JB8Z4K3Q7X",
  "errors": [
    {"pointer": "/lines", "code": "min_items", "message": "At least one line is required."},
    {"pointer": "/currency", "code": "unsupported", "message": "Currency XPT is not supported."}
  ]
}

type is a stable URI that identifies the class of problem — that is the field clients should branch on, never the human-readable title. Extension members (errors, trace_id) are explicitly allowed. Include a correlation id so a support ticket maps to a log line; exclude stack traces, SQL, and internal hostnames, always, including in staging that someone will inevitably point at production data.

Asked as — “How do you return validation errors?” 422, problem+json, machine-readable per-field codes with JSON Pointers, one stable type URI, and a trace id. The senior addition: error codes are part of your public contract and are subject to the same compatibility rules as fields.

What counts as a breaking change

Safe (additive)

  • Adding a new optional request field
  • Adding a new field to a response
  • Adding a new endpoint or a new optional query parameter
  • Adding a new value to an enum your clients only read and display

Breaking

  • Removing or renaming a field; changing its type
  • Making an optional request field required, or tightening validation
  • Changing a status code, an error type, or default sort order
  • Adding an enum value clients switch on — and changing pagination defaults

The counterpart on the client side is Postel-flavoured but sharper: be a tolerant reader. Ignore unknown fields instead of failing, do not depend on key order, do not assume the set of enum values is closed, and treat any unexpected 5xx as retryable rather than fatal. In PHP that means mapping JSON into DTOs field by field rather than asserting the whole shape, and having a default branch on every match over an external enum.

Contract testing. The credible way to know you have not broken anyone: an OpenAPI document in version control, a diff tool in CI that fails the build on a breaking change, and consumer-driven contract tests for internal consumers. “We would notice in code review” is not an answer at senior level.

Asked as — “Is adding a field to a response a breaking change?” Usually no — unless a client validates against a closed schema, which is exactly why you publish a schema that allows additional properties and say so in the docs.

The PHP side: PSR-7, 15, 17, 18

These four are what let the concepts above be framework-agnostic: PSR-7 immutable request/response objects, PSR-17 factories for creating them, PSR-15 middleware and request handlers, PSR-18 the client interface for outbound calls.

final class RateLimitMiddleware implements MiddlewareInterface   // PSR-15
{
    public function __construct(
        private RateLimiter $limiter,
        private ResponseFactoryInterface $responses,              // PSR-17
    ) {}

    public function process(ServerRequestInterface $request, RequestHandlerInterface $handler): ResponseInterface
    {
        $key = $request->getAttribute('api_key');
        $verdict = $this->limiter->consume($key);

        if (!$verdict->allowed) {
            return $this->responses->createResponse(429)
                ->withHeader('Retry-After', (string) $verdict->retryAfter)
                ->withHeader('RateLimit', "limit={$verdict->limit}, remaining=0, reset={$verdict->retryAfter}");
        }

        // PSR-7 messages are immutable: every wither returns a new instance.
        return $handler->handle($request)
            ->withHeader('RateLimit', "limit={$verdict->limit}, remaining={$verdict->remaining}");
    }
}

The immutability is the detail people trip on: $response->withHeader(...) returns a new response and does nothing if you discard the return value. Middleware composes as an onion — each layer may short-circuit before $handler->handle() (auth, rate limit, caching) or decorate on the way out (headers, timing, correlation id).

Asked as — “Why does PSR-7 use immutable messages?” So a message cannot be mutated under a middleware that already inspected it, which makes the pipeline predictable and thread-safe in long-running servers (RoadRunner, Swoole, FrankenPHP). The main PHP guide's standards section covers the rest of the PSR stack.

The one-liners worth having ready

PUT vs POST for create
POST when the server assigns the id, PUT when the client does and the URI is known up front.
Body on GET
Not forbidden outright any more, but proxies, caches and clients drop it. Never design one.
Why 204 has no body
The spec says so — anything you write there may be discarded silently by intermediaries.
CORS preflight
An OPTIONS request the browser sends before a non-simple cross-origin call. CORS is a browser policy, not server security.
Authorization and caching
Responses to authenticated requests are not shared-cacheable unless you explicitly opt in. Set private or no-store.
HTTP/2 does not change semantics
Same methods, headers and status codes; different framing. Domain sharding and sprite sheets became anti-patterns.
Timeouts
Every outbound call needs a connect timeout and a total timeout. A missing timeout is how one slow upstream exhausts your FPM pool.
Retry only what is safe
Idempotent methods, or anything carrying an idempotency key. Always with jitter.
Circuit breaker
After N consecutive failures, stop calling and fail fast for a cooldown. Protects you from an upstream and the upstream from you.
Webhooks
Sign the payload (HMAC + timestamp), expect duplicates, respond 2xx fast and process asynchronously.
Location on 201
Send it. Clients and test suites rely on it, and it is the cheapest form of hypermedia.
Bulk operations
207 Multi-Status exists, but a per-item result array under 200 is easier for clients. Decide whether the batch is atomic and document it.
Long-running work
202 Accepted plus a job resource the client polls, or a webhook. Do not hold the connection open.
Trailing slashes
Pick one form and 301 the other. Two URIs for one resource means two cache entries.
