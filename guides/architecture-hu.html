Az ezen az oldalon szereplő minden architektúra ugyanannak az egy gondolatnak más-más léptékű alkalmazása: húzz egy vonalat valahová, és szabályozd, milyen irányban léphetik át a függőségek. Ha a gondolatot érted, a nevesített mintákat nem kell bemagolni.

Rétegek és a függőségi szabály

A rétegzett, a hexagonális, az onion és a clean architektúra ugyanannak a szabálynak négyféle rajza: a forráskód-függőségek befelé mutatnak, a szabályok felé, sosem kifelé, a részletek felé. A doménnek nem szabad tudnia, hogy létezik MySQL, HTTP vagy Symfony.

NévMit hangsúlyozMit tesz hozzá
Klasszikus rétegzett (n-tier)Megjelenítés → üzleti logika → adatSemmi nem akadályozza, hogy a felső réteg lenyúljon az aljára; a függőségek lefelé, az adatbázis felé mutatnak

Az a mechanizmus, ami lehetővé teszi a befelé mutató függőséget akkor is, amikor a vezérlés kifelé folyik, a függőséginverzió: a domén deklarálja az interfészt, amire szüksége van, és az infrastruktúra megvalósítja. Ez az egyetlen mozdulat — hogy az interfész a fogyasztójánál lakik, nem a megvalósításánál — teszi a rétegzett alkalmazásból hexagonálissá.

// Domain/Repository/Orders.php — a domén deklarálja, rajta kívül valósul meg.
namespace App\Domain\Order;

interface Orders
{
    public function get(OrderId $id): Order;
    public function save(Order $order): void;
    public function nextIdentity(): OrderId;
}
// Infrastructure/Persistence/DoctrineOrders.php — ez ismeri a Doctrine-t; a domén sosem.
namespace App\Infrastructure\Persistence;

final class DoctrineOrders implements \App\Domain\Order\Orders
{
    public function __construct(private EntityManagerInterface $em) {}

    public function get(OrderId $id): Order
    {
        return $this->em->find(Order::class, $id->toString())
            ?? throw new OrderNotFound($id);
    }
}

Így kérdezik — „Mi a különbség a hexagonális és a clean architektúra között?” Lényegében kevés — mindkettő a függőségi szabályt kényszeríti ki; a hexagonális a szimmetrikus portokat hangsúlyozza minden külső szereplőhöz, a clean a használati eseteket a középpontban. Aki azt mondja, hogy „lényegében ugyanaz a gondolat, és itt a közös szabály”, sokkal jobban hangzik annál, aki két ábrát felmond.

    Négy rajz, egy szabály. A doménnek nem szabad tudnia, hogy létezik MySQL, HTTP vagy Symfony. A klasszikus n-tier épp azért lóg ki, mert ott semmi nem akadályozza, hogy a függőségek lefelé, az adatbázis felé folyjanak.

    Az interfész a fogyasztójánál lakik, nem a megvalósítójánál. Ez az egy lépés fordít egy rétegzett alkalmazást hexagonálissá, és ez a gépies válasz arra a kérdésre, amire a legtöbben egy ábrával felelnek.

  3. Mi a különbség a hexagonális és a clean architektúra között?

    A „lényegében ugyanaz a gondolat, és itt a szabály, amin osztoznak” sokkal jobban hangzik, mint két ábra felmondása. A különbség hangsúly, nem lényeg.

Portok és adapterek a gyakorlatban

A port egy interfész, aminek a belső oldal a gazdája. Az adapter valami valódihoz köti. Két irányban léteznek, és a kettő összekeverése a szokásos hiba.

Vezérlő (elsődleges) adapterek

  • A külvilág hív befelé
  • HTTP controller, CLI-parancs, sorfogyasztó, cron
  • Az alkalmazás use case interfészétől függenek
  • Teszteléskor egyszerűen közvetlenül a use case-t hívod

Vezérelt (másodlagos) adapterek

  • A belső oldal hív kifelé
  • Repository, mailer, fizetési átjáró, óra, eseménybusz
  • Egy belülről deklarált interfészt valósítanak meg
  • Teszteléskor memóriabeli hamisítvánnyal helyettesíted
// Egy vezérelt port és két adapter — éles és teszt — egyetlen interfész mögött.
interface PaymentGateway
{
    public function charge(Money $amount, CardToken $card): ChargeResult;
}

final class StripeGateway implements PaymentGateway { /* HTTP, újrapróbálkozás, leképezés */ }

final class InMemoryGateway implements PaymentGateway     // a tests/ könyvtárban él
{
    public array $charges = [];
    public function charge(Money $amount, CardToken $card): ChargeResult
    {
        $this->charges[] = $amount;
        return ChargeResult::succeeded('ch_test_1');
    }
}
Az igazi port ismertetőjele. Ha nem tudsz értelmes memóriabeli implementációt írni az interfészhez, akkor az nem port — hanem az adatbázisod API-ja új néven. Egy repository-interfészen a findByQueryBuilder(QueryBuilder $qb) szivárgás: a domén ezzel a szignatúrán keresztül függ a Doctrine-tól.

Két portról szoktak megfeledkezni, amíg egy teszt el nem kezd villogni: az óra (interface Clock { public function now(): DateTimeImmutable; }) és az azonosítógenerátor. Mindkettő nemdeterminizmus, ami bejut a doménbe; mindkettő egysoros interfész, amitől az aggregátumtesztek reprodukálhatóvá válnak.

Így kérdezik — „Mit ad valójában a hexagonális architektúra?” Cserélhetőséget a széleken, és egy olyan domént, amit a keretrendszer indítása nélkül tudsz tesztelni. Az őszinte költséget — több interfész, több közvetettség, a definícióra ugrás interfészen landol — érdemes kimondani, mielőtt ők hoznák fel.

Ellenőrizd magad — 3 kérdés a témából

Mindegyiknél egy helyes válasz van. A választásaidat ez a böngésző megjegyzi, így legközelebb is itt lesznek.

  1. Mi a különbség egy vezérlő (driving) és egy vezérelt (driven) adapter között?

    A két irány összekeverése a szokásos hiba. A vezérlő oldal az alkalmazás use case-interfészétől függ; a vezérelt oldal egy olyan interfészt valósít meg, aminek az alkalmazás a gazdája. Csak a második függőséginverzió.

  2. Miről ismered meg a valódi portot a szivárgótól?

    A findByQueryBuilder(QueryBuilder $qb) a tankönyvi szivárgás — a domén ettől a szignatúrán keresztül a Doctrine-tól függ. A memóriabeli fake próbája gyors, őszinte, és a legtöbbjüket elkapja review-ban.

  3. Mely két portról feledkezik meg mindenki, amíg egy teszt el nem kezd villódzni?

    Mindkettő nemdeterminizmus, ami beszivárog a doménbe, és mindkettő egysoros interfész, amitől az aggregátumtesztek reprodukálhatóvá válnak. Az egésznek az őszinte ára — több interfész, több közvetettség, az interfészben landoló jump-to-definition — érdemes megnevezni, mielőtt az interjúztató felhozza.

Az alkalmazásréteg: use case-ek, nem controllerek

Az alkalmazásszolgáltatás (vagy command handler, vagy interactor) az a vékony réteg, ami koordinál: betölt egy aggregátumot, meghív rajta egy doménmetódust, perzisztál, eseményt küld. Saját üzleti szabálya nincs — ha van benne egy if pénzről, az a szabály a doménbe való.

final class RefundOrder                       // egy use case, egy osztály
{
    public function __construct(
        private Orders $orders,               // domén-port
        private PaymentGateway $payments,     // domén-port
        private UnitOfWork $transaction,      // infrastruktúra, explicit módon
        private EventDispatcher $events,      // PSR-14
    ) {}

    public function __invoke(RefundOrderCommand $command): void
    {
        $order = $this->orders->get(new OrderId($command->orderId));

        // A szabály az aggregátumban él; a szolgáltatás csak sorba rendezi a lépéseket.
        $refund = $order->refund(Money::fromMinor($command->amountMinor, $command->currency));

        $this->transaction->wrap(function () use ($order, $refund) {
            $this->payments->refund($refund);
            $this->orders->save($order);
        });

        foreach ($order->releaseEvents() as $event) {
            $this->events->dispatch($event);   // commit után — lásd az outbox témát
        }
    }
}

A controller ettől fordításra zsugorodik: HTTP be, parancsobjektum ki, eredményből válasz. Ettől lesz ugyanaz a use case elérhető egy CLI-parancsból, egy sorkezelő workerből és egy tesztből, duplikálás nélkül — és mivel ez az egész szerkezet gyakorlati haszna, ezzel kezdd, amikor a réteget magyarázod.

Így kérdezik — „Mi kerül a szolgáltatásba és mi az entitásba?” Koordináció és tranzakcióhatárok a szolgáltatásba; invariánsok és állapotátmenetek az entitásba. A kimondandó szag: az a szolgáltatás, ami kiolvassa az entitás mezőit, eldönt valamit, majd visszaírja — ez anémiás modell, kiszervezett logikával.

Mindegyiknél egy helyes válasz van. A választásaidat ez a böngésző megjegyzi, így legközelebb is itt lesznek.

  1. Mi tartozik az alkalmazásszolgáltatásba, és mi az entitásba?

    Tölts be egy aggregátumot, hívj rajta egy doménmetódust, perzisztálj, küldj eseményt. Ha a szolgáltatásban van egy if a pénzről, az a szabály a doménbe való.

  2. Milyen szaghibát érdemes kimondani ennek a rétegnek a leírásakor?

    A viselkedés azon az objektumon kívülre került, amelyiké az adat. Ez az anémiás doménmodell a gyakorlatban, és az alak leírása meggyőzőbb, mint az antiminta megnevezése.

  3. Mi a gyakorlati haszna annak, hogy a use case kikerül a controllerből?

    Ezzel kezdd a réteg magyarázatát. HTTP be, parancsobjektum ki, eredmény válasszá — minden más ott lakik, ahol mind a három belépési pont eléri.

Entitások, értékobjektumok, aggregátumok

EntitásVan azonosítója; az alapján egyenlőIdővel változikOrder, Customer
AggregátumKlaszter egyetlen gyökérentitássalCsak a gyökéren keresztül módosulOrder és a hozzá tartozó OrderLine-ok

final class Order                       // aggregátumgyökér
{
    private array $lines = [];
    private array $events = [];

    public function addLine(ProductId $product, int $quantity, Money $unitPrice): void
    {
        if ($this->status !== OrderStatus::Draft) {
            throw new OrderNotEditable($this->id);      // az invariáns, itt kikényszerítve
        }
        if ($quantity < 1) {
            throw new InvalidQuantity($quantity);
        }

        $this->lines[] = new OrderLine($product, $quantity, $unitPrice);
        $this->events[] = new LineAdded($this->id, $product, $quantity);
    }

    /** Nincs setter, nincs publikus gyűjtemény. A hívó nem kerülheti meg a fenti szabályokat. */
    public function lines(): array { return $this->lines; }
}

Az aggregátumhatár konzisztenciahatár: ami belül van, az egy tranzakcióban mentődik és mindig érvényes; ami kívül, az azonosítón keresztül érhető el, és csak eventually lesz konzisztens. Ebből jön a méretezési heurisztika: tartsd kicsin az aggregátumokat, más aggregátumra azonosítóval hivatkozz, ne objektummal, és ha egy szabály két aggregátumon ível át, akkor vagy egy aggregátum a kettő, vagy a szabály eventually consistent. Egy Order, ami egy teljes Customer objektumot tart, a klasszikus túlméretezett aggregátum.

Anémiás doménmodell. Olyan entitások, amik getterekkel és setterekkel felszerelt adatzsákok, és minden viselkedés szolgáltatásokban van. Fowler azért nevezte antimintának, mert egy objektummodell költségét fizeted ki, és semmit nem kapsz cserébe belőle. Ugyanakkor ez a legtöbb keretrendszer-tutorial alapértelmezett alakja, tehát számíts rá, hogy megkérdezik, megtartanád-e — az „igen egy CRUD (create, read, update, delete) adminfelületen, nem az árazómotorban” jobb válasz, mint bármelyik irányba tett dogma.

Így kérdezik — „Hogyan döntöd el, hol van az aggregátumhatár?” Tranzakciós invariáns alapján: minek kell igaznak lennie minden commitnál. Ha két dolog rövid ideig inkonzisztens lehet anélkül, hogy az üzletet elrontaná, akkor különböző aggregátumokhoz tartoznak, és eseményeken keresztül beszélnek.

Mindegyiknél egy helyes válasz van. A választásaidat ez a böngésző megjegyzi, így legközelebb is itt lesznek.

  1. Hogyan döntöd el, hol legyen az aggregátumhatár?

    Az aggregátumhatár konzisztenciahatár. Ebből a méretezési ökölszabály közvetlenül adódik: tartsd kicsin az aggregátumokat, hivatkozz a többire azonosítóval, és ha egy szabály kettőn ível át, akkor vagy egy aggregátum a kettő, vagy a szabály eventually konzisztens.

  2. Mi különbözteti meg az értékobjektumot az entitástól?

    Az azonosság a választóvonal, és az immutabilitás ebből következik. A Money, az Email és a DateRange érték; az Order és a Customer entitás. A repository gyűjtemény-szerű hozzáférést ad, kizárólag aggregátumgyökerekhez.

  3. Megtartanál egy anémiás doménmodellt?

    A dogma mindkét irányban gyenge válasz. A kritika valós — az objektummodell költségét fizeted, a hasznát nem kapod meg —, de egy hat mezőt szerkesztő képernyőnek nem kell gazdag modell, és épp az a lényeg, hogy megmondod, melyik melyik.

Bounded contextek és a moduláris monolit

A bounded context (határolt kontextus) az a hatókör, amin belül egy fogalomnak egy jelentése van. A számlázás „ügyfele” (fizető fél adószámmal) nem ugyanaz, mint a support „ügyfele” (személy, akinek ticketjei vannak). Ha mindkettőre egy közös Customer osztályt erőltetsz, attól válik a modell karbantarthatatlanná.

KapcsolatJelentés
Shared kernelKét kontextus szándékosan oszt meg egy kis modellt. Olcsó, és összeköti a kiadási ciklusokat
Customer / supplierA lefelé lévő igényei befolyásolják a felfelé lévő tervét
ConformistA lefelé lévő úgy fogadja el a felfelé lévő modelljét, ahogy van — nincs fordítási keret
Anti-corruption layerA lefelé lévő a határon fordít, hogy a saját modelljét tisztán tartsa
Published languageKözös, verziózott csereformátum — események, API-séma

Moduláris monolit

  • Egy deploy-egység, kemény modulhatárokkal belül
  • Folyamaton belüli hívások: nincsenek hálózati hibamódok
  • Modulok közti tranzakció továbbra is lehetséges — és ez a kísértés
  • Egy határ átszabása átnevezés, nem migráció

Mikroszolgáltatások

  • Független deploy, skálázás és technológiaválasztás
  • Minden hívás hibázhat, lassulhat vagy kétszer érkezhet
  • Nincs szolgáltatásokon átívelő tranzakció — sagák és eventual consistency
  • Kell hozzá az üzemeltetési érettség: tracing, szerződések, CI/CD

A védhető alapértelmezés 2026-ban, és amit a legtöbb interjúztató hallani remél: kezdd moduláris monolitként, olyan határokkal, amiket tényleg kikényszerítesz (eszközzel, nem fegyelemmel), és akkor emelj ki egy szolgáltatást, amikor konkrét nyomás van rá — független skálázás, más futtatókörnyezet, vagy csapatautonómia olyan méretnél, ahol a közös kódbázis a szűk keresztmetszet. Az elosztott rendszer olyan költség, amit legalább annyiszor fizetsz ki szervezeti, mint technikai okból.

Így kérdezik — „Mikroszolgáltatásokat használnál itt?” Kérdezz vissza, milyen nyomás indokolná, aztán válaszolj. A „még nem — moduláris monolit kikényszerített határokkal, és itt az a seam, amit elsőként emelnék ki, ha X bekövetkezik” senior válasz. Az „igen, a mikroszolgáltatások jobban skálázódnak” nem.

  1. Mi az a bounded context?

    Ha mindkettőre ráerőltetsz egy közös Customer osztályt, onnantól lesznek karbantarthatatlanok a modellek. A kontextusok közti viszonyminták — shared kernel, konformista, anti-corruption layer, published language — arról szólnak, mennyi fordítást vagy hajlandó megfizetni.

  2. Mit tart meg a moduláris monolit abból, amit a mikroszolgáltatások feladnak?

    A modulokon átívelő tranzakció egyben a kísértés is — pont az, ami csendben erodálja a meghúzott határt. Ezért kell a határokat eszközzel kikényszeríteni, nem fegyelemmel.

  3. Mi a védhető alapértelmezés 2026-ban?

    A kiemelésnek megnevezhető nyomásra kell válaszolnia. A mikroszolgáltatások ráadásul megkövetelik a hozzájuk illő üzemeltetési érettséget — tracing, szerződések, CI/CD —, és a legtöbb „majd szétszedjük” terv épp ezt a költséget hagyja ki.

Ez az a három betűszó, amire az álláshirdetés gondolt, plusz az a két mechanizmus, amitől élesben túlélhetők. Mindegyik valóban hasznos és valóban drága; az interjú azt méri, ismered-e mindkét felét.

CQRS pontosan

Command Query Responsibility Segregation: különböző modell az íráshoz és az olvasáshoz. Ennyit mond. Nem követel event sourcingot, két adatbázist, üzenetbuszt vagy eventual consistencyt — ezek olyan lehetőségek, amiket megnyit.

Írási modell

  • Aggregátumok, invariánsok, normalizált
  • Azonosító alapján töltődik, sosem listákhoz kérdezed
  • Helyességre optimalizált

Olvasási modell

  • Lapos DTO-k a képernyő alakjára szabva
  • Sima SQL, joinok, nincsenek entitások
  • A lekérdezésre optimalizált, szabadon denormalizálva
// Olvasási oldal: nincs ORM, nincsenek doménobjektumok, csak az az alak, ami az oldalnak kell.
final class OrderSummaryQuery
{
    public function __construct(private PDO $db) {}

    /** @return list<OrderSummary> */
    public function forCustomer(string $customerId, int $limit): array
    {
        $stmt = $this->db->prepare(
            'SELECT o.id, o.status, o.total_minor, o.currency, c.name AS customer_name,
                    COUNT(l.id) AS line_count
             FROM orders o
             JOIN customers c ON c.id = o.customer_id
             LEFT JOIN order_lines l ON l.order_id = o.id
             WHERE o.customer_id = :customer
             GROUP BY o.id
             ORDER BY o.created_at DESC
             LIMIT :limit'
        );
        // ... végrehajtás, majd a sorok leképezése readonly DTO-kra.
    }
}

A CQRS (Command Query Responsibility Segregation) legolcsóbb hasznos változata pontosan ez: az írásokhoz marad a Doctrine, az olvasásokhoz leszállsz SQL-be, és nem próbálod ugyanazt az entitásgráfot mindkettőre ráhúzni. Nulla extra infrastruktúra, a haszon nagy része megvan. A drága változat — külön olvasási tár, amit események tartanak naprakészen — független skálázást és olyan lekérdezési alakokat ad, amiket az írási tár nem tud kiszolgálni, cserébe eventual consistencyt és egy karbantartandó projekciót kapsz. Használati esetenként vezesd be, sose egyben.

„Lássam a saját írásomat.” Amint az olvasási modell aszinkron, az a felhasználó, aki ment, majd átirányítódik egy listára, lehet, hogy nem látja a változását. Kezeld tudatosan: a parancs után olvass az írási modellből, add vissza a létrehozott erőforrást a válaszban, vagy tedd optimistává a felületet. A „a projekció általában gyors” nem terv.

Így kérdezik — „Mi az a CQRS, és mikor használnád?” Külön modell olvasásra és írásra; akkor, ha a kettőnek tényleg más az alakja vagy a terhelési profilja. Mondd ki kifejezetten, hogy nem jelent két adatbázist — általában pontosan ezt a különbségtételt ellenőrzik.

    Ennyi a teljes definíció. Ha ezt kimondod, majd megnevezed, mit tesz lehetővé, az különbözteti meg azt, aki használta, attól, aki olvasott róla.

Az outbox minta

Írnod kell az adatbázisba és publikálnod kell egy üzenetet. Két rendszer, közös tranzakció nélkül — tehát bármelyik sikerülhet egyedül. Naivan megcsinálva ez a dual-write probléma, és olyan rendelések lesznek belőle, amikről nincs értesítés, vagy értesítések olyan rendelésekről, amik nem léteznek.

// Ugyanabban a tranzakcióban, mint az üzleti változás: a broker még nincs a képben.
$this->transaction->wrap(function () use ($order) {
    $this->orders->save($order);

    foreach ($order->releaseEvents() as $event) {
        $this->outbox->add(new OutboxMessage(
            id: Uuid::v7(),
            topic: 'orders.refunded.v1',
            payload: $this->serializer->serialize($event),
            createdAt: $this->clock->now(),
        ));
    }
});

// Egy külön worker olvassa (vagy a binlogot követi) és publikál. Összeomlásbiztos:
// a sor csak a broker nyugtázása után lesz elküldöttnek jelölve, tehát a hibamód
// a duplikált publikálás - ezért kell a fogyasztóknak idempotensnek lenniük.

Ugyanennek a garanciának a fogyasztóoldali párja az inbox: minden feldolgozott eventId-t rögzítesz egy egyedi indexes táblában, ugyanabban a tranzakcióban, mint a mellékhatást. Az újraküldött üzenet így az egyediségsértésbe fut és kimarad. A kettő együtt gyakorlatilag pontosan-egyszeri feldolgozást ad a legalább-egyszeri kézbesítés fölött — ezt a megfogalmazást használd, mert „pontosan egyszeri kézbesítés” nem létezik, és az interjúztatók szeretik, ha ezt valaki kimondja.

Így kérdezik — „Hogyan tartod konzisztensen az adatbázist és az üzenetbrokert?” Tranzakciós outbox plusz idempotens fogyasztó. Attól ül le a válasz, hogy a megoldás előtt megnevezed a dual-write problémát.

  2. Mi az outbox fogyasztóoldali párja?

    Az interjúztatók szeretik, ha ezt kimondják. A garancia a fogyasztóban lakik, nem a szállításban, és minden terv, ami mást feltételez, rejt egy felfedezetlen duplikált feldolgozási hibát.

Event sourcing

Az igazság forrása az események sorozata; az aktuális állapot ennek a sorozatnak az összehajtogatása. Nem ugyanaz, mint a CQRS, bár természetesen párosodnak, hiszen egy eseménytár rossz hely lekérdezésre.

final class Order
{
    private array $pending = [];
    private int $version = 0;

    public static function reconstitute(iterable $history): self
    {
        $order = new self();
        foreach ($history as $event) {
            $order->apply($event);      // visszajátszáskor nincs validáció: a történelem tény
            $order->version++;
        }
        return $order;
    }

    public function refund(Money $amount): void
    {
        if ($amount->greaterThan($this->refundable())) {
            throw new RefundExceedsBalance();     // a döntések validálnak...
        }
        $this->recordThat(new OrderRefunded($this->id, $amount, $this->clock->now()));
    }

    private function apply(object $event): void   // ...az alkalmazás csak állapotot módosít
    {
        match (true) {
            $event instanceof OrderRefunded => $this->refunded = $this->refunded->plus($event->amount),
            $event instanceof OrderPlaced   => $this->total = $event->total,
        };
    }
}

Amibe kerül

Egy általad értett minta ellen érvelni ebben az egész részben a legerősebb jelzés.

Sagák, folyamatmenedzserek, eventual consistency

Egy több szolgáltatáson átívelő üzleti tranzakció nem lehet adatbázis-tranzakció. A saga lokális tranzakciókra bontja, mindegyikhez egy kompenzáló művelettel a visszagörgetéshez — mert egy terhelést nem tudsz meg nem történtté tenni, csak visszatéríteni.

Koreográfia

  • Minden szolgáltatás eseményekre reagál, nincs koordinátor
  • Lazán csatolt, könnyű elkezdeni
  • Nincs egyetlen hely, ahol a folyamat látszik
  • Körök és meglepetések, ahogy a folyamat nő

Orkesztráció

  • Egy folyamatmenedzser tartja az állapotgépet és ad ki parancsokat
  • A folyamat explicit, tesztelhető, megfigyelhető
  • Az orkesztrátor egy komponens, amit birtokolni és telepíteni kell
  • Isten-szolgáltatássá válhat, ha logikát halmoz

A sagáknak nincs izolációjuk, és ennek olyan következményei vannak, amiket érdemes kérdés nélkül kimondani: a köztes állapotok más olvasók számára láthatók, tehát adatbázis-zárak helyett szemantikus zárakra van szükség (egy rendelés pending_payment állapotban), a kompenzációknak pedig idempotensnek és sorrendfüggetlennek kell lenniük. Az időtúllépések a terv részei — minden lépésnél kell válasz arra, hogy „mi van, ha sosem jön válasz”, és ez általában egy ütemezett kompenzáció.

Így kérdezik — „Hogyan kezelsz egy három szolgáltatáson átívelő tranzakciót?” Sehogy; sagát futtatsz kompenzációkkal, és kimondod, hogy a rendszer eventually consistent, és a részleges állapotok megfigyelhetők. A kétfázisú commithoz nyúlni azért rossz válasz, amiért érdemes elmagyarázni: blokkol, és minden résztvevőnek támogatnia kell.

    Egy terhelést nem lehet visszacsinálni, csak visszatéríteni. A kétfázisú commit pont azért rossz válasz, amit érdemes elmondani: blokkol, és minden résztvevőnek támogatnia kell.

  2. Mi a kompromisszum a koreográfia és az orkesztráció között?

    Ha ezt kérdés nélkül kimondod, a válasz használtnak hangzik, nem olvasottnak. Az időkorlátok is a terv részei: minden lépésnek kell válasza arra, hogy „mi van, ha a válasz sosem érkezik meg” — ez rendszerint egy ütemezett kompenzáció.

  1. Mit jelent a gyakorlatban az, hogy „a keretrendszer csak részlet”?

    A hívás irányáról szól, nem absztinenciáról. Portok mint autowire-olt interfészek, adapterek mint szolgáltatások, use case-ek a Messenger command busa mögött, doménesemények PSR-14-en át flush után — az ő szókincsükben válaszolj.

  2. Az Eloquent Active Record, ami a modellt az adatbázishoz köti. Mi a két őszinte álláspont?

    Mindkettő védhető; a tettetés nem. Az „lecserélném az Eloquentet Doctrine-ra” egy Laravel-boltban rendszerint nem az a válasz, amit hallani akarnak.

  3. Melyik PSR szabványosítja azt a kéréspipeline-t, amit a Symfony és a Laravel is a maga módján fejez ki?

    A PSR-15 a middleware-ekre és kéréskezelőkre. A többi ugyanebben a leképezésben: PSR-11 a konténerre, PSR-14 az eseményekre, PSR-3 a naplózásra — és nevezetesen semmilyen szabvány az aszinkron munkára és a perzisztenciára.

Kompromisszumok, fitness functionök, ADR-ek

Egy architektúra-interjú senior része ritkán az, hogy „ismered-e a CQRS-t”. Hanem az, hogy meg tudod-e mondani, mibe kerül egy döntés, honnan tudnád meg, hogy rossz volt, és hogyan kerül rögzítésre.

Egy használható keret bármely javaslathoz, hangosan, ebben a sorrendben: melyik minőségi jellemzőre optimalizálunk (késleltetés? független deploy? auditálhatóság?), mit adunk fel, mennyibe kerül a visszafordítás, ha tévedünk, és mit mérnénk, hogy ez kiderüljön. Ez utóbbi a fitness function — egy automatikus ellenőrzés arra, hogy a tulajdonság még fennáll: architektúra-teszt a függőségi szabályra, teljesítménybüdzsé a CI-ban, riasztás a projekció lemaradására.

# docs/adr/0007-outbox-for-order-events.md
# Állapot:      Elfogadva (2026-09-10)
# Kontextus:    A rendeléseknek értesíteniük kell a számlázást; a közvetlen hívás összeköti
#               a rendelkezésre állást, a naiv commit utáni publikálás pedig üzenetet veszít,
#               ha a broker áll.
# Döntés:       Tranzakciós outbox a rendelések sémájában, workerrel olvasva.
# Következmények:
#   + Nincs dual-write inkonzisztencia; a broker leállása csak késlelteti a kézbesítést.
#   - Duplikált publikálás lehetséges: minden fogyasztónak kell inbox tábla.
#   - Egy további workert kell futtatni, monitorozni és riasztani rá (lemaradás > 60s riaszt).
# Alternatívák: 2PC (elvetve: blokkol, a brokerünk nem támogatja),
#               CDC a binlogon (egyelőre elvetve: üzemeltetési költség, méretnél újranézni).

Az ADR (Architecture Decision Record) egy oldal a repositoryban, elfogadás után módosíthatatlan, nem szerkesztjük, hanem leváltjuk. A valódi értéke fél évvel később derül ki, amikor valaki megkérdezi, hogy miért — és azért tűnik ki az a jelölt, aki ADR-eket említ, mert ez azt jelzi, hogy elvárja, hogy számon kérjék rajta a döntéseit, nem csak meghozza őket és továbbáll.

Így kérdezik — „Mesélj egy architekturális döntésről, amit megbántál.” Válaszolj egy valódival, a jellel, amiből kiderült, és azzal, amin változtattál. Annak megnevezése, hogy milyen visszafordítási költséget hagytál figyelmen kívül, többet ér bármennyi mintaszókincsnél.

Strangler fig, seamek, anti-corruption layer

Senki nem ír újra egy működő rendszert. A strangler fig minta fokozatosan cseréli le: teszel elé egy homlokzatot, egyszerre egy képességet irányítasz át az új implementációra, és törlöd a régi utat, amint elfogyott róla a forgalom.

// A seam: egy interfész, két implementáció, kapcsolóval vezérelt útválasztás.
final class RoutingInvoices implements Invoices
{
    public function __construct(
        private Invoices $legacy,
        private Invoices $rebuilt,
        private FeatureFlags $flags,
    ) {}

    public function issue(InvoiceRequest $request): Invoice
    {
        if (!$this->flags->enabled('invoices.rebuilt', $request->tenantId)) {
            return $this->legacy->issue($request);
        }

        $invoice = $this->rebuilt->issue($request);

        // Opcionális árnyékmód: fusson mindkettő, hasonlítsd össze, naplózd az eltérést,
        // és a régit szolgáld ki, amíg az eltérési arány nulla nem lesz.
        // Pénzügyi kódot így kell migrálni.
        return $invoice;
    }
}

A munka nagy részét két támogató gondolat végzi. A seam az a hely, ahol a viselkedés megváltoztatható a körülötte lévő kód szerkesztése nélkül — PHP-ban egy interfész plusz konstruktorinjektálás; a seamek megtalálása vagy létrehozása minden legacy migráció első lépése. Az anti-corruption layer egy fordítási határ, ami megakadályozza, hogy a legacy modell átszivárogjon az újba: az új kontextus a saját nyelvét beszéli, és a szélén konvertál. Enélkül az újraírás pontosan azt az alakot örökli, ami elől menekülni akart.

Így kérdezik — „Hogyan modernizálnál egy tízéves PHP-alkalmazást?” Soha nem nagy bumm újraírással. Karakterizációs tesztek a jelenlegi viselkedés rögzítésére, homlokzat a határon, egy képesség kiemelése ACL-lel (anti-corruption layer), forgalomátterelés feature flaggel és árnyékösszehasonlítással, majd a régi út törlése. Aztán: azt a képességet vedd először, ahol a változási ráta a legnagyobb, mert ott térül meg.

Mindegyiknél egy helyes válasz van. A választásaidat ez a böngésző megjegyzi, így legközelebb is itt lesznek.

  1. Mit mond ki Conway törvénye, és mi a „fordított manőver”?

    Ha három csapat birtokol egy szolgáltatást, három modult fogsz kapni benne. A fordított manőver szándékos: előbb a csapathatárokat változtatod meg, és a rendszer követi.

  2. Mi a CAP őszinte megfogalmazása?

    A „válassz kettőt” az a változat, ami diákon túlél, de az első rákérdezésnél szétesik. Ugyanez a műveletszintű gondolkodás áll az eventual consistencyre is: valakinek el kell fogadnia, hogy egy képernyő két másodpercig elavult lehet, és ez terméki döntés.

  3. Miért rosszabb két szolgáltatás közös adatbázisa, mint egy monolit?

    Megfizeted az elosztottság adóját anélkül, hogy bármit vennél rajta. Ugyanebbe az egysoros családba tartozik: a könyvtárak Domain/ és Infrastructure/ névre keresztelése semmit nem változtat, ha az entitás továbbra is az ORM ősosztályából származik — a hexagonális nem könyvtárszerkezet.
