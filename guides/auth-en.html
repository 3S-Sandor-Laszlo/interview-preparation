Foundations

4 topics

Every token question eventually reduces to two older ones: where does the secret live, and what happens when it leaks. Start here and the JWT debate answers itself.

Authentication, authorization, and the third one

Authentication

  • Who are you?
  • Verifies a claim of identity against a factor
  • Happens once per session, at a boundary
  • Failure → 401 + WWW-Authenticate

Authorization

  • May you do this, to this?
  • Evaluates a policy against identity, action and resource
  • Happens on every operation, near the data
  • Failure → 403

The third one is accounting — the audit trail. If your answer to “who cancelled this order” is a updated_at column, you do not have one. Factors come in three kinds: something you know (password), something you have (a TOTP device, a passkey, a hardware key), something you are (biometric). MFA means factors from different kinds; a password plus a security question is one factor twice.

Where authorization goes wrong. Authentication is a boundary concern and belongs in middleware. Authorization is a domain concern and belongs where the resource is loaded — the middleware that checked “is a logged-in user” cannot know whether this user owns that order. Splitting them across those two places is the single most useful structural idea in this guide.

Asked as — “What is the difference between 401 and 403?” Then, immediately: “Where in your application do each of those get decided?” The second question is the real one — a candidate who puts both in the same middleware layer has usually shipped an IDOR.

Password storage, done in four lines

PHP gives you the whole thing; the interview checks whether you know why each piece exists.

// Hash. The salt is generated for you and embedded in the output string.
$hash = password_hash($plain, PASSWORD_ARGON2ID);   // or PASSWORD_DEFAULT (bcrypt today)

// Verify. Constant-time comparison of the derived hash — never ===.
if (!password_verify($plain, $user->hash)) {
    throw new InvalidCredentials();
}

// Upgrade transparently when you raise the cost or change the algorithm.
if (password_needs_rehash($user->hash, PASSWORD_ARGON2ID)) {
    $users->updateHash($user->id, password_hash($plain, PASSWORD_ARGON2ID));
}
ConceptWhy it exists
Salt (per password, stored with the hash)Two users with the same password get different hashes; rainbow tables die
Pepper (a secret, stored outside the DB)A dumped database alone is not enough to start cracking. Optional, and a key-rotation problem
Work factor / memory costDeliberate slowness. Argon2id is memory-hard, so GPUs and ASICs lose their advantage
bcrypt's 72-byte limitLonger passwords are silently truncated — pre-hash with SHA-384+base64 if you must, or use Argon2id
Constant-time comparepassword_verify and hash_equals do not leak how many bytes matched

Around the hash: rate limit by account and by IP, lock out with exponential delay rather than a hard freeze (a hard freeze is a denial-of-service against your own users), return the same generic error and roughly the same timing for “no such user” and “wrong password”, and check new passwords against a breached-password list instead of demanding a symbol and a capital letter. Password reset tokens are single-use, short-lived, and stored hashed — they are password-equivalent.

Asked as — “How do you store passwords?” password_hash with Argon2id, verify with password_verify, rehash on login when the cost changes. If they push further, the answer they want is “the salt is inside the hash string, and the algorithm is deliberately slow”.

  1. Why does password_hash() need no separate salt column?

    The output is self-describing, which is what lets password_verify() work without being told anything and password_needs_rehash() detect a changed cost. Salting kills rainbow tables; the deliberate slowness is what fights brute force.

  2. What is bcrypt's notorious limit?

    Silent truncation is the dangerous part — a 100-character passphrase is no stronger than its first 72 bytes. Pre-hash with SHA-384 and base64 if you must stay on bcrypt, or use Argon2id, which is memory-hard and therefore far less friendly to GPUs and ASICs.

  3. Why return the same generic error, with roughly the same timing, for “no such user” and “wrong password”?

    Account enumeration is a real finding, and signup and reset forms leak it just as easily as login. Sessions in PHP

A session is a random identifier in a cookie plus server-side state. It is stateful by design, and that statefulness is a feature: you can revoke it instantly.

// Fixation defence: a new id at every privilege change, old data carried over.
session_start();
if ($credentialsAreValid) {
    session_regenerate_id(true);      // true = delete the old session file/row
    $_SESSION['user_id'] = $user->id;
    $_SESSION['issued_at'] = time();
    $_SESSION['fingerprint'] = hash('sha256', $request->getHeaderLine('User-Agent'));
}

// Idle and absolute timeouts. Only one of these is usually implemented; ask for both.
if (time() - $_SESSION['last_seen'] > 1800 || time() - $_SESSION['issued_at'] > 43200) {
    session_unset();
    session_destroy();
    throw new SessionExpired();
}
$_SESSION['last_seen'] = time();

Logout must destroy server state, not just clear the cookie — otherwise the id remains valid for anyone who captured it. Storage: files do not work across multiple app servers, so it is Redis, Memcached or a database table; a database gives you “list and revoke my active sessions”, which product will ask for eventually. Store the id, never anything sensitive, and treat the session record as the place to hang the security metadata (IP, device, created-at) you will want during an incident.

Session fixation. The attacker sets a known session id (via a link with ?PHPSESSID=, or a subdomain cookie), waits for the victim to log in, and then holds a session that is now authenticated. session_regenerate_id(true) at login is the fix; session.use_strict_mode=1 in php.ini makes PHP reject client-supplied unknown ids in the first place.

Asked as — “What is session fixation and how do you prevent it?” Regenerate the id on every privilege change, enable strict mode, and scope the cookie so subdomains cannot write it. Bonus points for “and rotate on password change, then invalidate every other session”.

  1. Why must logout destroy server-side state rather than just clearing the cookie?

    The id is the credential. Revocability is the whole advantage of stateful sessions, and it only exists if you actually delete the record.

  2. Why is file-based session storage a problem in production?

    Sticky sessions are a workaround, not a solution. The session record is also the right place to hang security metadata — IP, device, created-at — that you will want during an incident.

  3. What does session.use_strict_mode=1 add on top of regenerating the id at login?

    Two layers against fixation. session_regenerate_id(true) at every privilege change invalidates a planted id; strict mode stops it being accepted at all. Bonus: rotate on password change and invalidate every other session.

    'lifetime' => 0,          // session cookie; expiry is enforced server-side anyway
    'path'     => '/',
    'domain'   => '',         // host-only: no subdomain sharing
    'secure'   => true,
    'httponly' => true,

ini_set('session.cookie_httponly', '1');

SameSite=Lax removes most classic CSRF, but it is a defence in depth, not a replacement: it does not protect against GET-triggered state changes, it does not apply to same-site requests from a compromised subdomain, and older clients ignore it. Keep synchroniser tokens (or the double-submit pattern) on state-changing forms, and never make a GET mutate anything.

Asked as — “Does SameSite mean we can drop CSRF tokens?” No — narrower attack surface, same requirement. Explaining why (subdomains, legacy clients, non-browser clients) is the answer; “no, because best practice” is not.

5 topics

The JWT conversation is the most reliable senior filter in this whole area, because the popular answer (“stateless, therefore scalable”) is the one that falls apart under two follow-up questions.

Sessions vs JWT: the actual trade-off

Server-side session

  • Opaque random id; all state on the server
  • Revocation is instant — delete the row
  • Small cookie, no size pressure
  • Needs a shared store (Redis/DB) across app servers
  • Every request costs one store lookup

JWT (self-contained)

  • Claims carried in the token, verified by signature
  • Revocation is the hard part — valid until it expires
  • Grows with claims; goes in every request
  • No shared store — attractive across services
  • Verification is local (a signature check)

Notice what is not on the list: “sessions do not scale”. A Redis lookup is sub-millisecond and you almost certainly already run Redis. The honest framing is that a JWT trades revocability for independence — you accept a window in which a logged-out or demoted user still passes the check, in exchange for services that can verify without calling anyone. That trade is worth it between services and across trust boundaries. Inside one monolith serving its own browser clients, it usually buys nothing.

The blacklist tell. Teams add a revocation list in Redis so JWTs can be invalidated — and now every request hits a shared store, which was precisely the cost they adopted JWTs to avoid, plus signature verification. If you find yourself there, you have re-implemented sessions with extra steps. The defensible middle: short-lived access tokens (5–15 minutes) so the revocation window is bounded, and a stateful refresh token that you can revoke.

Asked as — “Sessions or JWT for a new app?” Sessions for a first-party web app; JWT (or better, opaque tokens plus introspection) at service boundaries. Then name the revocation window explicitly. Answering “JWT, because stateless scales better” without that is the single most common way to lose a senior interview on this topic.

JWT anatomy

Three base64url segments separated by dots: header, payload, signature. Base64 is encoding, not encryption — anyone holding the token reads every claim. A signed token (JWS) proves integrity and origin; only an encrypted one (JWE) hides content, and almost nobody uses JWE.

{ "alg": "RS256", "typ": "JWT", "kid": "2026-09-key-1" }
{
  "iss": "https://auth.example.com",
  "sub": "user_42",
  "aud": "https://api.example.com",
  "exp": 1789004400,
  "nbf": 1789003500,
  "iat": 1789003500,
  "jti": "01JB8Z4K3Q7X",
  "scope": "orders:read orders:write",
  "tenant": "acme"
}
use Firebase\JWT\{JWT, Key};

// Verification: pin the algorithm, then check every claim that matters.
$claims = JWT::decode($jwt, new Key($publicKeyForKid, 'RS256'));   // alg pinned here

if ($claims->iss !== 'https://auth.example.com') { throw new UntrustedIssuer(); }
if (!in_array('https://api.example.com', (array) $claims->aud, true)) { throw new WrongAudience(); }
if ($this->revoked->contains($claims->jti)) { throw new TokenRevoked(); }
// exp / nbf are checked by the library; JWT::$leeway allows for clock skew (keep it small).

HS256 (symmetric)

  • One shared secret signs and verifies
  • Fine when issuer and verifier are the same service
  • Every verifier can also forge tokens

RS256 / ES256 (asymmetric)

  • Private key signs, public key verifies
  • Correct across services and third parties
  • Public keys published at a JWKS endpoint, selected by kid — which is what makes rotation possible

Asked as — “Can you put the user's role in a JWT?” Yes, and that is exactly the revocation trap: demote the user and the old token still says admin until exp. Either keep the token lifetime short enough that you accept the window, or look up authorization data server-side and keep only identity in the token.

  1. What does signing a JWT give you, and what does it not?

    JWS proves nobody changed it; it hides nothing. JWE exists and almost nobody uses it — which means email addresses, internal ids and permission sets in a payload are disclosure you did not intend.

  2. When is HS256 acceptable, and when do you need RS256 or ES256?

    Symmetric signing makes every verifier an issuer. The asymmetric setup also gives you rotation: public keys published at a JWKS endpoint and selected by kid.

  3. Can you put the user's role in a JWT?

    Either keep the lifetime short enough that you accept the window, or keep only identity in the token and look up authorization data server-side. Putting a permission set in a long-lived token is how a fired employee keeps access.

How JWTs get broken

AttackMechanismDefence
alg: noneAttacker strips the signature; a naive library accepts an unsigned tokenNever let the token choose the algorithm — pass the expected one explicitly
Algorithm confusionToken switched from RS256 to HS256, signed with the public key as the HMAC secretPin the algorithm per key; reject any mismatch
Unverified decodeCode reads claims before (or instead of) verifying the signatureVerify first, always. Never trust kid or iss from an unverified token
kid injectionkid used as a file path or SQL value → traversal or injectionTreat kid as an opaque lookup key in a fixed key set
jku / x5u abuseHeader points at an attacker-controlled key URLIgnore these headers; hardcode or allowlist the JWKS URI
Missing aud checkA token minted for service A is replayed against service BVerify aud (and iss) on every service

Sensitive data in claims. A JWT in a browser is readable by the user, by anything with XSS, and by whatever logs the Authorization header. Email addresses, internal ids and permission sets in a token are all disclosure you did not intend. Also watch payload size — a few kilobytes of claims on every request adds up, and some proxies cap header size.

Asked as — “What is the none algorithm attack?” Then the sharper follow-up: “Your library takes the algorithm from the token header. Is that safe?” No — the verifier must state which algorithm and key it expects, because the token is attacker-controlled input.

Check yourself — 3 questions on this topic

One right answer each. Your choices are kept in this browser, so the page remembers them next time.

  1. Your JWT library takes the algorithm from the token's own header. Is that safe?

    Letting the token choose is the root of two attacks at once. alg: none strips the signature entirely; algorithm confusion switches RS256 to HS256 and signs with the public key as the HMAC secret. Pin the algorithm per key and reject any mismatch.

  2. Why must kid be treated as an opaque lookup key into a fixed key set?

    Everything in the header is unverified until the signature checks out. The same reasoning kills jku and x5u: a header pointing at an attacker-controlled key URL should simply be ignored.

  3. What is wrong with reading a claim before verifying the signature?

    Verify first, always. The convenience helper that decodes without verifying exists in most libraries and is the source of a whole class of incidents. Watch payload size too: a few kilobytes of claims on every request adds up, and some proxies cap header size.

Refresh token rotation and reuse detection

Short access tokens need a way to be renewed without a fresh login. A refresh token is long-lived, opaque, stored server-side hashed, and — this is the part interviews probe — single-use.

final class RefreshTokens
{
    /**
     * Rotation: every use mints a new token and retires the old one.
     * If a retired token is presented again, the family is compromised.
     */
    public function rotate(string $presented): TokenPair
    {
        $row = $this->findByHash(hash('sha256', $presented));

        if ($row === null) {
            throw new InvalidToken();
        }

        if ($row->usedAt !== null) {
            // Reuse of an already-rotated token: either the legitimate client
            // replayed it, or it was stolen. You cannot tell which — assume theft.
            $this->revokeFamily($row->familyId);
            throw new TokenReuseDetected();          // force a full re-login
        }

        if ($row->expiresAt < new DateTimeImmutable()) {
            throw new TokenExpired();
        }

        $this->markUsed($row->id);
        $new = $this->issue($row->userId, $row->familyId);   // same family, new token

        return new TokenPair($this->mintAccessToken($row->userId), $new);
    }
}

The family id is what makes detection useful: revoking one token stops nothing if the attacker can keep rotating, so revoke every descendant of the original login. Add a small grace window (a few seconds, returning the same new pair) if you have clients that race their own refresh calls — otherwise a double-tab reload logs people out. Refresh tokens are also where “log out everywhere”, device lists and absolute session lifetime live.

Asked as — “How do you revoke a JWT?” You do not revoke the access token; you keep it short-lived and revoke the refresh token, which is stateful. Then describe rotation with reuse detection — that is the answer that shows you have built this rather than read about it.

OAuth 2 & OpenID Connect

4 topics

OAuth is a delegation protocol, not a login protocol. Half of all OAuth confusion comes from using it as one; the other half comes from flows that were deprecated years ago and still appear in tutorials.

Roles and the mental model

RoleWho that is
Resource ownerThe human who owns the data
ClientThe application asking for access — not the user
Authorization serverAuthenticates the owner and issues tokens
Resource serverThe API that accepts the access token

The sentence to have ready: OAuth exists so a user can grant an application limited access to their data without handing over their password. Everything else — scopes, consent screens, redirect URIs — follows from that. Clients are confidential (a server that can keep a secret) or public (SPA, mobile app, anything shipped to a user's device — it cannot keep a secret, whatever the tutorial says).

Scopes are coarse delegation labels (orders:read), not your permission model. The authorization server says “this client may act on the user's behalf within these scopes”; your API still decides whether that user may touch that record. Conflating the two is how APIs end up with a valid token reading someone else's data.

Asked as — “Explain OAuth to a junior.” Use the valet key analogy — a key that starts the car but does not open the boot — then immediately name the trap: OAuth answers “what may this app do”, not “who is this user”. That is what OIDC adds.

  1. In OAuth, who is the “client”?

    The four roles are resource owner (the human), client (the app), authorization server (issues tokens) and resource server (the API). The naming trips people up constantly, and getting it wrong makes every subsequent sentence ambiguous.

  2. What are scopes, and what are they not?

    Conflating the two is how an API ends up with a valid token reading someone else's data. The authorization server answers what the client may do; your API still has to answer object-level authorization itself.

  3. Why is a mobile app or SPA a “public” client?

    A confidential client is a server that can genuinely keep a secret. Shipping a client secret inside an app binary or a JavaScript bundle publishes it — which is the reason PKCE became mandatory for these clients first.

Authorization Code with PKCE — the flow to know

Under OAuth 2.1 this is the flow for essentially every client type, public or confidential. PKCE (RFC 7636) stops an attacker who intercepts the authorization code from exchanging it.

// 1. Client generates a high-entropy verifier and its challenge.
$verifier  = rtrim(strtr(base64_encode(random_bytes(32)), '+/', '-_'), '=');
$challenge = rtrim(strtr(base64_encode(hash('sha256', $verifier, true)), '+/', '-_'), '=');

$_SESSION['pkce_verifier'] = $verifier;
$_SESSION['oauth_state']   = $state = bin2hex(random_bytes(16));

// 2. Redirect the user to the authorization server.
$url = 'https://auth.example.com/authorize?' . http_build_query([
    'response_type'         => 'code',
    'client_id'             => $clientId,
    'redirect_uri'          => 'https://app.example.com/callback',   // exact match, pre-registered
    'scope'                 => 'openid profile orders:read',
    'state'                 => $state,                                // CSRF defence
    'code_challenge'        => $challenge,
    'code_challenge_method' => 'S256',                                // never 'plain'
]);
// 3. On the callback: verify state, then exchange the code + verifier for tokens.
if (!hash_equals($_SESSION['oauth_state'] ?? '', $_GET['state'] ?? '')) {
    throw new StateMismatch();          // the request did not start here
}

$tokens = $http->post('https://auth.example.com/token', ['form_params' => [
    'grant_type'    => 'authorization_code',
    'code'          => $_GET['code'],
    'redirect_uri'  => 'https://app.example.com/callback',
    'client_id'     => $clientId,
    'code_verifier' => $_SESSION['pkce_verifier'],   // proves this is the same client
]]);

Why the back-channel exchange matters: the code travels through the browser (visible in history, logs, referrers), the token does not. Why PKCE matters on top: without it, a malicious app registered for the same redirect URI on a mobile OS could steal the code and redeem it; with it, redemption requires the verifier that never left the legitimate client. state and PKCE solve different problems — state is CSRF on the redirect, PKCE is code interception — so you need both.

Asked as — “What does PKCE protect against, and why is it now recommended even for confidential clients?” Authorization code interception. Recommended universally because it costs nothing, and “this client keeps its secret safe” is an assumption that fails often enough to stop relying on.

  1. What does PKCE protect against?

    Code interception, not CSRF. state is the CSRF defence on the redirect, and the two solve different problems — so you need both.

  2. Why does the code travel through the browser but the token not?

GrantStatusUse

OpenID Connect: the identity layer

OIDC is a thin standard layer on top of OAuth 2 that adds what OAuth deliberately left out: a verified statement about who the user is.

Access token

  • Audience: the API
  • Opaque to the client — do not parse it
  • Says what the client may do
  • Sent as Authorization: Bearer

ID token

  • Audience: the client
  • Always a JWT, meant to be read by the client
  • Says who authenticated, when, and how
  • Never send it to an API as a credential

The moving parts worth naming: the openid scope triggers OIDC; nonce binds the ID token to your authorization request (replay defence, distinct from state); the discovery document at /.well-known/openid-configuration gives you endpoints and the JWKS URI; /userinfo returns claims the ID token omitted. Validate an ID token by checking signature, iss, aud (equals your client id), exp and nonce.

Asked as — “Difference between an access token and an ID token?” Different audiences, different purposes. The follow-up trap: “can we just send the ID token to our API?” No — it was issued for the client, so your API has no basis for accepting it, and doing so breaks audience validation, which is the only thing preventing token replay across services.

Enforcement: where the check lives

Authorization needs the resource in hand, so it cannot live in routing middleware. The pattern that keeps it testable is a policy (Laravel) or voter (Symfony) object: one class per resource type, given the subject, the action and the object.

interface Policy
{
    public function supports(string $action, object $subject): bool;
    public function allows(User $user, string $action, object $subject): bool;
}

final class OrderPolicy implements Policy
{
    public function supports(string $action, object $subject): bool
    {
        return $subject instanceof Order
            && in_array($action, ['view', 'update', 'refund'], true);
    }

    public function allows(User $user, string $action, object $subject): bool
    {
        /** @var Order $subject */
        if (!$user->belongsToTenant($subject->tenantId)) {
            return false;                                  // tenant isolation first
        }

        return match ($action) {
            'view'   => $user->can('order.view')   || $subject->customerId === $user->customerId,
            'update' => $user->can('order.update') && $subject->isEditable(),
            'refund' => $user->can('order.refund') && $subject->isPaid(),
        };
    }
}

// One entry point, deny by default — an unknown action has no policy and is refused.
final class Gate
{
    /** @param iterable<Policy> $policies */
    public function __construct(private iterable $policies) {}

    public function authorize(User $user, string $action, object $subject): void
    {
        foreach ($this->policies as $policy) {
            if ($policy->supports($action, $subject)) {
                if (!$policy->allows($user, $action, $subject)) {
                    throw new AccessDenied();      // → 403
                }
                return;
            }
        }
        throw new AccessDenied();                  // no policy = no permission
    }
}

Two properties make this hold up: deny by default (a missing policy refuses rather than allows), and a single entry point so you can log every decision and unit-test the matrix of user × action × resource without booting HTTP. Enforce at the point the resource is loaded — and if a background job, a CLI command and a controller all touch the same operation, put the check in the application service they share, not in the controller.

Asked as — “Where do you put authorization logic?” Not in the controller, not in the entity, not in middleware: in a policy invoked by the application service, with deny-by-default. Then explain how you test it — the answer that separates people who have maintained this from people who have written it once.

    “May this user do this to this object” requires the object. The pattern that keeps it testable is a policy (Laravel) or voter (Symfony): one class per resource type, given the subject, the action and the object.

IDOR, BOLA, and multi-tenant leakage

The most common serious API vulnerability is not exotic: it is an endpoint that authenticates the caller and then loads a record by id without checking ownership. OWASP calls it Broken Object Level Authorization; older material calls it IDOR.

// Vulnerable: authenticated, but not authorized. Changing the id reads someone else's order.
public function show(int $id): Response
{
    $order = $this->orders->find($id);
    return $this->json($order);
}

// Fixed twice over: scope the query to the tenant, then check the policy on the object.
public function show(int $id): Response
{
    $order = $this->orders->findForTenant($id, $this->currentTenantId())
        ?? throw new NotFound();               // 404, not 403 — do not confirm existence

    $this->gate->authorize($this->user(), 'view', $order);

    return $this->json($order);
}

The structural fix is to make the unsafe version hard to write: a repository whose finders require a tenant, a global query scope applied at the ORM level, or separate connections/schemas per tenant. Sequential integer ids make enumeration trivial, so UUIDv7 or a prefixed opaque id (ord_8127) raises the cost — that is defence in depth, not authorization; a guessed id must still be refused.

404 or 403? If confirming that a record exists is itself a leak — and in multi-tenant systems it usually is — return 404. Reserve 403 for resources the caller can legitimately know about but may not act on. Be consistent, because the difference between the two responses is itself an oracle.

Asked as — “A user changes the id in the URL and sees another customer's invoice. What went wrong and how do you prevent a repeat?” Object-level authorization was missing. Prevention is structural — tenant-scoped repositories plus a policy check — followed by a test that asserts cross-tenant access fails for every endpoint.

The one-liners worth having ready

Base64 is not encryption
Everything in a JWT payload is readable by whoever holds the token.
hash_equals
Constant-time string comparison. Use it for tokens, HMACs and CSRF values — === leaks timing.
random_bytes, not rand
rand/mt_rand/uniqid are not cryptographically secure. random_int and random_bytes are.
Store reset tokens hashed
A leaked reset-token table is a leaked account table otherwise. Single use, short expiry.
Bearer means bearer
Whoever holds the token is the user. Nothing binds it to a client unless you add DPoP or mTLS.
Log out = server-side invalidation
Clearing the cookie only affects a cooperative client.
Rotate on privilege change
New session id at login, at password change, at role elevation.
Enumeration
“No such email” on the login and signup forms tells an attacker who has an account. Same message, same timing.
MFA is per-factor-kind
Password plus security question is one factor twice. TOTP secrets are shared secrets — encrypt them at rest.
Passkeys / WebAuthn
Origin-bound public-key credentials: phishing-resistant, no shared secret to steal. The direction of travel.
API keys are passwords
Hash them at rest, show them once, prefix them so they are greppable in leaks, and support rotation with two live keys.
Token introspection
RFC 7662. Opaque token + a call to the authorization server — revocation is instant, at the cost of a round trip.
state vs nonce
state protects the redirect against CSRF; nonce binds the ID token to your request.
Never roll your own crypto
And “never roll your own auth” has a corollary: if you must, at least do not roll your own token format.

  1. Why use hash_equals() rather than === for tokens, HMACs and CSRF values?

    Timing is a side channel. Alongside it: random_int() and random_bytes() are the cryptographically secure generators — rand(), mt_rand() and uniqid() are not — and password reset tokens must be stored hashed, single-use and short-lived, because they are password-equivalent.

  2. What does “bearer” mean, and what follows from it?

    A stolen bearer token is a working credential from anywhere. That is the whole reason for short lifetimes, HttpOnly storage and sender-constraining mechanisms.

  3. What do passkeys / WebAuthn change?

    Nothing secret leaves the authenticator, and the credential only works on the origin it was created for — which is what kills phishing.
