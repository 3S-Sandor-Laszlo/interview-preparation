Az interjúztatók ritkán kérdezik meg, hogy „mi az egységbezárás”. Azt kérdezik, mi történik egy konkrét határesetben — ezért minden téma a mechanizmussal kezdődik, és azzal a peremesettel zárul, amiben a kérdés általában elrejtőzik.

Osztályok, objektumok, konstruktoros promóció

Az osztály a tervrajz; az objektum egy példány saját tulajdonságállapottal. A PHP 8 a konstruktor paramétereit közvetlenül tulajdonságokká lépteti elő — deklaráció, típus, láthatóság és értékadás egy helyen.

class Money
{
    public function __construct(
        public readonly int $amount,        // váltópénzben, pl. fillér
        public readonly string $currency = 'HUF',
    ) {}

    public function add(self $other): static
    {
        if ($other->currency !== $this->currency) {
            throw new InvalidArgumentException('Eltérő pénznem');
        }
        return new static($this->amount + $other->amount, $this->currency);
    }
}

$a = new Money(1_500);
$b = $a->add(new Money(500));   // Money(2000); $a érintetlen marad

class Discount extends Money {}

$d = new Discount(1_000);
$e = $d->add(new Money(500));   // Discount(1500) — a new static() a ténylegesen hívott
                                // osztályt példányosítja; new self() esetén Money jönne vissza

Így kérdezik — „Mit csinál a new static(), amit a new self() nem?” A self arra az osztályra oldódik fel, ahol a kód meg van írva; a static futásidőben a ténylegesen hívott osztályra (késői statikus kötés).

Mindegyiknél egy helyes válasz van. A választásaidat ez a böngésző megjegyzi, így legközelebb is itt lesznek.

  1. Mit deklarál valójában a public readonly int $amount a konstruktor szignatúrájában?

    A promóció négy dolgot csinál egyszerre: deklarálja a tulajdonságot, típust és láthatóságot ad neki, és hozzárendeli a bejövő argumentumot. Pontosan ez a lényege — nincs kettőzött deklaráció, és nincs $this->amount = $amount; sor.

  2. A Money::add() belsejében mit csinál a new static(...), amit a new self(...) nem?

    Késői statikus kötés. A self ott oldódik fel, ahol a kód meg van írva; a static azon az osztályon, amin a metódust hívták. Így a Discount által örökölt Money::add() a new static()-kal Discount-ot ad vissza, a new self()-fel viszont Money-t.

  3. Melyik állítás igaz a konstruktoros promócióra?

    A promóció kizárólag konstruktoros lehetőség. Alapértelmezett érték megengedett (string $currency = 'HUF'), a láthatósági kulcsszó pedig épp az, ami a promóciót kiváltja; ha a tulajdonságot a törzsben újra felveszed, „Cannot redeclare property” hibát kapsz.

  4. Mi a viszony $a és $b között a $a = new Money(1500); $b = $a; után?

    Az objektum hivatkozás, nem érték. Az értékadás a hivatkozást másolja, tehát mindkét név egyetlen objektumra mutat — a tömbökkel ellentétben, amik copy-on-write értékek. Valódi másolathoz clone kell, és az sekély, hacsak a __clone() mást nem mond.

  5. A fenti Money osztálynál mi történik a példányosítás után az $a->amount = 2000; sornál?

    „Cannot modify readonly property Money::$amount” — futásidejű Error. A readonly egyszer írható a deklaráló hatókörből, nem pusztán „kívülről privát” — pontosan ezért ad vissza az add() új példányt ahelyett, hogy ezt módosítaná.

Egységbezárás és láthatóság

Három módosító: a public mindenhonnan, a protected az osztályból és leszármazottaiból, a private csak a deklaráló osztályból érhető el. A láthatóság a PHP-ban osztályszintű, nem objektumszintű: az egyik példány elolvashatja a másik privát tagjait, amíg a kód ugyanabban az osztályban van.

class Account
{
    public function __construct(private int $balance) {}

    public function richerThan(Account $other): bool
    {
        return $this->balance > $other->balance;  // megengedett: azonos osztály
    }
}

A PHP 8.4 bevezeti az aszimmetrikus láthatóságot — kívülről olvasható, csak belülről írható:

class Order
{
    public private(set) string $status = 'draft';   // PHP 8.4+

    public function pay(): void { $this->status = 'paid'; }
}

Így kérdezik — „Mi a különbség a private és a protected között?” Aztán jön a folytatás: „Meghívhatja a szülő a gyermek privát metódusát?” Nem — és ha a gyermek újradeklarálja, a PHP két külön metódust tart nyilván.

Mindegyiknél egy helyes válasz van. A választásaidat ez a böngésző megjegyzi, így legközelebb is itt lesznek.

  1. A PHP-ban a láthatóság osztályszintű, nem objektumszintű. Mit tesz ez lehetővé?

    Az ellenőrzés kérdése az, hogy „a deklaráló osztályban vagyok-e?”, nem az, hogy „ezen az objektumon vagyok-e”. Ezért olvashatja az Account::richerThan(Account $other) az $other->balance-t. A leszármazott továbbra sem látja a szülő privát tagjait — arra való a protected.

  2. Mit deklarál a public private(set) string $status a PHP 8.4-ben?

    Aszimmetrikus láthatóság. Az első módosító az olvasási, a private(set) az írási láthatóság. Kiváltja a csak-getter boilerplate-et: a hívó közvetlenül olvassa az $order->status-t, de csak a pay() írhatja.

  3. Meghívhatja-e egy szülőosztály a leszármazottjában deklarált private metódust?

    A privát metódusok nem vesznek részt a polimorfizmusban. A szülő kódja mindig a szülő privát metódusát hívja, a gyermeké a gyermekét — egymást nem definiálják felül. Ezért figyelmeztet a PHP 8 a final private function-re: a privát eleve nem felüldefiniálható.

Öröklődés

Csak egyszeres öröklődés van — egyetlen extends. A parent:: a felüldefiniált implementációt éri el. A final megakadályozza a további származtatást vagy felüldefiniálást.

abstract class Repository
{
    public function __construct(protected PDO $pdo) {}

    protected function fetchOne(string $sql, array $params): ?array
    {
        $stmt = $this->pdo->prepare($sql);
        $stmt->execute($params);
        return $stmt->fetch(PDO::FETCH_ASSOC) ?: null;
    }
}

final class UserRepository extends Repository
{
    public function __construct(PDO $pdo, private Clock $clock)
    {
        parent::__construct($pdo);
    }

    public function find(int $id): ?array
    {
        return $this->fetchOne('SELECT * FROM users WHERE id = ?', [$id]);
    }
}
Kompozíció az öröklődés helyett. Erre számíts folytatásként. Az öröklődés örökre a szülő implementációjához köti a leszármazottakat; a kompozíció (egy együttműködő objektum injektálása) futásidőben cserélhető viselkedést ad, és laposan tartja a hierarchiát. Öröklődést akkor válassz, ha valóban „is-a” viszonyról van szó, egyébként interfészt és kompozíciót.

Mindegyiknél egy helyes válasz van. A választásaidat ez a böngésző megjegyzi, így legközelebb is itt lesznek.

  1. Miért kell a UserRepository példájában a parent::__construct($pdo)?

    Ha a leszármazott deklarál __construct()-ot, az teljesen kiváltja a szülőét. A Javával ellentétben a PHP nem szúr be implicit super() hívást — ha a szülőnek van beállítania valója, neked kell meghívnod, különben a $pdo inicializálatlan marad.

  2. Mit akadályoz meg pontosan a final egy osztályon?

    A final class magát az extends-et tiltja; a final function egyetlen metódus felüldefiniálását. Egy final osztály tetszőleges számú interfészt megvalósíthat — sőt pontosan ez az ajánlott alak: final osztályok interfészek mögött.

  3. A szokásos rákérdezés: „kompozíció öröklődés helyett”. Mi az érv egy mondatban?

    A költség a csatolás, nem a teljesítmény. A leszármazott a szülő minden jövőbeli változását örökli, akarja vagy sem. Öröklődést valódi „is-a” viszonyra használj; egyébként függj interfésztől, és injektáld az implementációt.

Polimorfizmus

Egy hívási hely, sokféle implementáció, a futásidejű típus dönt. A PHP nem támogatja a szignatúra szerinti metódus-túlterhelést — a __call() és az alapértelmezett vagy változó számú paraméter az, ami helyette van.

interface Exporter
{
    public function extension(): string;
    public function export(array $rows): string;
}

final class CsvExporter implements Exporter
{
    public function extension(): string { return 'csv'; }

    public function export(array $rows): string
    {
        $out = fopen('php://temp', 'r+');
        foreach ($rows as $row) { fputcsv($out, $row); }
        rewind($out);
        return stream_get_contents($out);
    }
}

final class JsonExporter implements Exporter
{
    public function extension(): string { return 'json'; }
    public function export(array $rows): string
    {
        return json_encode($rows, JSON_THROW_ON_ERROR | JSON_PRETTY_PRINT);
    }
}

function save(Exporter $e, array $rows, string $name): void
{
    file_put_contents("{$name}.{$e->extension()}", $e->export($rows));
}

Így kérdezik — „Támogat a PHP metódus-túlterhelést?” Java értelemben nem. Amit a kézikönyv „overloading”-nak hív, az a __call()/__callStatic(), és az mást jelent: nem elérhető hívások elkapását.

  1. Támogatja a PHP a Java értelmében vett metódus-túlterhelést — azonos név, eltérő szignatúrák?

    Egy név, egy metódus. Amit a PHP kézikönyve „overloading”-nak hív, az a __call()/__callStatic() — a nem elérhető metódushívások elkapása —, ami megtévesztően hasonló néven egészen más dolog.

  2. A save(Exporter $e, array $rows, string $name) hívásban mi dönti el, melyik export() törzse fut?

    Dinamikus diszpécselés. A típusjelölés csak azt korlátozza, mit adhatsz át; a motor hívás közben, a valódi osztályon keresi meg a metódust. Ez a teljes mechanizmus, és ezért nem kell a save()-hez hozzányúlni egy harmadik formátum megjelenésekor.

  3. Mi a gyakorlati haszna annak, hogy a save() az Exporter-től függ, nem a két konkrét osztálytól?

    Bővítésre nyitott, módosításra zárt. Az alternatíva — egy match a formátum sztringjére a save()-en belül — minden új formátumnál egy ággal nő, és minden bővítés kockáztatja a meglévőket.

Absztrakt osztály vs interfész

Az interfész állapot nélküli szerződés; az absztrakt osztály egy félig megépített osztály, amiből származtatsz. A PHP 8.4 óta az interfészek konstansokat is deklarálhatnak (8.3 óta típusosat is), de értékkel bíró tulajdonságot soha.

Absztrakt osztály

  • Tartalmazhat tulajdonságot és állapotot
  • Definiálhat konstruktort
  • Megvalósított és absztrakt metódusok vegyesen
  • Láthatóság: public / protected / private
  • Egy darab osztályonként

Interfész

  • Nincs tulajdonság, nincs állapot
  • Nincs konstruktortörzs
  • Csak metódusszignatúrák (és konstansok)
  • Minden tag implicit módon public
  • Több is osztályonként; interfész több interfészt is kiterjeszthet
interface Notifier
{
    const int MAX_RETRIES = 3;              // típusos konstans, PHP 8.3+
    public function send(string $to, string $body): void;
}

abstract class QueuedNotifier implements Notifier
{
    public function __construct(protected Queue $queue) {}

    public function send(string $to, string $body): void
    {
        $this->queue->push($this->payload($to, $body));
    }

    abstract protected function payload(string $to, string $body): array;
}

Így kérdezik — „Mikor melyiket választanád?” Interfészt akkor, ha olyan képességről van szó, amit egymással nem rokon osztályok is felvehetnek; absztrakt osztályt akkor, ha a leszármazottak valóban közös implementáción osztoznak. A gyakorlatban: az interfészre programozz, a kódot pedig absztrakt ősosztályban vagy trait-ben oszd meg.

Mindegyiknél egy helyes válasz van. A választásaidat ez a böngésző megjegyzi, így legközelebb is itt lesznek.

  1. Mit tud az absztrakt osztály, amit az interfész nem?

    Az állapot és a konstruálás a választóvonal. Az interfész tiszta szerződés: szignatúrák és konstansok, tulajdonság nélkül, konstruktortörzs nélkül, minden tagja implicit publikus. Az absztrakt osztály félkész osztály — ezért kapsz belőle csak egyet.

  2. Egy osztálynak közös implementációra és több, egymástól független képesség-szerződésre is szüksége van. Mit enged a PHP?

    Egyszeres öröklődés, több interfész. A QueuedNotifier az egyetlen öröklődési helyét a közös sorkezelő kódra költi, miközben a Notifier szerződés marad, amit bármely osztály felvállalhat. Maguk az interfészek több interfészt is kiterjeszthetnek.

  3. Mi a const int MAX_RETRIES = 3; egy interfészen belül?

    Az interfészkonstans régóta létezik; a típus az, ami PHP 8.3. A PHP 8.1 óta a megvalósító osztály felül is definiálhatja az interfész konstansát — korábban ez tilos volt.

Trait-ek

Horizontális újrafelhasználás — fordítási szintű másolás-beillesztés: metódusok, tulajdonságok és absztrakt követelmények kerülnek be az osztályba. Nem típus: trait-re nem lehet típusmegkötést írni.

trait Timestamps
{
    private ?DateTimeImmutable $updatedAt = null;

    public function touch(): void
    {
        $this->updatedAt = $this->clock()->now();
    }

    abstract protected function clock(): Clock;   // a trait együttműködőt követel
}

trait Loggable
{
    public function touch(): void { /* … */ }
}

final class Article
{
    use Timestamps, Loggable {
        Timestamps::touch insteadof Loggable;   // ütközés feloldása
        Loggable::touch as logTouch;            // a másik új néven megmarad
    }

    public function __construct(private Clock $clock) {}
    protected function clock(): Clock { return $this->clock; }
}

Precedencia, a legerősebbtől: az osztály saját metódusa → a trait metódusa → az örökölt metódus. A trait tartalmazhat statikus és absztrakt tagokat; két trait azonos nevű tulajdonsága csak akkor engedélyezett, ha a definíciók megegyeznek.

Így kérdezik — „Trait vs interfész vs absztrakt osztály?” Interfész = szerződés kód nélkül. Trait = kód szerződés nélkül. Absztrakt osztály = mindkettő, de elhasználja az egyetlen öröklődési helyet.

Mindegyiknél egy helyes válasz van. A választásaidat ez a böngésző megjegyzi, így legközelebb is itt lesznek.

  1. Mit csinál nyelvi szinten a use Timestamps;?

    A trait fordító által segített másolás-beillesztés. Semmi nem marad belőle típusként — az $x instanceof Timestamps végzetes hiba, és típusjelölésre sem használható. Ha típus kell, párosítsd a traitet egy interfésszel.

  2. Egy osztály két traitet használ, és mindkettő definiálja a touch()-ot. Mi történik?

    Az ütközés tervezetten fordítási idejű végzetes hiba. A Timestamps::touch insteadof Loggable; kiválasztja a győztest, a Loggable::touch as logTouch; pedig új néven megtartja a vesztest.

  3. Az osztály, az általa használt trait és a szülője is definiálja ugyanazt a metódust. Melyik fut?

    Saját metódus → trait metódus → örökölt metódus. Ennek hasznos következménye: a trait felüldefiniálhat egy örökölt implementációt a szülő érintése nélkül, de a végső szó mindig az osztályé.

Statikus tagok és késői statikus kötés

A self, static és parent a három hatókör-kulcsszó. A self:: fordítási időben kötődik a definiáló osztályhoz; a static:: futásidőben ahhoz, amit ténylegesen meghívtak — ez a késői statikus kötés (LSB).

abstract class Model
{
    public static function create(array $attrs): static
    {
        return new static($attrs);        // LSB: a konkrét leszármazottat adja vissza
    }

    public static function table(): string
    {
        return self::guess();             // mindig Model::guess(), leszármazottban is
    }

    protected static function guess(): string { return 'models'; }
}

final class User extends Model
{
    public function __construct(private array $attrs) {}
    protected static function guess(): string { return 'users'; }
}

User::create(['name' => 'Laslow']);  // User példány a `new static` miatt
User::table();                       // 'models' — a self:: figyelmen kívül hagyta a felüldefiniálást

Cseréld a self::guess()-t static::guess()-re, és a második hívás már 'users'-t ad vissza. Ez az egysoros különbség maga a kérdés.

A statikus tagok globális állapotot jelentenek. Megkerülik a DI-t, tesztben nehezen helyettesíthetők, és láthatatlanná teszik a függőségeket a szignatúrában. Tiszta függvényekhez és névvel ellátott konstruktorokhoz elfogadható; bármihez, ami I/O-t érint, code smell.

Mindegyiknél egy helyes válasz van. A választásaidat ez a böngésző megjegyzi, így legközelebb is itt lesznek.

  1. A Model::table() a self::guess()-t adja vissza. Miért ad a User::table() 'models'-t?

    A self lexikális, a static dinamikus. Írj a törzsbe static::guess()-t, és ugyanaz a hívás 'users'-t ad. Ez az egy kulcsszónyi különbség a késői statikus kötés, és ez a statikus tagokkal kapcsolatos leggyakoribb kérdés.

  2. Mit ér a static visszatérési típusként, mint a public static function create(array $attrs): static esetében?

    A static visszatérési típusként a késői statikus kötés a típusrendszerben. Nélküle minden ősosztályból örökölt névvel ellátott konstruktor az ősosztályt adná vissza típus szerint, és a hívónak felesleges szűkítő ellenőrzést kellene írnia.

  3. Mi a szokásos kifogás a statikus metódusok ellen?

    A függőség eltűnik a szignatúrából. Egy osztály, ami a Mailer::send()-et hívja, függőségmentesnek látszik, pedig nem az, és a teszt nem tudja kicserélni. Tiszta függvényekhez és névvel ellátott konstruktorokhoz rendben van; bármi, ami I/O-t érint, szaghiba.

final class Config implements Stringable

    {

    }

    {
        return isset($this->items[$key]);
    }

    {
        if (str_starts_with($name, 'get')) {

Klónozás: alapból sekély

A clone a tulajdonságok értékeit másolja. Az objektum típusú tulajdonságok hivatkozás szerint másolódnak, így a másolat osztozik rajtuk. A __clone() az új objektumon fut le, és itt kell mélymásolni.

final class Invoice
{
    private DateTimeImmutable $issuedAt;
    private ArrayObject $lines;

    public function __clone(): void
    {
        $this->lines = clone $this->lines;   // a módosítható gyűjtemény mélymásolása
        // az $issuedAt immutable — biztonságos és olcsóbb megosztva hagyni
    }
}

$copy = clone $invoice;

A PHP 8.3 óta a __clone() újra tudja inicializálni a readonly tulajdonságokat, ami végre működővé teszi a „módosítsd a másolatot” stílusú with*() metódusokat readonly értékobjektumokon.

Enumok

A PHP 8.1 enumjai objektumok: szingleton esetek, megvalósíthatnak interfészt, lehetnek konstansaik és metódusaik, de példányállapotuk soha. A tiszta enumnak nincs skalár értéke; a backed enum int-re vagy string-re képződik le.

enum OrderStatus: string implements JsonSerializable
{
    case Draft     = 'draft';
    case Paid      = 'paid';
    case Shipped   = 'shipped';
    case Cancelled = 'cancelled';

    public function isFinal(): bool
    {
        return match ($this) {
            self::Shipped, self::Cancelled => true,
            default => false,
        };
    }

    public function label(): string
    {
        return ucfirst($this->value);
    }

    public function jsonSerialize(): string { return $this->value; }
}

OrderStatus::from('paid');       // OrderStatus::Paid — ismeretlenre ValueError
OrderStatus::tryFrom('nope');    // null
OrderStatus::cases();            // az összes eset tömbben
OrderStatus::Paid->name;         // 'Paid'   (csak olvasható)
OrderStatus::Paid->value;        // 'paid'

Így kérdezik — „Enum vagy osztálykonstans?” Az enum típusbiztos (egy OrderStatus típusú paraméter nem kaphat véletlen stringet), kimerítően illeszthető match-csel, és viselkedést is hordoz. A konstans csak egy érték.

A típusrendszer, variancia, never

Nullozható (?T), unió (A|B), metszet (A&B, PHP 8.1), plusz a speciális típusok: void, never, static, self, mixed, iterable. A PHP 8.2 hozza a DNF-típusokat: (A&B)|null.

declare(strict_types=1);

function shutdown(string $reason): never   // sosem tér vissza: dob vagy kilép
{
    throw new RuntimeException($reason);
}

function persist(Countable&Traversable $rows): void { /* … */ }

Kovariancia — a leszármazott szűkítheti a visszatérési típust. Kontravariancia — a leszármazott bővítheti a paramétertípust. Mindkettő megőrzi a Liskov-helyettesíthetőséget.

class AnimalShelter          { public function adopt(): Animal { /* … */ } }
class DogShelter extends AnimalShelter
{
    public function adopt(): Dog { /* … */ }   // kovariáns visszatérés: szűkebb, rendben
}

class Handler       { public function handle(Dog $a): void {} }
class LooseHandler extends Handler
{
    public function handle(Animal $a): void {}  // kontravariáns paraméter: bővebb, rendben
}
A declare(strict_types=1) fájlonként érvényes, és azokra a hívásokra vonatkozik, amelyeket abból a fájlból indítanak — nem a hívott fájlra. Nélküle a PHP konvertál ("5" → 5); vele a rossz skalártípus TypeError-t dob. A következő téma részletesen tárgyalja a szabályokat.

    Kovariáns visszatérés, kontravariáns paraméter. A visszatérés szűkítése minden meglévő hívót kielégít; a paraméter bővítése minden meglévő hívási helyet érvényben hagy. Mindkét irány megőrzi a Liskov-helyettesíthetőséget — a fordítottja végzetes hiba.

    A never az alsó típus, erősebb a void-nál: a void azt jelenti, „nem ad vissza semmit”, a never azt, „a vezérlés nem jön vissza”. A never hívása után minden kód bizonyíthatóan halott, amit az analizátorok és a motor is kihasznál.

    Diszjunktív normálforma. A PHP 8.1 hozta a metszeteket (A&B), de azok 8.2-ig nem voltak uniókkal kombinálhatók, és akkor is csak ebben az alakban: zárójelezett metszetek |-lal összefűzve.

Strict mód — és miben más, mint a Java

A PHP-nak két típusmódja van. A kényszerítő (coercive) az alapértelmezett: az a skalár, amiből ésszerűen előállítható a deklarált típus, átalakul. A strict fájlonként bekapcsolható, és az átalakítás helyett visszautasít.

declare(strict_types=1);   // a fájl LEGELSŐ utasításának kell lennie

Három szabály dönt el mindent, és az interjúztatók mindhármat tesztelik:

  • Fájlonként érvényes, és a hívó fájl dönt. Nem az, ahol a függvényt deklarálták. Egy strict fájl akkor is strict a hívás helyén, ha egy laza könyvtárat hív; egy kényszerítő fájl akkor is konvertál, ha egy strict könyvtár függvényét hívja.
  • Csak a skalárokra hat — int, float, string, bool. Az osztálytípusokat, az array-t, a callable-t és az iterable-t soha nem konvertálta a PHP, így ezeken a strict mód nem változtat.
  • Egyetlen bővítés marad: az int → float strict módban is elfogadott. Semmi más.
function vatOf(int $netHuf): int { return (int) round($netHuf * 0.27); }

// Kényszerítő mód (declare nélkül)
vatOf('1500');    // 1500 — numerikus string átalakítva
vatOf(1500.0);    // 1500 — tört rész nélküli float átalakítva
vatOf(1500.5);    // 1500 + deprecation (implicit veszteséges átalakítás, PHP 8.1+)
vatOf('abc');     // TypeError itt is — a PHP 8 már nem fogad el nem numerikus stringet
vatOf(true);      // 1

// Strict mód
vatOf('1500');    // TypeError: int típusú kell legyen, string érkezett
vatOf(1500.0);    // TypeError — nincs float-ból int, még veszteségmentesen sem
vatOf(1500);      // rendben

function avg(float $x): float { return $x; }
avg(3);           // strict módban is rendben: int -> float az egyetlen megengedett bővítés

// A beépített függvényekre is vonatkozik
strlen(42);       // strict: TypeError.  kényszerítő: 2

A visszatérési értékek annak a fájlnak a módját követik, ahol a függvényt deklarálták, hiszen a return ott van. Egy strict fájlban deklarált függvény tehát nem adhat vissza csendben "5"-öt int szignatúrából, bárki is hívja.

Immutabilitás: readonly és értékobjektumok

A readonly tulajdonságok (8.1) egyszer írhatók, a deklaráló osztály hatóköréből. A readonly osztályok (8.2) ezt implicit módon minden tulajdonságra kiterjesztik.

final readonly class Coordinates      // PHP 8.2
{
    public function __construct(
        public float $lat,
        public float $lon,
    ) {}

    public function withLat(float $lat): self
    {
        return new self($lat, $this->lon);   // új példány, sosem módosítás
    }
}

$c = new Coordinates(47.4979, 19.0402);
$c->lat = 0;   // Error: readonly tulajdonság nem módosítható

Így kérdezik — „A readonly immutable-lé teszi az objektumot?” Csak sekélyen. Egy readonly tulajdonságban tárolt módosítható objektum továbbra is módosítható; csak a hivatkozás van befagyasztva.

Névterek és feloldás

A névterek fordítási idejű névprefixek, \-sel elválasztva. A kezdő backslash teljesen minősített nevet jelent; nélküle a PHP az aktuális névtérhez képest old fel, majd — csak függvényeknél és konstansoknál — visszaesik a globális névtérre.

namespace App\Billing;

use App\Support\Clock;                 // osztály importálása
use App\Support\{Money, Currency};     // csoportos use
use function App\Support\format_huf;   // függvény importálása
use const App\Support\VAT_RATE;        // konstans importálása
use App\Support\Clock as SystemClock;  // alias

$now = new \DateTimeImmutable();       // \ kell: globális osztály névtéren belül
$len = strlen('x');                    // \ nem kell: a függvények visszaesnek globálisra
Ellenőrizd magad — 3 kérdés a témából

Mindegyiknél egy helyes válasz van. A választásaidat ez a böngésző megjegyzi, így legközelebb is itt lesznek.

  1. A namespace App\Billing; alatt miért hibázik a new DateTimeImmutable(), míg a strlen('x') működik?

    A visszaesés csak függvényekre és konstansokra vonatkozik. Az osztályhoz tehát \DateTimeImmutable vagy use kell, a strlen() viszont a névtérbeli keresés kudarca után globálisan megtalálható. Ez az aszimmetria maga a kérdés.

  2. Mit csinál a use App\Support\Clock as SystemClock;?

    A use tisztán névkezelő utasítás. Fájlszintű, fordítási időben oldódik fel, és semmilyen autoloadot nem vált ki — az autoloader csak akkor fut, amikor a névre ténylegesen hivatkozol.

A kivételhierarchia

Minden elkapható dolog a Throwable-t valósítja meg. Alatta két ág van: az Error (motorszintű: TypeError, ValueError, ArgumentCountError, DivisionByZeroError) és az Exception (alkalmazásszintű, az SPL RuntimeException és LogicException gyökerekkel).

{
    public function __construct(
        public readonly string $reference,
        ?Throwable $previous = null,
    ) {
        parent::__construct("A(z) {$reference} fizetés elutasítva", 0, $previous);

} finally {
    $gateway->disconnect();       // akkor is lefut, ha kivétel szökött meg

Generátorok

A yield-et tartalmazó függvény Generator-t ad vissza (ami Iterator), és lustán számol — konstans memóriahasználat korlátlan adatfolyamon.

function readRows(string $path): Generator
{
    $fh = fopen($path, 'r');
    try {
        while (($row = fgetcsv($fh)) !== false) {
            yield $row;                 // egyszerre egy sor van a memóriában
        }
    } finally {
        fclose($fh);
    }
    return 'kész';                      // a $gen->getReturn() adja vissza
}

foreach (readRows('export.csv') as $row) { /* … */ }

A yield from egy másik iterálhatóra delegál; a $gen->send($v) értéket ad vissza a generátorba, ezzel korutinokat is lehetővé tesz.

Szemétgyűjtés

A PHP két lépcsőben szabadít fel memóriát. A munka nagy részét a referenciaszámlálás végzi: minden érték hordoz egy refcount-ot, és amint az nullára csökken, az érték azonnal megsemmisül — ezért determinisztikus a __destruct() a PHP-ban, szemben a Javával vagy a C#-pal. A ciklusgyűjtő csak azt takarítja el, amire a referenciaszámlálás képtelen: az egymásra hivatkozó, így soha nullára nem jutó objektumcsoportokat.

$a = new Article();   // refcount 1
$b = $a;              // refcount 2 — az objektumok handle szerint osztódnak meg, nem másolódnak
unset($a);            // refcount 1 — még semmi nem szabadul fel
unset($b);            // refcount 0 — most semmisül meg, itt fut a __destruct()

Miért kell gyűjtő a ciklusokhoz

Két egymásra mutató objektum életben tartja egymást akkor is, ha kívülről már senki nem hivatkozik rájuk. Ez a klasszikus szülő ↔ gyermek szivárgás:

final class Node
{
    public ?Node $parent = null;
    /** @var list<Node> */
    public array $children = [];

    public function add(Node $child): void
    {
        $child->parent = $this;      // gyermek -> szülő
        $this->children[] = $child;  // szülő -> gyermek   ← a ciklus
    }

    public function __destruct() { echo "felszabadult\n"; }
}

function build(): void
{
    $root = new Node();
    $root->add(new Node());
}   // a $root kikerül a hatókörből, de egyik refcount sem lesz 0 — semmi nem íródik ki

build();
gc_collect_cycles();   // MOST szabadul fel mindkettő: "felszabadult felszabadult"

Hogyan működik a gyűjtő

A PHP szinkron mark-and-sweep algoritmust futtat egy gyökérpufferen (a Bacon–Rajan ciklusgyűjtő eljárás), nem pedig a teljes heapet bejáró tracing GC-t:

  • Ha egy refcount csökken, de nem éri el a nullát, az objektum lehetséges gyökérré válik, és bekerül a gyökérpufferbe.
  • Amikor a puffer megtelik — alapból 10 000 gyökérnél, a zend.gc_root_buffer_max_entries hangolható —, lefut egy gyűjtés.
  • A gyűjtő szimulálja minden gyökér hivatkozásainak eltávolítását. Amié a szimulációban nullára esik, az csak a cikluson belülről volt elérhető, tehát eltakarítható.
  • A többiek visszakapják a számlálójukat. A gyűjtés stop-the-world szünet, ami a puffer méretével arányos, nem a teljes heapével.
gc_collect_cycles();   // kényszerített futtatás; az összegyűjtött ciklusok számát adja
gc_enabled();          // be van kapcsolva a ciklusgyűjtő?
gc_disable();          // ki — a referenciaszámlálás a ciklusmentes részt továbbra is felszabadítja
gc_enable();
gc_status();           // ['runs' => …, 'collected' => …, 'threshold' => …, 'roots' => …]

memory_get_usage(true);       // az operációs rendszertől lefoglalt bájtok
memory_get_peak_usage(true);  // csúcsérték — ezt hasonlítja a memory_limit-hez

A zend.enable_gc (alapból be) szabályozza, a folyamatot pedig a memory_limit keretezi. A PHP 8.3 kapott egy külön GC-vödröt az objektumoknak, és jelentősen olcsóbbá tette a gyűjtőt, de a modell nem változott.

Ciklusok elkerülése: WeakReference és WeakMap

A jobb megoldás nem létrehozni a ciklust. A gyenge hivatkozás nem növeli a refcountot, így a hivatkozott objektum felszabadulhat.

final class Node
{
    private ?WeakReference $parent = null;    // PHP 7.4

    public function setParent(Node $p): void { $this->parent = WeakReference::create($p); }
    public function parent(): ?Node { return $this->parent?->get(); }   // null, ha már elfogyott
}

// WeakMap (PHP 8.0): a kulcsok objektumok, a bejegyzés eltűnik a kulccsal együtt.
// Ez a bevett mód objektumonkénti adat gyorsítótárazására anélkül, hogy memóriában tartanád.
final class HydrationCache
{
    private WeakMap $meta;

    public function __construct() { $this->meta = new WeakMap(); }

    public function remember(object $entity, array $data): void
    {
        $this->meta[$entity] = $data;     // nincs szivárgás: az $entity elengedésével ez is megy
    }
}
Hol fáj ez igazán. A klasszikus kérésenkénti folyamatmodellben (mod_php, PHP-FPM) az egész aréna lebomlik a kérés végén, így a szivárgás ritkán jelentkezik. Hosszan futó folyamatokban — queue worker, Swoole, RoadRunner, FrankenPHP, adatfolyamot fogyasztó démon — ugyanaz a ciklus addig halmozódik, míg a memory_limit le nem lövi a workert. Ezért indítja újra a Laravel Horizon és a Symfony Messenger a workereket N feladat után.

Így kérdezik — „Hogyan kezeli a PHP a memóriát?” A teljes válasz három ütemben: a referenciaszámlálás mohón és determinisztikusan szabadít fel; a mark-and-sweep gyűjtő kizárólag a hivatkozási ciklusokat kezeli; a WeakReference/WeakMap pedig lehetővé teszi, hogy eleve ne hozz létre ciklust. Ha megemlíted a copy-on-write-ot is (a tömbök és stringek osztoznak a tárolón, amíg valaki nem ír beléjük — ezért olcsó egy nagy tömb átadása), az általában lezárja a kérdést.

Active Record vs Data Mapper

Két válasz arra, hogyan jut el egy objektum az adatbázisig; mindkettőt Fowler nevezte el a Patterns of Enterprise Application Architecture-ben. Active Record: az objektum maga a sor, és tudja, hogyan mentse el magát. Data Mapper: az objektum semmit sem tud a tárolásról, egy külön mapper mozgatja az adatot közte és az adatbázis között.

Active Record

  • Egy osztály = egy tábla; a példány egy sor
  • $user->save(), User::find(1)
  • Eloquent (Laravel), Yii, CakePHP, Rails
  • Gyorsan fejleszthető, CRUD-ra jól olvasható
  • A modell domain- és perzisztencia-felelősséget is visel — tervezetten SRP-sértés
  • A unit tesztekhez adatbázis vagy sok mockolás kell
  • A domain alakját a séma húzza magához

Data Mapper

  • Az entitás egyszerű objektum; az I/O-t a mapper végzi
  • $em->persist($user); $em->flush();
  • Doctrine (Symfony), Hibernate
  • Az entitások pusztán new-val is tesztelhetők
  • A Unit of Work kötegeli az írásokat; az Identity Map soronként egy példányt garantál
  • A séma és a domain külön fejlődhet
  • Több ceremónia, proxyk, meredekebb tanulási görbe
// Active Record — az objektum menti magát
$user = User::find(1);
$user->email = 'laslow@example.com';
$user->save();

// Data Mapper — az entitás nem tud semmiről; a manager menti
$user = $em->find(User::class, 1);
$user->changeEmail('laslow@example.com');   // tiszta domain-viselkedés
$em->flush();                                // egy tranzakció, a Unit of Work alapján

Az „írj egy minimális Active Recordot” gyakori táblás feladat. Az alak, amit látni akarnak, a késői statikus kötést, a mágikus elérőket és a piszkos mezők követését ötvözi:

abstract class ActiveRecord
{
    protected static PDO $pdo;
    protected static string $table;

    private array $attributes = [];
    private array $dirty = [];
    private bool $exists = false;

    public function __get(string $k): mixed  { return $this->attributes[$k] ?? null; }

    public function __set(string $k, mixed $v): void
    {
        if (($this->attributes[$k] ?? null) !== $v) {
            $this->dirty[$k] = $v;          // csak azt jegyezzük, ami tényleg változott
        }
        $this->attributes[$k] = $v;
    }

    public static function find(int $id): ?static
    {
        $stmt = static::$pdo->prepare('SELECT * FROM ' . static::$table . ' WHERE id = ?');
        $stmt->execute([$id]);
        $row = $stmt->fetch(PDO::FETCH_ASSOC);

        if ($row === false) {
            return null;
        }

        $model = new static();              // LSB: a konkrét leszármazott
        $model->attributes = $row;
        $model->exists = true;
        return $model;
    }

    public function save(): void
    {
        if ($this->dirty === []) {
            return;                         // nincs mit írni
        }

        $this->exists ? $this->update() : $this->insert();
        $this->dirty = [];
    }

    private function update(): void
    {
        $set = implode(', ', array_map(fn ($c) => "$c = ?", array_keys($this->dirty)));
        $sql = 'UPDATE ' . static::$table . " SET $set WHERE id = ?";

        static::$pdo->prepare($sql)
            ->execute([...array_values($this->dirty), $this->attributes['id']]);
    }

    private function insert(): void { /* … */ }
}

A megoldás az eager loading (User::with('orders') Eloquentben, JOIN FETCH DQL Doctrine-ban). Ezt folyamatosan kérdezik, és mindkét mintában ugyanaz a csapda — a Data Mapper csak láthatóbbá teszi a lusta betöltő proxyt.

Így kérdezik — „Melyiket választanád?” Active Recordot CRUD-alakú alkalmazásokhoz és kis csapatoknál, ahol a szállítási sebesség számít. Data Mappert akkor, ha a domainben valódi viselkedés és invariánsok vannak, és a séma nem tükrözi őket — vagy ha az üzleti logikát adatbázis nélkül akarod tesztelni. A senior válasz megnevezi az árat is, amit így vagy úgy megfizetsz, ahelyett hogy az egyiket univerzálisan jobbnak kiáltaná ki.

Adatszerkezetek: PHP a Pythonhoz mérve

A fő különbség, hogy a Python szétválasztja a list-et és a dict-et; a PHP-ban egyetlen array játssza mindkét szerepet. A második különbség a gyakorlatban jobban fáj: a PHP-tömbök értéktípusok copy-on-write-tal; a Python listái és szótárai referenciák. Egy PHP-tömb átadásakor logikai másolat keletkezik, így a kettő sosem alias. Egy Python-lista átadásakor nem.

PSR-1 (alap) — a fájlok csak <?php vagy <?= nyitótagot használnak, UTF-8 BOM nélkül; egy fájl vagy deklarál szimbólumokat, vagy mellékhatása van, de sosem mindkettő; az osztálynevek StudlyCaps, a konstansok UPPER_SNAKE, a metódusok camelCase alakúak.

PSR-12 (kiterjesztett) — 4 szóköz (soha tabulátor), 120 karakteres puha sorhossz, egy üres sor a namespace-blokk és a use-blokk után, kapcsos zárójel külön sorban osztálynál és metódusnál, de azonos sorban vezérlési szerkezeteknél, kötelező láthatóság minden tulajdonságon, metóduson és konstanson, rögzített declare(strict_types=1) pozíció.

PER Coding Style — a FIG újabb, verziózott utódja (jelenleg PER-CS 3.1). „Kiterjeszti, kibővíti és leváltja a PSR-12-t”, és lefedi azt a szintaxist, ami a PSR-12 után jött: enumok, readonly, attribútumok, konstruktoros promóció, first-class callable-ök. A PSR-12 formálisan elfogadott marad; új projekt viszont a PER-CS-t célozza.

<?php

declare(strict_types=1);

namespace App\Billing;

use App\Support\Clock;
use Psr\Log\LoggerInterface;

final class InvoiceService implements InvoiceServiceInterface
{
    public const int MAX_RETRIES = 3;

    public function __construct(
        private readonly Clock $clock,
        private readonly LoggerInterface $logger,
    ) {
    }

    public function issue(Order $order): Invoice
    {
        if ($order->isEmpty()) {
            throw new EmptyOrderException();
        }

        return new Invoice($order, $this->clock->now());
    }
}

  1. Melyik szabály tartozik a PSR-1-hez, nem a PSR-12-höz?

    A PSR-1 a rövid alapszabvány: csak <?php/<?= nyitótag, UTF-8 BOM nélkül, a deklarál-vagy-mellékhatás szabály, StudlyCaps osztálynevek, UPPER_SNAKE konstansok, camelCase metódusok. Minden, ami whitespace és elrendezés, a PSR-12.

    A PER-CS verziózott, nem befagyasztott, így fedi le azt a szintaxist, amit a PSR-12 megelőzött: enumok, readonly, attribútumok, konstruktoros promóció, first-class callable-ök. Új projekt a PER-CS-t célozza; a PSR-12-t sosem vonták vissza.

    Ezt kézzel senki nem tartatja be. A „muszáj a PSR-12?” senior megfogalmazása az, hogy a szabvány kiválasztása sokkal kevésbé számít, mint az, hogy egyet választotok, és a CI a döntőbíró. A PHPStan típusokat és logikát ellenőriz, nem elrendezést.

PSR-4 — autoload

Egy névtérprefixet egy alapkönyvtárhoz rendel; a maradék névtérszegmensek egy az egyben alkönyvtárakra képződnek, az osztálynév pedig a fájlnévre, kis-nagybetű érzékenyen, .php kiterjesztéssel. Fájlonként egy osztály.

// composer.json
{
    "autoload": {
        "psr-4": { "App\\": "src/" }
    },
    "autoload-dev": {
        "psr-4": { "App\\Tests\\": "tests/" }
    }
}

// App\Billing\InvoiceService  ->  src/Billing/InvoiceService.php

A háttérben ez továbbra is spl_autoload_register(); a Composer csak legenerálja a leképezést. Éles környezetben futtass composer dump-autoload -o-t a classmapért.

Így kérdezik — „PSR-0 vagy PSR-4?” A PSR-0 az osztálynévben lévő aláhúzásokat is könyvtárelválasztóra fordította, és a teljes névteret útvonalként tartotta meg az alapkönyvtár alatt. A PSR-4 elhagyja az aláhúzás-szabályt, és megengedi, hogy a prefix rövidebb útvonallá olvadjon — így az App\ mutathat közvetlenül a src/-re.

    Az illesztett prefix beleolvad az alapkönyvtárba. Csak a maradék szegmensek lesznek alkönyvtárak, az osztálynév a fájlnév, az illesztés kis-nagybetű érzékeny, és .php jön a végére. Ennek elmondhatósága a szabvány lényege.

PSR-3 — logger interfész

Nyolc RFC 5424 szint: emergency, alert, critical, error, warning, notice, info, debug, plusz az általános log($level, …). Az üzenet {helyőrző} tokeneket tartalmazhat, amelyeket a context tömbből tölt ki; az exception kulcs alatt Throwable álljon.

use Psr\Log\LoggerInterface;
use Psr\Log\LoggerAwareTrait;
use Psr\Log\NullLogger;

final class PaymentProcessor
{
    public function __construct(private LoggerInterface $logger = new NullLogger()) {}

    public function charge(Order $order): void
    {
        try {
            $this->gateway->charge($order);
            $this->logger->info('A(z) {id} rendelés terhelve: {amount}', [
                'id'     => $order->id,
                'amount' => $order->total,
            ]);
        } catch (Throwable $e) {
            $this->logger->error('A(z) {id} rendelés terhelése meghiúsult', [
                'id'        => $order->id,
                'exception' => $e,
            ]);
            throw $e;
        }
    }
}

A csomag hoz még LoggerTrait-et (valósítsd meg a log()-ot, és a nyolc rövidítést ingyen kapod), LoggerAwareInterface/LoggerAwareTrait-et (setter-injektálás) és NullLogger-t.

    A nyolc RFC 5424 szint, plusz az általános log($level, …). Az a részlet szokott ütni, hogy kölcsönzött, nem kitalált — ezért képződnek le tisztán a syslogra és minden naplóaggregátorra.

    Az üzenet konstans marad, és ettől csoportosíthatók a naplók. A helyőrzőket a handler tölti ki, a fenntartott exception context-kulcsban pedig Throwable-t illik átadni, hogy a handler rendesen rendereljen tracet.

    Egy metódust írsz, nyolcat kapsz ingyen. A setter-injektálás párja a LoggerAwareInterface/LoggerAwareTrait, a NullLogger pedig az üres implementáció tesztekhez és alapértelmezésnek.

PSR-6 vs PSR-16 — két cache

PSR-6 · Caching Interface

  • CacheItemPoolInterface + CacheItemInterface
  • Az elem tévesztéskor is létezik — az isHit() árulja el
  • Késleltetett mentés, commit(), lejárat az elemen
  • Több ceremónia, több kontroll

PSR-16 · Simple Cache

  • Egyetlen CacheInterface
  • get/set/delete/has, plusz a *Multiple párjaik
  • Alapérték tévesztéskor, TTL hívásonként
  • Az esetek 90%-ában ez kell
// PSR-6
$item = $pool->getItem('rates.huf');
if (!$item->isHit()) {
    $item->set($provider->fetch())->expiresAfter(3600);
    $pool->save($item);
}
$rates = $item->get();

// PSR-16
$rates = $cache->get('rates.huf');
if ($rates === null) {
    $cache->set('rates.huf', $rates = $provider->fetch(), 3600);
}
Kulcsszabályok mindkettőhöz: a kulcs legalább egy karakter hosszú string, kötelezően támogatottak az A–Z a–z 0–9 _ . karakterek 64 hosszig, a {}()/\@: pedig fenntartott. Érvénytelen kulcsra InvalidArgumentException dobódik (a PSR sajátja, ami a Throwable-t terjeszti ki).

Mindegyiknél egy helyes válasz van. A választásaidat ez a böngésző megjegyzi, így legközelebb is itt lesznek.

  1. Mi a meghatározó különbség a PSR-6 és a PSR-16 között?

    Az item maga a tervezési döntés. Ez teszi lehetővé az isHit()-et, a késleltetett mentést és a commit()-ot. A PSR-16 ezt a kontrollt cseréli egyetlen lapos interfészre — ami az esetek nagy részében pont elég. Mindkettő elfogadott szabvány.

  2. Melyik kulcs érvényes mindkét cache-PSR alatt?

    A–Z, a–z, 0–9, aláhúzás és pont, legfeljebb 64 karakter, legalább egy hosszan. A {}()/\@: karakterek jövőbeli használatra fenntartottak, így a Redisből hozott kettőspontos névterezés nem hordozható. Az érvénytelen kulcs a PSR saját InvalidArgumentException-ét kell dobja.

    Pontosan ezt oldja meg a PSR-6 itemje. Az egyszerű interfésznél vagy olyan alapértelmezést választasz, ami valódi értékkel nem ütközhet, vagy elfogadod a has()-utána-get() versenyhelyzetet. Ha a különbség számít, használj PSR-6-ot.

PSR-7, 15, 17, 18 — a HTTP-verem

A PSR-7 immutable objektumként modellezi az üzeneteket: RequestInterface, ResponseInterface, ServerRequestInterface, StreamInterface, UriInterface, UploadedFileInterface. Minden with*() módosított klónt ad vissza — az eredmény visszaértékelésének elfelejtése a leggyakoribb PSR-7 hiba.

$response->withHeader('Content-Type', 'application/json');   // elveszett!
$response = $response->withHeader('Content-Type', 'application/json');  // helyes

A PSR-17 azért létezik, mert a PSR-7 szerződéseiben nincsenek konstruktorok: RequestFactoryInterface, ResponseFactoryInterface, StreamFactoryInterface, UriFactoryInterface és a két szerveroldali társuk. Factory-t injektálj ahelyett, hogy a kódodban a Guzzle vagy a Nyholm nevét említenéd.

A PSR-15 két apró interfészt definiál, és ebből adódik a middleware-hagyma:

use Psr\Http\Message\{ResponseInterface, ServerRequestInterface};
use Psr\Http\Server\{MiddlewareInterface, RequestHandlerInterface};

final class AuthenticationMiddleware implements MiddlewareInterface
{
    public function __construct(
        private Tokens $tokens,
        private ResponseFactoryInterface $responses,   // PSR-17
    ) {}

    public function process(
        ServerRequestInterface $request,
        RequestHandlerInterface $handler,
    ): ResponseInterface {
        $token = $request->getHeaderLine('Authorization');

        if (!$this->tokens->valid($token)) {
            return $this->responses->createResponse(401);   // rövidre zár: a $handler nem hívódik
        }

        $response = $handler->handle($request->withAttribute('user', $this->tokens->user($token)));

        return $response->withHeader('X-Auth', 'ok');       // kifelé jövet is lehet dolgozni
    }
}

A PSR-18 a klienoldal: egyetlen metódus, sendRequest(RequestInterface): ResponseInterface, szinkron, és a 4xx/5xx nem dob kivételt (azok érvényes válaszok). A kivételfája: ClientExceptionInterface ← NetworkExceptionInterface / RequestExceptionInterface.

use Psr\Http\Client\{ClientInterface, NetworkExceptionInterface};

final class ExchangeRates
{
    public function __construct(
        private ClientInterface $http,          // PSR-18
        private RequestFactoryInterface $rf,    // PSR-17
    ) {}

    public function today(): array
    {
        try {
            $response = $this->http->sendRequest($this->rf->createRequest('GET', self::URL));
        } catch (NetworkExceptionInterface $e) {
            throw new RatesUnavailable(previous: $e);
        }

        return $response->getStatusCode() === 200
            ? json_decode((string) $response->getBody(), true, flags: JSON_THROW_ON_ERROR)
            : throw new RatesUnavailable("HTTP {$response->getStatusCode()}");
    }
}

Így kérdezik — „Miért immutable a PSR-7?” Mert egy middleware-vermen áthaladó kérést nem szabad egy másik réteg háta mögött módosítani; az immutabilitás explicitté teszi az egyes rétegek változtatásait, és biztonságosan megoszthatóvá az objektumot.

  1. Mi a leggyakoribb PSR-7-es hiba?

    A $response->withHeader(...) semmit nem módosít. Módosított klónt ad vissza, amit el kell menteni vagy vissza kell adni. A PSR-7 minden interfésze így immutábilis — és pontosan ettől biztonságos a middleware-kompozíció.

  2. Miért létezik a PSR-17?

    Interfészt nem lehet new-val példányosítani. A factoryk nélkül minden választ építő könyvtárnak be kellene égetnie a Guzzle-t vagy a Nyholmot. Injektálj inkább ResponseFactoryInterface-t, és a döntés az alkalmazásnál marad.

    Csak a szállítási hiba dob. A fa: ClientExceptionInterface ← NetworkExceptionInterface (nem jött létre kapcsolat) és RequestExceptionInterface (maga a kérés használhatatlan). A státuszkód információ, nem hiba.

PSR-11 — konténerinterfész

Két metódus, és szándékosan semmilyen regisztrációs lehetőség: a PSR-11 azt szabványosítja, hogyan fogyasztják a keretrendszerek és könyvtárak a konténert, nem azt, hogyan konfigurálod.

namespace Psr\Container;

interface ContainerInterface
{
    public function get(string $id): mixed;   // NotFoundExceptionInterface-t dob
    public function has(string $id): bool;
}

interface ContainerExceptionInterface extends Throwable {}
interface NotFoundExceptionInterface extends ContainerExceptionInterface {}

A get()-nek ugyanarra az id-ra ugyanazt a példányt kell adnia (hacsak a konténert kifejezetten másképp nem konfigurálták), és ha has($id) === true, akkor a get($id) nem dobhat „nem található” hibát.

Ellenőrizd magad — 3 kérdés a témából

Mindegyiknél egy helyes válasz van. A választásaidat ez a böngésző megjegyzi, így legközelebb is itt lesznek.

  1. Miért nem definiál a PSR-11 semmilyen regisztrációs módot?

    Két metódus: get() és has(). A konfigurációs formátumok a Symfony, a Laravel és a PHP-DI között gyökeresen eltérnek, és ezek egységesítése sosem volt cél — a cél az, hogy egy könyvtár bármelyik konténert elfogadhassa.

  2. Mi kell hogy igaz legyen a get()-re a PSR-11 szerint?

    Azonos id, azonos példány. A másik garancia a has()-szal alkotott pár: ha a has($id) true, akkor a get($id) nem dobhat not-found hibát. Ismeretlen id NotFoundExceptionInterface-t dob, sosem null-t ad.

  3. A PSR-11 konténer melyik használata számít helyesnek?

    A PSR-11 a fogyasztói oldalt szabványosítja, nem engedélyt ad a mindenhol használatra. A konténer hétköznapi szolgáltatásokba injektálása a service locator antiminta — a szignatúra megszűnik leírni a valódi függőségeket.

PSR-14 — eseménydiszpécser

Három interfész, és egy figyelemre méltó tervezési döntés: az eseményeknek nincs nevük. Az esemény objektumának osztálya maga az azonosító, és az osztály → listener leképezés a provider dolga.

use Psr\EventDispatcher\{EventDispatcherInterface, ListenerProviderInterface, StoppableEventInterface};

final class OrderPaid           // egyszerű objektum, semmi más
{
    public function __construct(public readonly Order $order) {}
}

final class OrderCancelling implements StoppableEventInterface
{
    private bool $stopped = false;
    public function stop(): void { $this->stopped = true; }
    public function isPropagationStopped(): bool { return $this->stopped; }
}

// Kibocsátó oldal
$dispatcher->dispatch(new OrderPaid($order));

// Fogyasztó oldal — a provider dönti el, ki figyel
final class SendReceipt
{
    public function __invoke(OrderPaid $event): void
    {
        $this->mailer->send($event->order->customerEmail, /* … */);
    }
}

A specifikáció szándékosan szétválasztja a szerepeket: a diszpécser sorban hívja a listenereket, és korán leáll, ha az esemény megállítható és megállított; a listener provider kizárólag arra felel, hogy „mely callable-ök tartoznak ehhez az eseményhez”. Ez az interfész-szétválasztás a vadonban.

  1. Mi azonosít egy eseményt a PSR-14 szerint?

    Az osztály az azonosító. Ez szünteti meg a régebbi diszpécserek sztringalapú regiszterét, és teszi a provider feladatává az osztály → listener leképezést. Egyben azt is jelenti, hogy a listener saját paramétertípusa vezérelheti a regisztrációt.

  2. Mi a listener provider egyetlen felelőssége?

    Ez a szétválasztás az interfész-szegregáció a vadonban. A diszpécser meghívja a kapott listenereket sorban; a provider ismeri a regisztert. Attribútum- vagy konfigalapú felderítésre váltani így egyetlen komponens cseréje.

    A megállíthatóság opcionális, és az eseményen lakik. A diszpécser minden listener előtt ellenőrzi — így fejezhető ki, hogy „az első kezelő, ami tud válaszolni, nyer”. A pusztán értesítő események egyszerűen nem valósítják meg az interfészt.

SQL injection és a PDO

A string-összefűzés adatot kever a parancsba. Az előkészített lekérdezés külön csatornán küldi a lekérdezést és az értékeket, így az érték soha nem értelmeződhet SQL-ként — ez maga a védelem, nem az escapelés.

// Hibás — az $email SQL-ként értelmeződik
$pdo->query("SELECT * FROM users WHERE email = '$email'");

// Helyes
$pdo = new PDO($dsn, $user, $pass, [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,  // hangos hibázás
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    PDO::ATTR_EMULATE_PREPARES   => false,                    // valódi szerveroldali prepare
]);

$stmt = $pdo->prepare('SELECT * FROM users WHERE email = :email AND active = :active');
$stmt->execute(['email' => $email, 'active' => 1]);
$user = $stmt->fetch();
A folytatás, amire várnak. A helyőrzők értéket kötnek, azonosítót soha. Dinamikus ORDER BY, tábla- vagy oszlopnév nem paraméterezhető — fehérlistával kell validálni: 
$sortable = ['created_at', 'total', 'status'];
$column   = in_array($sort, $sortable, true) ? $sort : 'created_at';
$dir      = strtoupper($dir) === 'ASC' ? 'ASC' : 'DESC';

$pdo->prepare("SELECT * FROM orders ORDER BY $column $dir LIMIT :n");

Kikapcsolt EMULATE_PREPARES mellett a LIMIT :n-hez explicit egész kötés kell — bindValue(':n', $n, PDO::PARAM_INT) —, mert az emuláció már nem castol csendben helyetted. Az emuláció kikapcsolása ettől még helyes: ez teszi valódivá a szétválasztást ahelyett, hogy a driver stringgé fűzné össze.

Így kérdezik — „Elég a mysqli_real_escape_string()?” Nem. Kontextusfüggő, szokatlan karakterkészleteken elromlik, és semmit sem ad az azonosítókra vagy az idézőjel nélküli numerikus kontextusra. A válasz az előkészített lekérdezés; az escapelés egy előző évtized visszalépése.

Jelszavak, tokenek, véletlenszerűség

Soha ne hashelj jelszót md5()-tel, sha1()-gyel vagy bármilyen általános célú hash-sel — azok tervezetten gyorsak, ami pontosan a rossz tulajdonság. Használd a jelszó-API-t, ami a sózást, az algoritmusazonosítót és a költségfaktort is intézi.

// Regisztráció
$hash = password_hash($plain, PASSWORD_DEFAULT);   // ma bcrypt; követi az alapértelmezést
// vagy kifejezetten:
$hash = password_hash($plain, PASSWORD_ARGON2ID, ['memory_cost' => 65536, 'time_cost' => 4]);

// Bejelentkezés
if (!password_verify($plain, $user->passwordHash)) {
    throw new InvalidCredentials();
}

// Átlátszó frissítés, ha az alapértelmezés vagy a költség változik
if (password_needs_rehash($user->passwordHash, PASSWORD_DEFAULT)) {
    $repo->updateHash($user, password_hash($plain, PASSWORD_DEFAULT));
}

A kimenet már tartalmazza a sót és a paramétereket, ezért nincs külön só-oszlop. A password_verify() időzítésbiztos; amit magad hasonlítasz össze — API-kulcs, jelszó-visszaállító token, HMAC-aláírás —, ahhoz hash_equals() kell, soha nem ===.

$token = bin2hex(random_bytes(32));    // CSPRNG — titkokhoz alkalmas
$n     = random_int(1, 100);           // CSPRNG egész

// NEM titkokhoz: rand(), mt_rand(), shuffle(), uniqid(), str_shuffle()

hash_equals($expectedToken, $providedToken);   // konstans idejű
$sig = hash_hmac('sha256', $payload, $secret);

Így kérdezik — „Miért nem biztonságos a uniqid()?” Az aktuális időből származik mikroszekundum pontossággal, tehát megjósolható és kevés entrópiát hordoz. Az erre épített jelszó-visszaállító tokenek visszatérő forrásai a fiókátvételi hibáknak.

XSS, kimeneti escapelés és CSRF

A szabály: a kimeneten escapelj, abban a kontextusban, ahová írsz — nem a bemeneten sanitizálj. Ugyanaz a string az egyik kontextusban biztonságos, a másikban veszélyes.

// HTML-törzs vagy attribútum
echo htmlspecialchars($name, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');

// URL-en belül
echo '<a href="/search?q=' . rawurlencode($q) . '">';

// <script> blokkon belül — JSON, nem htmlspecialchars
echo '<script>const cfg = ' . json_encode($cfg, JSON_HEX_TAG | JSON_HEX_AMP
    | JSON_HEX_APOS | JSON_HEX_QUOT | JSON_THROW_ON_ERROR) . ';</script>';

Mindig add meg az ENT_QUOTES-t (az aposztróf attribútumban számít) és a karakterkészletet. A gyakorlatban egy automatikusan escapelő sablonmotor — Twig, Blade — az igazi válasz, plusz egy Content-Security-Policy fejléc, hogy a beinjektált szkriptnek ne legyen hol futnia. Jegyezd meg: a strip_tags() nem XSS-védelem; felhasználói rich texthez fehérlistás sanitizáló, például HTML Purifier kell.

A CSRF más támadás: a böngésző elküldi az áldozat sütijeit egy olyan kéréssel, amit az áldozat nem szándékozott. Sütikkel ezt nem lehet megkülönböztetni, ezért kell egy érték, amit a támadó oldala nem tud kiolvasni.

// Munkamenetenként egyszer generáljuk
$_SESSION['csrf'] ??= bin2hex(random_bytes(32));

// Az űrlapban
echo '<input type="hidden" name="_token" value="'
   . htmlspecialchars($_SESSION['csrf'], ENT_QUOTES, 'UTF-8') . '">';

// Minden állapotváltoztató kérésnél
if (!hash_equals($_SESSION['csrf'], $_POST['_token'] ?? '')) {
    http_response_code(419);
    exit;
}

Párosítsd SameSite=Lax (vagy Strict) sütikkel, ami modern böngészőkben blokkolja a cross-site kérést — mélységi védelem, nem helyettesítés, mert a SameSite nem fed le minden esetet. És a GET soha ne változtasson állapotot: a linkre tett CSRF-token a tünetet kezeli.

Munkamenet, feltöltés és unserialize

Session fixation — a támadó elhelyez egy általa ismert munkamenet-azonosítót, majd megvárja, hogy az áldozat azzal jelentkezzen be. A javítás egyetlen sor, minden jogosultságváltásnál:

session_set_cookie_params([
    'httponly' => true,        // JavaScriptből nem olvasható
    'secure'   => true,        // csak HTTPS
    'samesite' => 'Lax',
]);
session_start();

// sikeres bejelentkezéskor, és kilépéskor újra
session_regenerate_id(true);   // true = a régi munkamenet törlése

Fájlfeltöltés — a $_FILES-ból semmi nem megbízható, ami a klienstől jött, beleértve a name-et és a type-ot:

$file = $_FILES['avatar'];

if ($file['error'] !== UPLOAD_ERR_OK || !is_uploaded_file($file['tmp_name'])) {
    throw new UploadFailed();
}

$mime = (new finfo(FILEINFO_MIME_TYPE))->file($file['tmp_name']);   // a tartalmat nézzük
if (!in_array($mime, ['image/png', 'image/jpeg', 'image/webp'], true)) {
    throw new UnsupportedMediaType($mime);
}

$name = bin2hex(random_bytes(16)) . '.' . self::EXT[$mime];   // a kliens nevét sosem használjuk
move_uploaded_file($file['tmp_name'], self::STORAGE . '/' . $name);   // a webgyökéren kívülre

Az unserialize() nem megbízható bemeneten távoli kódfuttatás, POP-láncokon keresztül, amiket a betöltött osztályok __destruct/__wakeup metódusaiból építenek. Bizalmi határon átlépő adathoz használj json_decode()-ot; ha tényleg unserialize-ra van szükség, add át a ['allowed_classes' => false] opciót.

Típuszsonglőrködés az összehasonlításban. A laza == hash-re alkalmazva a klasszikus „magic hash” hiba: két különböző string, ha mindkettő 0e-vel és utána számjegyekkel kezdődik, számként egyenlőnek bizonyul. A PHP 8 jelentősen szigorított a string-szám összehasonlításon, de a tanulság áll: biztonsági szempontból bármihez === vagy hash_equals() kell. Élesben ezen felül állítsd a display_errors=0-t és naplózz helyette; a képernyőn megjelenő stack trace információszivárgás.

Kérés-életciklus, OPcache és a JIT

A PHP shared-nothing: minden kérés tiszta interpreterállapottal indul, és a végén minden lebomlik. Alkalmazásszintű memória nem él túl kéréseket — ezért skálázódik a PHP olyan könnyen vízszintesen, és ezért kell mindennek, amin osztozni kell, Redisben, adatbázisban vagy a munkamenet-tárolóban laknia.

Ami kérésenként történik: a SAPI (általában PHP-FPM) átadja a szkriptet a motornak → lexer → parser → AST → opkódokká fordítás → a Zend VM végrehajtja → a leállás mindent felszabadít.

Az OPcache megszünteti a fordítási lépést azzal, hogy megosztott memóriában tárolja az opkódokat. Ez a legnagyobb elérhető teljesítménynyereség, és modern buildekben alapból be van kapcsolva.

; php.ini — éles
opcache.enable=1
opcache.memory_consumption=256
opcache.max_accelerated_files=20000      ; több legyen, mint a fájljaid száma
opcache.interned_strings_buffer=16
opcache.validate_timestamps=0            ; nincs fájl-stat; deploykor újratöltés kell
opcache.preload=/var/www/preload.php     ; PHP 7.4+: a keretrendszer osztályai egyszer, induláskor

A validate_timestamps=0 az éles beállítás, és a klasszikus deploy-csapda: a deploynak újra kell töltenie az FPM-et (vagy opcache_reset()-et hívnia), különben a régi kódot szolgálod ki tovább. A preloading még tovább megy: induláskor véglegesen memóriába fordítja az osztályokat, így többé nem töltődnek be.

A JIT (PHP 8.0, a 8.4-ben átdolgozva) gépi kódra fordítja a forró opkódokat. Ezt mondd ki nyíltan: nagy nyereséget CPU-igényes numerikus munkán ad, és tipikusan alig vagy semennyit egy szokásos webalkalmazáson, mert azokat az adatbázis és a hálózati I/O korlátozza, nem az opkód-diszpécselés.

opcache.jit=tracing
opcache.jit_buffer_size=64M    ; 0 kikapcsolja a JIT-et

A PHP-FPM egy mesterfolyamatot és worker-készletet futtat. A pm.max_children-t a rendelkezésre álló RAM és a valódi workerenkénti memóriaigény hányadosaként méretezd — a túltervezés swappeléshez vezet, ami sokkal rosszabb a sorban állásnál.

pm = dynamic
pm.max_children = 40           ; RAM / átlagos worker-memória
pm.start_servers = 8
pm.max_requests = 500          ; a workerek újraindítása korlátozza a szivárgást
request_terminate_timeout = 30s
slowlog = /var/log/php-fpm-slow.log
request_slowlog_timeout = 5s   ; stack trace-t ír a lassú kérésekről — nagyon hasznos

Így kérdezik — „Lassú az alkalmazás. Hol nézel utána?” Először mérj, profilerrel (Blackfire, Xdebug, Excimer) vagy APM-mel — ne találgass. A megtérülés sorrendje a gyakorlatban: N+1 lekérdezések és hiányzó indexek, aztán cache-elés, aztán OPcache és autoloader-beállítás, aztán minden más. A JIT-hez nyúlni elsőként rossz válasz.

Párhuzamosság, sorok és Fiberek

A PHP-nak a szokásos felhasználói kódban nincsenek szálai. A párhuzamosság több folyamat futtatásából jön — amit a shared-nothing modell triviálissá tesz —, vagy egy folyamaton belüli eseményhurokból.

A Fiberek (PHP 8.1) a második lehetőség nyelvi primitívjei: teljes vermű, megszakítható függvény, amit a hívási verem bármely pontjáról fel lehet függeszteni és folytatni. A fiberek önmagukban nem párhuzamosság — a nyelvben nincs ütemező —, hanem azt teszik lehetővé, hogy az AMPHP és a ReactPHP az aszinkron I/O-t hétköznapi, szinkronnak látszó kódként mutassa be, async/await kulcsszavak nélkül.

$fiber = new Fiber(function (string $start): string {
    echo "$start\n";
    $resumeValue = Fiber::suspend('felfüggesztve');   // visszaadja a vezérlést az indítónak
    echo "folytatva ezzel: $resumeValue\n";
    return 'kész';
});

$suspendValue = $fiber->start('fut');       // 'felfüggesztve'
$fiber->resume('egy érték');                // kiírja: "folytatva ezzel: egy érték"
$fiber->getReturn();                        // 'kész'

Fiber vs generátor

  • A generátor csak a saját törzsében függeszthető fel — minden hívónak is yieldelnie kell
  • A fiber a teljes vermet felfüggeszti, tetszőleges mélységből
  • Ez szünteti meg a „függvényszínezés” problémáját az aszinkron PHP-ban

Munka levétele a kérésről

  • Sorok: Symfony Messenger, Laravel Horizon — az alapértelmezett válasz
  • Hosszan futó futtatókörnyezetek: Swoole, RoadRunner, FrankenPHP worker mód
  • curl_multi_* párhuzamos kimenő HTTP-hez, keretrendszer nélkül

Így kérdezik — „Hogyan küldenél ki 10 000 e-mailt?” Nem a kérésben. Told a feladatokat sorba, dolgozd fel workerekben, tedd minden feladatot idempotenssé és újrapróbálhatóvá exponenciális visszalépéssel, és korlátozd a párhuzamosságot a szolgáltató rate limitjéhez. Aztán említsd meg a memóriapontot a szemétgyűjtés témából: a hosszan futó workereket újra kell indítani.

    Nincsenek szálak, és a Fiberek sem azok. A Fiberek egyszerre egy futnak — felfüggesztési primitívek, nem párhuzamosság. A valódi párhuzamosság PHP-ban több folyamatot jelent, amit a shared-nothing modell triviálissá tesz.

Adatbázisok: PDO, tranzakciók, izoláció

PDO vagy mysqli — a PDO tucatnyi drivert fed le, támogatja a névvel ellátott paramétereket, és egységes az API-ja; a mysqli csak MySQL-hez való, de kínál néhány driverspecifikus funkciót. Új kódhoz PDO, hacsak nem kell valami, ami csak a mysqliben van.

$pdo->beginTransaction();

try {
    $pdo->prepare('UPDATE accounts SET balance = balance - ? WHERE id = ?')
        ->execute([$amount, $from]);
    $pdo->prepare('UPDATE accounts SET balance = balance + ? WHERE id = ?')
        ->execute([$amount, $to]);

    $pdo->commit();
} catch (Throwable $e) {
    $pdo->rollBack();
    throw $e;
}

A composer.json azt mondja meg, mit szeretnél; a composer.lock azt rögzíti, mit kaptál, commit szintjéig. Az alkalmazások commitolják a lock fájlt, hogy minden környezet bájtra azonos függőségeket telepítsen; a könyvtárak nem, mert a fogyasztóik maguk oldják fel a verziókat.

Tesztelés

A modern PHPUnit annotációk helyett attribútumokat használ, ami szépen összecseng a korábbi attribútum-témával.

use PHPUnit\Framework\Attributes\{DataProvider, Test};
use PHPUnit\Framework\TestCase;

final class ConvertMoneyTest extends TestCase
{
    #[Test]
    public function it_converts_using_the_injected_rate(): void
    {
        $rates = $this->createStub(RateProvider::class);   // stub: előre megadott válaszok
        $rates->method('rate')->willReturn(0.0025);

        $convert = new ConvertMoney($rates);

        self::assertSame(500, $convert(new Money(200_000, 'HUF'), 'EUR')->amount);
    }

    #[Test]
    public function it_notifies_the_gateway_exactly_once(): void
    {
        $gateway = $this->createMock(Gateway::class);      // mock: az interakciót ellenőrzi
        $gateway->expects(self::once())
                ->method('charge')
                ->with(self::isInstanceOf(Order::class));

        (new PaymentProcessor($gateway))->charge(new Order());
    }

    #[Test]
    #[DataProvider('invalidEmails')]
    public function it_rejects_invalid_emails(string $email): void
    {
        $this->expectException(InvalidArgumentException::class);
        new EmailAddress($email);
    }

    public static function invalidEmails(): iterable
    {
        yield 'nincs kukac'    => ['laslow.example.com'];
        yield 'üres'           => [''];
        yield 'két kukac'      => ['a@b@c.hu'];
    }
}

A teszthelyettesek szótára, mert az interjúztatók kérik a megkülönböztetést: a dummy átadódik, de sosem használódik; a stub előre megadott értékeket ad vissza; a spy rögzíti a hívásokat későbbi ellenőrzésre; a mock előre beállított elvárásokkal rendelkezik, és elbukik, ha nem teljesülnek; a fake valódi, működő implementáció, ami éles használatra alkalmatlan — például egy memóriabeli repository.

A tesztelhetőség tervezési tulajdonság, nem tesztelési technika — ezért is tartozik ez a szakasz a DI-téma mellé. Az a kód, ami new-val hoz létre együttműködőt, statikust olvas, vagy a date()-től kérdezi az időt, nem tesztelhető izoláltan. Injektálj PSR-20 órát, PSR-18 HTTP-klienst és repository-interfészt, és a tesztek szinte megírják magukat.

Így kérdezik — „Milyen lefedettséget céloztok?” A senior válasz ellenáll a számnak: a lefedettség azt méri, mely sorok futottak le, nem azt, hogy állítottunk-e róluk bármit. A mutációs tesztelés (Infection) azt méri, hogy a tesztjeid tényleg elkapnának-e egy hibát — ez az a tulajdonság, ami érdekel. A kritikus utak legyenek jól tesztelve, a lefedettségi célszám pedig inkább padló legyen, mint cél.

  1. Dummy, stub, spy, mock és fake — melyik melyik?

    Amit valójában kérdeznek, az a mock és a spy különbsége: a mock előre kimondja az elvárásait, és a művelet közben bukik; a spy csendben marad, és utólag kérdezed ki. A memóriabeli repository a tankönyvi fake.
