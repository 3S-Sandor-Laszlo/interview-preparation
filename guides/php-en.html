Classes, objects, constructor promotion

A class is a blueprint; an object is an instance with its own property state. PHP 8 promotes constructor parameters straight to properties — declaration, type, visibility and assignment in one place.

class Money
{
    public function __construct(
        public readonly int $amount,        // minor units, e.g. fillér
        public readonly string $currency = 'HUF',
    ) {}

    public function add(self $other): static
    {
        if ($other->currency !== $this->currency) {
            throw new InvalidArgumentException('Currency mismatch');
        }
        return new static($this->amount + $other->amount, $this->currency);
    }
}

$a = new Money(1_500);
$b = $a->add(new Money(500));   // Money(2000); $a is untouched

class Discount extends Money {}

$d = new Discount(1_000);
$e = $d->add(new Money(500));   // Discount(1500) — new static() instantiates the class actually
                                // called on; with new self() this would come back as Money

Asked as — “What does new static() do that new self() doesn’t?” self resolves to the class where the code is written; static resolves to the called class at runtime (late static binding).

  1. What does public readonly int $amount in a constructor signature actually declare?

    Promotion does four things at once: it declares the property, gives it a type and a visibility, and assigns the incoming argument to it. That is the whole point — no duplicated declaration, no $this->amount = $amount; line.

  2. Inside Money::add(), what does new static(...) do that new self(...) would not?

    Late static binding. self is resolved where the code is written; static is resolved by the class the method was called on. So Money::add() inherited by Discount returns a Discount with new static(), but a Money with new self().

  3. Which statement about constructor promotion is true?

    Promotion is a constructor-only feature. Defaults are allowed (string $currency = 'HUF'), the visibility keyword is what triggers promotion in the first place, and declaring the property again in the body raises “Cannot redeclare property”.

  4. After $a = new Money(1500); $b = $a; — what is the relationship between $a and $b?

    Objects are handles, not values. Assignment copies the handle, so both names point at one object — unlike arrays, which are values with copy-on-write. A real copy needs clone, and that is shallow unless __clone() says otherwise.

  5. Given the Money class above, what happens at $a->amount = 2000; after construction?

    “Cannot modify readonly property Money::$amount”, an Error at runtime. Readonly is write-once from the declaring scope, not merely private-for-writing — which is exactly what makes add() return a new instance instead of mutating this one.

Encapsulation & visibility

Three modifiers: public everywhere, protected in the class and its subclasses, private in the declaring class only. Visibility in PHP is class-scoped, not object-scoped — one instance can read another instance’s privates as long as the code lives in the same class.

class Account
{
    public function __construct(private int $balance) {}

    public function richerThan(Account $other): bool
    {
        return $this->balance > $other->balance;  // legal: same class
    }
}

PHP 8.4 adds asymmetric visibility — readable publicly, writable only from inside:

class Order
{
    public private(set) string $status = 'draft';   // PHP 8.4+

    public function pay(): void { $this->status = 'paid'; }
}

Asked as — “Difference between private and protected?” Then the follow-up: “Can a parent call a private method of a child?” No — and if the child redeclares it, PHP keeps two separate methods.

  1. PHP visibility is class-scoped rather than object-scoped. What does that allow?

    The check is “am I in the declaring class?”, not “am I on this object?” That is why Account::richerThan(Account $other) can read $other->balance. A subclass still cannot see the parent's privates — that is what protected is for.

  2. What does public private(set) string $status declare in PHP 8.4?

    Asymmetric visibility. The first modifier is the read visibility, private(set) is the write visibility. It replaces the getter-only boilerplate: callers read $order->status directly, but only pay() can change it.

  3. Can a parent class call a private method declared in one of its children?

    Private methods do not participate in polymorphism. The parent's code always calls the parent's private method, the child's code always calls the child's — they coexist without overriding each other. This is why final private function warns on PHP 8: private is already unoverridable.

Inheritance

Single inheritance only — one extends. parent:: reaches the overridden implementation. final stops further extension or overriding.

abstract class Repository
{
    public function __construct(protected PDO $pdo) {}

    protected function fetchOne(string $sql, array $params): ?array
    {
        $stmt = $this->pdo->prepare($sql);
        $stmt->execute($params);
        return $stmt->fetch(PDO::FETCH_ASSOC) ?: null;
    }
}

final class UserRepository extends Repository
{
    public function __construct(PDO $pdo, private Clock $clock)
    {
        parent::__construct($pdo);
    }

    public function find(int $id): ?array
    {
        return $this->fetchOne('SELECT * FROM users WHERE id = ?', [$id]);
    }
}
Composition over inheritance. Expect the follow-up. Inheritance couples subclasses to a parent’s implementation forever; composition (injecting a collaborator) swaps behaviour at runtime and keeps the hierarchy flat. Reach for inheritance when it is genuinely “is-a”, and for interfaces + composition otherwise.

  1. In the UserRepository example, why is parent::__construct($pdo) needed?

    Declaring __construct() in the child replaces the parent's entirely. Unlike Java, PHP inserts no implicit super() call — if the parent has setup to do, you must call it yourself, and forgetting it leaves $pdo uninitialised.

  2. What does final on a class actually prevent?

    final class blocks extends outright; final function blocks overriding a single method. A final class may still implement as many interfaces as it likes — which is exactly the recommended shape: final classes behind interfaces.

  3. The standard follow-up is “composition over inheritance”. What is the argument in one sentence?

    The cost is coupling, not performance. A subclass inherits every future change to the parent, whether or not it wants it. Use inheritance for a genuine “is-a” relationship; otherwise depend on an interface and inject the implementation.

Polymorphism

One call site, many implementations, chosen by the runtime type. PHP does not support method overloading by signature — __call() and default/variadic parameters are the substitute.

interface Exporter
{
    public function extension(): string;
    public function export(array $rows): string;
}

final class CsvExporter implements Exporter
{
    public function extension(): string { return 'csv'; }

    public function export(array $rows): string
    {
        $out = fopen('php://temp', 'r+');
        foreach ($rows as $row) { fputcsv($out, $row); }
        rewind($out);
        return stream_get_contents($out);
    }
}

final class JsonExporter implements Exporter
{
    public function extension(): string { return 'json'; }
    public function export(array $rows): string
    {
        return json_encode($rows, JSON_THROW_ON_ERROR | JSON_PRETTY_PRINT);
    }
}

function save(Exporter $e, array $rows, string $name): void
{
    file_put_contents("{$name}.{$e->extension()}", $e->export($rows));
}

Asked as — “Does PHP support method overloading?” Not in the Java sense. __call()/__callStatic() is what the manual calls “overloading”, and it means something different: intercepting inaccessible calls.

  1. Does PHP support method overloading in the Java sense — several methods with the same name and different signatures?

    One name, one method. What the PHP manual calls “overloading” is __call()/__callStatic() — intercepting calls to inaccessible methods — which is a different feature with a confusingly similar name.

  2. In save(Exporter $e, array $rows, string $name), what decides which export() body runs?

    Dynamic dispatch. The type hint only constrains what may be passed; the engine looks up the method on the object's real class at call time. That is the whole mechanism, and it is why save() never needs to change when a third exporter appears.

  3. What is the practical benefit of save() depending on Exporter rather than on the two concrete classes?

    Open for extension, closed for modification. The alternative — a match on a format string inside save() — grows a branch for every new format, and every addition risks breaking the existing ones.

Abstract class vs interface

An interface is a contract with no state; an abstract class is a partially built class you inherit from. Since PHP 8.4 interfaces may also declare constants and (8.3) typed constants, but never properties with values.

Abstract class

  • Can hold properties and state
  • Can define constructors
  • Mix of implemented and abstract methods
  • Visibility: public / protected / private
  • One per class

Interface

  • No properties, no state
  • No constructor body
  • Method signatures only (plus constants)
  • All members implicitly public
  • Many per class; interfaces may extend several interfaces
interface Notifier
{
    const int MAX_RETRIES = 3;              // typed constant, PHP 8.3+
    public function send(string $to, string $body): void;
}

abstract class QueuedNotifier implements Notifier
{
    public function __construct(protected Queue $queue) {}

    public function send(string $to, string $body): void
    {
        $this->queue->push($this->payload($to, $body));
    }

    abstract protected function payload(string $to, string $body): array;
}

Asked as — “When would you pick one over the other?” Interface when you need a capability that unrelated classes can claim; abstract class when subclasses genuinely share implementation. In practice: program against the interface, share code via an abstract base or a trait.

  1. Which of these can an abstract class do that an interface cannot?

    State and construction are the dividing line. Interfaces are pure contracts: signatures and constants, no properties, no constructor body, all members implicitly public. An abstract class is a half-built class, which is why you only get one.

  2. A class needs both a shared implementation and several unrelated capability contracts. What does PHP allow?

    Single inheritance, multiple interfaces. QueuedNotifier spends its one inheritance slot on shared queueing code while Notifier stays a contract that any class can claim. Interfaces themselves may extend several interfaces.

  3. What is const int MAX_RETRIES = 3; inside an interface?

    Interface constants have existed for a long time; the type is the PHP 8.3 part. Since PHP 8.1 an implementing class may also override an interface constant — before that it was forbidden.

Traits

Horizontal reuse — a compiler-level copy-paste of methods, properties and abstract requirements into a class. Not a type: you cannot type-hint against a trait.

trait Timestamps
{
    private ?DateTimeImmutable $updatedAt = null;

    public function touch(): void
    {
        $this->updatedAt = $this->clock()->now();
    }

    abstract protected function clock(): Clock;   // trait demands a collaborator
}

trait Loggable
{
    public function touch(): void { /* … */ }
}

final class Article
{
    use Timestamps, Loggable {
        Timestamps::touch insteadof Loggable;   // resolve the collision
        Loggable::touch as logTouch;            // keep the other under a new name
    }

    public function __construct(private Clock $clock) {}
    protected function clock(): Clock { return $this->clock; }
}

Precedence, highest first: the class’s own method → trait method → inherited method. Traits can hold static and abstract members; two traits with the same property are only allowed if the definitions are identical.

Asked as — “Trait vs interface vs abstract class?” Interface = contract, no code. Trait = code, no contract. Abstract class = both, but uses up your one inheritance slot.

  1. What does use Timestamps; do at the language level?

    Traits are compiler-assisted copy-paste. Nothing about the trait survives as a type — $x instanceof Timestamps is a fatal error, and you cannot type-hint it. If you need the type, pair the trait with an interface.

  2. Two traits used by the same class both define touch(). What happens?

    Collisions are a compile-time fatal error by design. Timestamps::touch insteadof Loggable; picks the winner, and Loggable::touch as logTouch; keeps the loser available under a new name.

  3. A class, a trait it uses, and its parent all define the same method. Which one runs?

    Own method → trait method → inherited method. The useful consequence: a trait can override an inherited implementation without touching the parent, but the class itself always keeps the final say.

Static members & late static binding

self, static, parent are the three scope keywords. self:: binds at compile time to the defining class; static:: binds at runtime to the class that was actually called — that is late static binding (LSB).

abstract class Model
{
    public static function create(array $attrs): static
    {
        return new static($attrs);        // LSB: returns the concrete subclass
    }

    public static function table(): string
    {
        return self::guess();             // always Model::guess(), even in subclasses
    }

    protected static function guess(): string { return 'models'; }
}

final class User extends Model
{
    public function __construct(private array $attrs) {}
    protected static function guess(): string { return 'users'; }
}

User::create(['name' => 'Laslow']);  // User instance, thanks to `new static`
User::table();                       // 'models' — self:: ignored the override

Swap self::guess() for static::guess() and the second call returns 'users'. That one-line difference is the whole question.

Named constructors

PHP has no constructor overloading — one class, one __construct. The idiom that replaces it is the named constructor: hide the real constructor behind private or protected, and expose static factories whose names say what they build and which validate their own input. Late static binding is what keeps them inheritable.

class Duration
{
    protected function __construct(public readonly int $seconds)
    {
        if ($seconds < 0) {
            throw new InvalidArgumentException('A duration cannot be negative.');
        }
    }

    public static function fromSeconds(int $seconds): static
    {
        return new static($seconds);                 // LSB: the called class, not Duration
    }

    public static function fromMinutes(int $minutes): static
    {
        return static::fromSeconds($minutes * 60);   // static:: so overrides win
    }

    public static function zero(): static
    {
        return static::fromSeconds(0);
    }
}

final class Timeout extends Duration
{
    public static function fromSeconds(int $seconds): static
    {
        return new static(min($seconds, 30));        // clamp: never wait longer
    }
}

Duration::fromMinutes(2);   // Duration(120)
Timeout::fromMinutes(2);    // Timeout(30) — static:: reached the override
Timeout::zero();            // Timeout(0)  — inherited, still the right class

Write new self($seconds) or self::fromSeconds(...) instead and both subclass calls collapse back to Duration: the factory silently returns the wrong type and the clamp never runs. The static return type carries the same promise into the type system, so Timeout::fromMinutes() is typed as Timeout without a narrowing check at the call site.

Asked as — “How do you do constructor overloading in PHP?” You don’t. You give the constructor restricted visibility and add named static factories — fromString(), fromArray(), zero() — which is also where validation and normalisation belong.

Statics are global state. They bypass DI, are hard to substitute in tests, and make dependencies invisible in the signature. Acceptable for pure functions and named constructors; a smell for anything touching I/O.

  1. Model::table() returns self::guess(). Why does User::table() return 'models'?

    self is lexical, static is dynamic. Change the body to static::guess() and the same call returns 'users'. That one-keyword difference is late static binding, and it is the single most asked static-related question.

Hooks the engine calls for you. They are slower than real methods and invisible to static analysis, so use them for genuine dynamism only.

final class Config implements Stringable
{
    public function __construct(private array $items = []) {}

    public function __get(string $key): mixed
    {
        return $this->items[$key] ?? throw new OutOfBoundsException($key);
    }

    public function __isset(string $key): bool   // without this, isset($c->foo) is false
    {
        return isset($this->items[$key]);
    }

    public function __call(string $name, array $args): mixed
    {
        if (str_starts_with($name, 'get')) {
            return $this->{lcfirst(substr($name, 3))};
        }
        throw new BadMethodCallException($name);
    }

    public function __toString(): string { return json_encode($this->items); }
}

$config = new Config(['dsn' => 'pgsql:host=localhost', 'debug' => true]);

$config->dsn;              // __get      'pgsql:host=localhost'
isset($config->debug);     // __isset    true
isset($config->missing);   // __isset    false — __get is never consulted
$config->getDsn();         // __call     falls through to __get('dsn')
echo $config;              // __toString {"dsn":"pgsql:host=localhost","debug":true}

$config->missing;          // __get      throws OutOfBoundsException('missing')
$config->reload();         // __call     throws BadMethodCallException('reload')

Asked as — “Why does isset() return false on a magic property?” Because __get is not consulted by isset(); you must implement __isset too.

  1. Why does isset($config->missing) return false even when __get() would have returned a value?

    They are separate hooks. isset() and empty() route to __isset(), unset() to __unset(). Implementing __get() alone gives you a property that reads fine but reports itself as not set — including inside ??.

  2. When does __call() fire?

    Inaccessible counts as missing. Calling a private method from outside the class routes to __call() if one exists, which is a genuine surprise in code review — and why the manual calls these hooks “overloading”.

  3. What is the main cost of building an API out of magic methods?

    You trade tooling for dynamism. PHPStan cannot check a call it cannot see, so the safety net disappears exactly where the behaviour is hardest to follow. Use them where the shape is genuinely dynamic, and document with @method when you do.

Cloning: shallow by default

clone copies property values. Object-typed properties are copied by handle, so the copy shares them. __clone() runs on the new object and is where you deep-copy.

final class Invoice
{
    private DateTimeImmutable $issuedAt;
    private ArrayObject $lines;

    public function __clone(): void
    {
        $this->lines = clone $this->lines;   // deep copy the mutable collection
        // $issuedAt is immutable — sharing it is safe and cheaper
    }
}

$copy = clone $invoice;

PHP 8.3 lets __clone() reinitialise readonly properties, so a readonly property holding a mutable object can finally be deep-copied — before 8.3 that assignment was a fatal error. The permission is scoped to __clone() itself: a with*() method still cannot assign to $copy->prop after cloning, and trying is Error: Cannot modify readonly property.

Where you actually need it: withers

The everyday reason to reach for clone is “the same object, with one thing changed” on a type you refuse to mutate. Rebuilding with new self(...) means re-passing every property — so each new property means editing every wither, and any state the constructor does not take is lost. Cloning carries the whole object across and you adjust the one field:

final class Request
{
    private array $headers = [];
    private array $query   = [];

    public function __construct(
        private string $method,
        private string $uri,
    ) {}

    public function withHeader(string $name, string $value): self
    {
        $copy = clone $this;                         // carries method, uri, query, everything
        $copy->headers[strtolower($name)] = $value;  // private, but $copy is the same class
        return $copy;
    }

    public function withQuery(string $key, string $value): self
    {
        $copy = clone $this;
        $copy->query[$key] = $value;
        return $copy;
    }
}

$base = (new Request('GET', '/reports'))->withHeader('Accept', 'application/json');
$csv  = $base->withHeader('Accept', 'text/csv')->withQuery('period', '2026-Q1');

// $base is untouched: Accept is still application/json and its query is still empty
$base === $csv;   // false — a new identity carrying the old state plus the change

Two things make this work. clone gives a new identity, so whoever handed you $base is unaffected; and because $copy is an instance of the same class, its private properties are still writable from inside the method. This is exactly how PSR-7 withHeader()/withUri() are built, and why passing a request object around is safe. DateTimeImmutable::modify() is the same idea in the core library.

Asked as — “Why does PSR-7 use withHeader() rather than setHeader()?” Because a shared request must not change under a middleware that did not expect it; each with*() hands back a clone and leaves the caller’s copy alone.

Enums

PHP 8.1 enums are objects: singleton cases, allowed to implement interfaces, hold constants and methods, but never instance state. Pure enums have no scalar value; backed enums map to int or string.

enum OrderStatus: string implements JsonSerializable
{
    case Draft     = 'draft';
    case Paid      = 'paid';
    case Shipped   = 'shipped';
    case Cancelled = 'cancelled';

    public function isFinal(): bool
    {
        return match ($this) {
            self::Shipped, self::Cancelled => true,
            default => false,
        };
    }

    public function label(): string
    {
        return ucfirst($this->value);
    }

    public function jsonSerialize(): string { return $this->value; }
}

OrderStatus::from('paid');       // OrderStatus::Paid — throws ValueError if unknown
OrderStatus::tryFrom('nope');    // null
OrderStatus::cases();            // array of all cases
OrderStatus::Paid->name;         // 'Paid'   (read-only)
OrderStatus::Paid->value;        // 'paid'

Asked as — “Enum vs class constants?” Enums are type-safe (a function typed OrderStatus cannot receive a stray string), exhaustively matchable, and carry behaviour. Constants are just values.

  1. What is the difference between OrderStatus::from('nope') and OrderStatus::tryFrom('nope')?

    Use from() for trusted input and tryFrom() at a boundary, where an unknown value is a validation failure rather than a bug. Both exist only on backed enums; a pure enum has no scalar to convert from.

  2. Which of these is not possible in a PHP enum?

    Cases are singletons with no instance state. name and the backed value are the only data; anything else must be derived in a method, as label() and isFinal() do. That constraint is what makes === comparison of cases reliable.

  3. Why prefer an enum over a set of class constants?

    Type safety is the headline. With constants, the parameter type is still string and any typo passes; with an enum, the engine rejects it, static analysis can prove a match covers every case, and methods like isFinal() live next to the data.

The type system, variance, never

Nullable (?T), union (A|B), intersection (A&B, PHP 8.1), plus the special types void, never, static, self, mixed, iterable. PHP 8.2 adds DNF types: (A&B)|null.

declare(strict_types=1);

function shutdown(string $reason): never   // never returns: throws or exits
{
    throw new RuntimeException($reason);
}

function persist(Countable&Traversable $rows): void { /* … */ }

Covariance — a child may narrow a return type. Contravariance — a child may widen a parameter type. Both preserve Liskov substitutability.

class AnimalShelter          { public function adopt(): Animal { /* … */ } }
class DogShelter extends AnimalShelter
{
    public function adopt(): Dog { /* … */ }   // covariant return: narrower, OK
}

class Handler       { public function handle(Dog $a): void {} }
class LooseHandler extends Handler
{
    public function handle(Animal $a): void {}  // contravariant param: wider, OK
}
declare(strict_types=1) is per-file and applies to calls made from that file, not to the file being called. Without it PHP coerces ("5" → 5); with it, a wrong scalar type throws TypeError. The next topic covers the rules in full.

Strict mode — and how it differs from Java

PHP has two typing modes. Coercive is the default: a scalar that can reasonably become the declared type is converted. Strict is opted into per file and refuses the conversion instead.

declare(strict_types=1);   // must be the VERY first statement in the file

Three rules decide everything, and interviewers test all three:

  • It is per file, and the calling file decides. Not the file where the function was declared. A strict file calling a sloppy library is still strict at that call site; a coercive file calling a strict library’s function still coerces.
  • It affects scalars only — int, float, string, bool. Class types, array, callable and iterable were never coerced, so strict mode changes nothing for them.
  • One widening survives: int → float is still accepted in strict mode. Nothing else is.
function vatOf(int $netHuf): int { return (int) round($netHuf * 0.27); }

// Coercive mode (no declare)
vatOf('1500');    // 1500 — numeric string converted
vatOf(1500.0);    // 1500 — float with no fractional part converted
vatOf(1500.5);    // 1500 + deprecation notice (implicit lossy conversion, PHP 8.1+)
vatOf('abc');     // TypeError even here — PHP 8 stopped accepting non-numeric strings
vatOf(true);      // 1

// Strict mode
vatOf('1500');    // TypeError: must be of type int, string given
vatOf(1500.0);    // TypeError — no float-to-int, not even a lossless one
vatOf(1500);      // fine

function grossOf(float $netHuf): float { return $netHuf * 1.27; }
grossOf(1500);    // 1905.0 — fine even in strict mode: int -> float is the one allowed widening

// Internal functions honour it too
strlen(42);       // strict: TypeError.  coercive: 2

Return values follow the mode of the file where the function is declared, since that is where the return statement lives. So a function declared in a strict file cannot quietly return "5" from an int signature, no matter who calls it.

Exception hierarchy

Everything catchable implements Throwable. Below it sit two branches: Error (engine-level: TypeError, ValueError, ArgumentCountError, DivisionByZeroError) and Exception (application-level, with RuntimeException and LogicException as the SPL roots).

Generators

A function containing yield returns a Generator (which implements Iterator) and computes lazily — constant memory over an unbounded stream.

function readRows(string $path): Generator
{
    $fh = fopen($path, 'r');
    try {
        while (($row = fgetcsv($fh)) !== false) {
            yield $row;                 // one row in memory at a time
        }
    } finally {
        fclose($fh);
    }
    return 'done';                      // retrieved via $gen->getReturn()
}

foreach (readRows('export.csv') as $row) { /* … */ }

Garbage collection

PHP frees memory in two stages. Reference counting does almost all the work: every value carries a refcount, and the moment it drops to zero the value is destroyed immediately — that is why __destruct() is deterministic in PHP, unlike Java or C#. The cycle collector exists only to clean up what refcounting cannot: groups of objects that reference each other and so never reach zero.

$a = new Article();   // refcount 1
$b = $a;              // refcount 2 — objects are shared by handle, not copied
unset($a);            // refcount 1 — nothing freed yet
unset($b);            // refcount 0 — destroyed now, __destruct() runs here

Why cycles need a collector

Two objects pointing at each other keep each other alive even after the last outside reference is gone. This is the classic parent ↔ child leak:

final class Node
{
    public ?Node $parent = null;
    /** @var list<Node> */
    public array $children = [];

    public function add(Node $child): void
    {
        $child->parent = $this;      // child -> parent
        $this->children[] = $child;  // parent -> child   ← the cycle
    }

    public function __destruct() { echo "freed\n"; }
}

function build(): void
{
    $root = new Node();
    $root->add(new Node());
}   // $root goes out of scope, but neither refcount reaches 0 — nothing printed

build();
gc_collect_cycles();   // NOW both are freed: "freed freed"

How the collector works

PHP uses a synchronous mark-and-sweep over a root buffer (the Bacon–Rajan concurrent cycle collection algorithm), not a tracing GC that walks the whole heap:

  • When a refcount is decremented but does not reach zero, the object becomes a possible root and is recorded in the root buffer.
  • When that buffer fills — 10,000 roots by default, tunable via zend.gc_root_buffer_max_entries — a collection runs.
  • The collector simulates removing each root’s references. Anything whose refcount falls to zero in the simulation was reachable only from within the cycle, so it is swept.
  • Everything else has its count restored. Collection is a stop-the-world pause proportional to the buffer, not to total heap size.
gc_collect_cycles();   // force a run; returns the number of cycles collected
gc_enabled();          // is the cycle collector on?
gc_disable();          // off — refcounting still frees everything acyclic
gc_enable();
gc_status();           // ['runs' => …, 'collected' => …, 'threshold' => …, 'roots' => …]

memory_get_usage(true);       // bytes allocated from the OS
memory_get_peak_usage(true);  // high-water mark — what memory_limit compares against

Configure it with zend.enable_gc (on by default) and cap the process with memory_limit. Note that PHP 8.3 added a GC bucket for objects and made the collector considerably cheaper, but the model is unchanged.

Breaking cycles yourself: WeakReference and WeakMap

The better fix is not to create the cycle. A weak reference does not increment the refcount, so the referent can still be freed.

final class Node
{
    private ?WeakReference $parent = null;    // PHP 7.4

    public function setParent(Node $p): void { $this->parent = WeakReference::create($p); }
    public function parent(): ?Node { return $this->parent?->get(); }   // null once collected
}

// WeakMap (PHP 8.0): keys are objects, entries vanish when the key is collected.
// The standard way to cache per-object data without pinning the object in memory.
final class HydrationCache
{
    private WeakMap $meta;

    public function __construct() { $this->meta = new WeakMap(); }

    public function remember(object $entity, array $data): void
    {
        $this->meta[$entity] = $data;     // no leak: drop $entity and this entry goes too
    }
}
Where this actually bites. In classic request-per-process PHP (mod_php, PHP-FPM) the whole arena is torn down at request end, so leaks rarely surface. In long-running processes — queue workers, Swoole, RoadRunner, FrankenPHP, a daemon consuming a stream — the same cycle accumulates until memory_limit kills the worker. That is why Laravel Horizon and Symfony Messenger restart workers after N jobs.

Asked as — “How does PHP manage memory?” The full answer in three beats: refcounting frees eagerly and deterministically; a mark-and-sweep collector handles reference cycles only; and WeakReference/WeakMap let you avoid creating cycles in the first place. Mentioning copy-on-write (arrays and strings share storage until written to, which is why passing a big array is cheap) usually ends the question.

Active Record vs Data Mapper

Two answers to “how does an object reach the database”, both named by Fowler in Patterns of Enterprise Application Architecture. Active Record: the object is the row and knows how to persist itself. Data Mapper: the object knows nothing about storage, and a separate mapper moves data between it and the database.

Active Record

  • One class = one table; instance = one row
  • $user->save(), User::find(1)
  • Eloquent (Laravel), Yii, CakePHP, Rails
  • Fast to build, reads well for CRUD
  • Model carries domain and persistence — an SRP violation by design
  • Unit tests need a database or heavy mocking
  • Domain shape is dragged toward the schema

Data Mapper

  • Entity is a plain object; a mapper handles I/O
  • $em->persist($user); $em->flush();
  • Doctrine (Symfony), Hibernate
  • Entities are unit-testable with new alone
  • Unit of Work batches writes; Identity Map guarantees one instance per row
  • Schema and domain evolve independently
  • More ceremony, proxies, and a learning curve
// Active Record — the object persists itself
$user = User::find(1);
$user->email = 'laslow@example.com';
$user->save();

// Data Mapper — the entity is ignorant; the manager persists it
$user = $em->find(User::class, 1);
$user->changeEmail('laslow@example.com');   // pure domain behaviour
$em->flush();                                // one transaction, computed from the Unit of Work

“Write a minimal Active Record” is a common whiteboard task. The shape they want combines late static binding, magic accessors and dirty tracking:

abstract class ActiveRecord
{
    protected static PDO $pdo;
    protected static string $table;

    private array $attributes = [];
    private array $dirty = [];
    private bool $exists = false;

    public function __get(string $k): mixed  { return $this->attributes[$k] ?? null; }

    public function __set(string $k, mixed $v): void
    {
        if (($this->attributes[$k] ?? null) !== $v) {
            $this->dirty[$k] = $v;          // track only what actually changed
        }
        $this->attributes[$k] = $v;
    }

    public static function find(int $id): ?static
    {
        $stmt = static::$pdo->prepare('SELECT * FROM ' . static::$table . ' WHERE id = ?');
        $stmt->execute([$id]);
        $row = $stmt->fetch(PDO::FETCH_ASSOC);

        if ($row === false) {
            return null;
        }

        $model = new static();              // LSB: the concrete subclass
        $model->attributes = $row;
        $model->exists = true;
        return $model;
    }

    public function save(): void
    {
        if ($this->dirty === []) {
            return;                         // nothing to write
        }

        $this->exists ? $this->update() : $this->insert();
        $this->dirty = [];
    }

    private function update(): void
    {
        $set = implode(', ', array_map(fn ($c) => "$c = ?", array_keys($this->dirty)));
        $sql = 'UPDATE ' . static::$table . " SET $set WHERE id = ?";

        static::$pdo->prepare($sql)
            ->execute([...array_values($this->dirty), $this->attributes['id']]);
    }

    private function insert(): void { /* … */ }
}

Data structures: PHP compared to Python

The headline difference is that Python separates list and dict; PHP has one array that plays both roles. A PHP array is an ordered hash map — insertion-ordered like a Python dict, index-addressable like a list — and PHP optimises it into a compact “packed” form when the keys happen to be sequential integers.

The second difference bites harder in practice: PHP arrays are value types with copy-on-write; Python lists and dicts are references. Assigning a PHP array hands over a logical copy, so the two never alias. Assigning a Python list does not.

PSR-1, PSR-12 and PER Coding Style

PSR-1 (Basic) — files use <?php or <?= only, UTF-8 without BOM; a file either declares symbols or has side effects, never both; class names in StudlyCaps, constants in UPPER_SNAKE, methods in camelCase.

PSR-12 (Extended) — 4 spaces (never tabs), soft 120-column limit, one blank line after the namespace block and after the use block, braces on their own line for classes and methods but on the same line for control structures, visibility declared on every property, method and constant, declare(strict_types=1) placement fixed.

PSR-7, 15, 17, 18 — the HTTP stack

PSR-7 models messages as immutable objects: RequestInterface, ResponseInterface, ServerRequestInterface, StreamInterface, UriInterface, UploadedFileInterface. Every with*() returns a modified clone — forgetting to reassign the result is the single most common PSR-7 bug.

$response->withHeader('Content-Type', 'application/json');   // discarded!
$response = $response->withHeader('Content-Type', 'application/json');  // correct

PSR-17 exists because PSR-7 has no constructors in its contracts: RequestFactoryInterface, ResponseFactoryInterface, StreamFactoryInterface, UriFactoryInterface, and the two server-side ones. Inject a factory instead of naming Guzzle or Nyholm in your code.

PSR-15 defines two tiny interfaces, and the middleware onion falls out of them:

use Psr\Http\Message\{ResponseInterface, ServerRequestInterface};
use Psr\Http\Server\{MiddlewareInterface, RequestHandlerInterface};

final class AuthenticationMiddleware implements MiddlewareInterface
{
    public function __construct(
        private Tokens $tokens,
        private ResponseFactoryInterface $responses,   // PSR-17
    ) {}

    public function process(
        ServerRequestInterface $request,
        RequestHandlerInterface $handler,
    ): ResponseInterface {
        $token = $request->getHeaderLine('Authorization');

        if (!$this->tokens->valid($token)) {
            return $this->responses->createResponse(401);   // short-circuit: never call $handler
        }

        $response = $handler->handle($request->withAttribute('user', $this->tokens->user($token)));

        return $response->withHeader('X-Auth', 'ok');       // act on the way out too
    }
}

PSR-18 is the client side: one method, sendRequest(RequestInterface): ResponseInterface, synchronous, no exceptions for 4xx/5xx (those are valid responses). Its exception tree is ClientExceptionInterface ← NetworkExceptionInterface / RequestExceptionInterface.

SQL injection & PDO

String concatenation mixes data into the command. A prepared statement sends the query and the values over separate channels, so the value can never be parsed as SQL — that is the whole defence, not escaping.

// Broken — $email is parsed as SQL
$pdo->query("SELECT * FROM users WHERE email = '$email'");

// Correct
$pdo = new PDO($dsn, $user, $pass, [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,  // fail loudly
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
    PDO::ATTR_EMULATE_PREPARES   => false,                    // real server-side prepares
]);

$stmt = $pdo->prepare('SELECT * FROM users WHERE email = :email AND active = :active');
$stmt->execute(['email' => $email, 'active' => 1]);
$user = $stmt->fetch();
The follow-up they are waiting for. Placeholders bind values, never identifiers. A dynamic ORDER BY, table or column name cannot be parameterised — it must be validated against a whitelist: 
$sortable = ['created_at', 'total', 'status'];
$column   = in_array($sort, $sortable, true) ? $sort : 'created_at';
$dir      = strtoupper($dir) === 'ASC' ? 'ASC' : 'DESC';

$pdo->prepare("SELECT * FROM orders ORDER BY $column $dir LIMIT :n");

With EMULATE_PREPARES off, LIMIT :n needs an explicit integer bind — bindValue(':n', $n, PDO::PARAM_INT) — because emulation is no longer quietly casting for you. Turning emulation off is still right: it is what makes the separation real rather than string-interpolated by the driver.

Asked as — “Is mysqli_real_escape_string() enough?” No. It is context-dependent, breaks on unusual charsets, and does nothing for identifiers or for numeric contexts without quotes. Prepared statements are the answer; escaping is a fallback from a previous decade.

Passwords, tokens & randomness

Never hash a password with md5(), sha1(), or any general-purpose hash — those are fast by design, which is exactly wrong. Use the password API, which handles salting, the algorithm identifier and the cost factor for you.

// Registration
$hash = password_hash($plain, PASSWORD_DEFAULT);   // bcrypt today; follows the default forward
// or, explicitly:
$hash = password_hash($plain, PASSWORD_ARGON2ID, ['memory_cost' => 65536, 'time_cost' => 4]);

// Login
if (!password_verify($plain, $user->passwordHash)) {
    throw new InvalidCredentials();
}

// Transparent upgrade when the default or cost changes
if (password_needs_rehash($user->passwordHash, PASSWORD_DEFAULT)) {
    $repo->updateHash($user, password_hash($plain, PASSWORD_DEFAULT));
}

The output already contains the salt and parameters, so there is no separate salt column. password_verify() is timing-safe; for anything you compare yourself — API keys, reset tokens, HMAC signatures — use hash_equals(), never ===.

$token = bin2hex(random_bytes(32));    // CSPRNG — suitable for secrets
$n     = random_int(1, 100);           // CSPRNG integer

// NOT for secrets: rand(), mt_rand(), shuffle(), uniqid(), str_shuffle()

hash_equals($expectedToken, $providedToken);   // constant time
$sig = hash_hmac('sha256', $payload, $secret);

Asked as — “Why is uniqid() unsafe?” It is derived from the current time in microseconds, so it is predictable and low-entropy. Password reset tokens built on it have been a recurring source of account-takeover bugs.

XSS, output escaping & CSRF

The rule is escape on output, in the context you are outputting into — not sanitise on input. The same string is safe in one context and dangerous in another.

// HTML body or attribute
echo htmlspecialchars($name, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');

// Inside a URL
echo '<a href="/search?q=' . rawurlencode($q) . '">';

// Inside a <script> block — JSON, not htmlspecialchars
echo '<script>const cfg = ' . json_encode($cfg, JSON_HEX_TAG | JSON_HEX_AMP
    | JSON_HEX_APOS | JSON_HEX_QUOT | JSON_THROW_ON_ERROR) . ';</script>';

Always pass ENT_QUOTES (single quotes matter in attributes) and the charset. In practice a templating engine with auto-escaping — Twig, Blade — is the real answer, plus a Content-Security-Policy header so an injected script has nowhere to run. Note that strip_tags() is not an XSS defence; for user-supplied rich text use an allow-list sanitiser such as HTML Purifier.

CSRF is a different attack: the browser sends the victim’s cookies to your site on a request the victim did not intend. Cookies alone cannot distinguish it, so you need a value the attacker’s page cannot read.

// Issue once per session
$_SESSION['csrf'] ??= bin2hex(random_bytes(32));

// In the form
echo '<input type="hidden" name="_token" value="'
   . htmlspecialchars($_SESSION['csrf'], ENT_QUOTES, 'UTF-8') . '">';

// On any state-changing request
if (!hash_equals($_SESSION['csrf'], $_POST['_token'] ?? '')) {
    http_response_code(419);
    exit;
}

Pair it with SameSite=Lax (or Strict) cookies, which blocks the cross-site request in modern browsers — defence in depth, not a replacement, since SameSite does not cover every case. And GET must never change state: a CSRF token on a link is treating the symptom.

Sessions, uploads & unserialize

Session fixation — an attacker plants a known session id, then waits for the victim to log in with it. The fix is one line, at every privilege change:

session_set_cookie_params([
    'httponly' => true,        // not readable from JavaScript
    'secure'   => true,        // HTTPS only
    'samesite' => 'Lax',
]);
session_start();

// on successful login, and again on logout
session_regenerate_id(true);   // true = delete the old session file

File uploads — nothing in $_FILES that came from the client is trustworthy, including name and type:

$file = $_FILES['avatar'];

if ($file['error'] !== UPLOAD_ERR_OK || !is_uploaded_file($file['tmp_name'])) {
    throw new UploadFailed();
}

$mime = (new finfo(FILEINFO_MIME_TYPE))->file($file['tmp_name']);   // inspect content
if (!in_array($mime, ['image/png', 'image/jpeg', 'image/webp'], true)) {
    throw new UnsupportedMediaType($mime);
}

$name = bin2hex(random_bytes(16)) . '.' . self::EXT[$mime];   // never reuse the client's name
move_uploaded_file($file['tmp_name'], self::STORAGE . '/' . $name);   // outside the web root

unserialize() on untrusted input is remote code execution, via POP chains built from __destruct/__wakeup in whatever classes happen to be loaded. Use json_decode() for anything crossing a trust boundary; if you truly must unserialize, pass ['allowed_classes' => false].

Type juggling in comparisons. Loose == against a hash is the classic “magic hash” bug: two different strings both starting 0e followed by digits compare equal as numbers. PHP 8 tightened string-to-number comparison considerably, but the lesson stands — use === or hash_equals() for anything security-relevant. In production also set display_errors=0 and log instead; a stack trace on screen is an information leak.

Request lifecycle, OPcache and the JIT

PHP is shared-nothing: every request begins with a clean interpreter state and ends with everything torn down. No application-level memory survives between requests — that is why PHP scales horizontally so easily, and why anything shared must live in Redis, a database, or the session store.

What happens per request: the SAPI (usually PHP-FPM) hands the script to the engine → lexer → parser → AST → compiled into opcodes → the Zend VM executes them → shutdown frees everything.

OPcache removes the compile step by caching opcodes in shared memory. It is the single largest performance win available, and it is on by default in modern builds.

; php.ini — production
opcache.enable=1
opcache.memory_consumption=256
opcache.max_accelerated_files=20000      ; must exceed your file count
opcache.interned_strings_buffer=16
opcache.validate_timestamps=0            ; never stat files; requires a reload on deploy
opcache.preload=/var/www/preload.php     ; PHP 7.4+: load framework classes once, at startup

validate_timestamps=0 is the production setting and the classic deployment gotcha: your deploy must reload FPM (or call opcache_reset()) or you keep serving the old code. Preloading goes further, compiling classes into memory permanently at startup so they are never loaded again.

The JIT (PHP 8.0, reworked in 8.4) compiles hot opcodes to machine code. Say this plainly: it delivers large gains on CPU-bound numeric work and typically little to nothing on ordinary web applications, because those are bound by database and network I/O, not by opcode dispatch.

opcache.jit=tracing
opcache.jit_buffer_size=64M    ; 0 disables the JIT

PHP-FPM runs a master process and a pool of workers. Size pm.max_children by dividing available RAM by the real per-worker memory footprint — over-provisioning causes swapping, which is far worse than queueing.

pm = dynamic
pm.max_children = 40           ; RAM / avg worker memory
pm.start_servers = 8
pm.max_requests = 500          ; recycle workers to bound leaks
request_terminate_timeout = 30s
slowlog = /var/log/php-fpm-slow.log
request_slowlog_timeout = 5s   ; dumps a stack trace for slow requests — very useful

Asked as — “The app is slow. Where do you look?” Measure first, with a profiler (Blackfire, Xdebug, Excimer) or APM — not guesses. In practice the order of payoff is: N+1 queries and missing indexes, then caching, then OPcache and autoloader configuration, then everything else. Reaching for the JIT first is the wrong answer.

Concurrency, queues and Fibers

PHP has no threads in normal userland code. Concurrency comes from running multiple processes — which the shared-nothing model makes trivial — or from an event loop inside one process.

Fibers (PHP 8.1) are the language primitive for the second option: a full-stack, interruptible function that can be suspended and resumed from anywhere in its call stack. Fibers are not concurrency by themselves — there is no scheduler in the language — they are what lets AMPHP and ReactPHP present async I/O as ordinary synchronous-looking code without async/await keywords.

$fiber = new Fiber(function (string $start): string {
    echo "$start\n";
    $resumeValue = Fiber::suspend('paused');   // yields control to whoever started it
    echo "resumed with $resumeValue\n";
    return 'done';
});

$suspendValue = $fiber->start('running');   // 'paused'
$fiber->resume('a value');                  // prints "resumed with a value"
$fiber->getReturn();                        // 'done'

Fibers vs generators

  • A generator suspends only in its own body — every caller must also yield
  • A fiber suspends the entire stack from any depth
  • That is what removes “function colouring” from async PHP

Getting work off the request

  • Queues: Symfony Messenger, Laravel Horizon — the default answer
  • Long-running runtimes: Swoole, RoadRunner, FrankenPHP worker mode
  • curl_multi_* for parallel outbound HTTP without a framework

Asked as — “How would you send 10,000 emails?” Not in the request. Push jobs onto a queue, process them in workers, make each job idempotent and retryable with backoff, and cap concurrency at the provider’s rate limit. Databases: PDO, transactions, isolation

PDO vs mysqli — PDO covers a dozen drivers, supports named parameters and has a consistent API; mysqli is MySQL-only but exposes a few driver-specific features. For new code, PDO unless you need something mysqli alone offers.

$pdo->beginTransaction();

try {
    $pdo->prepare('UPDATE accounts SET balance = balance - ? WHERE id = ?')
        ->execute([$amount, $from]);
    $pdo->prepare('UPDATE accounts SET balance = balance + ? WHERE id = ?')
        ->execute([$amount, $to]);

    $pdo->commit();
} catch (Throwable $e) {
    $pdo->rollBack();
    throw $e;
}

Two MySQL traps worth naming: DDL statements cause an implicit commit, so never mix schema changes into a transaction; and PDO transactions do not nest — nesting needs savepoints, which is what frameworks emulate for you.

The one-liners worth having ready

self vs static vs $this
Compile-time class · runtime called class · the current instance.
Interface constants
Allowed, and since PHP 8.1 implementing classes may override them.
Can a trait have a constructor?
Yes, and it becomes the class’s constructor unless the class defines its own.
instanceof with strings
$obj instanceof $className works with a string variable, but not a string literal.
Abstract + final
Illegal together on a class. On PHP 8.0+, final on a private method is pointless and warns.
Why DateTimeImmutable?
DateTime::modify() mutates in place, so a shared instance changes under callers; the immutable variant returns a new object.
::class on an object
$obj::class (PHP 8.0+) replaces get_class($obj).
Constructor in an interface
Legal to declare, almost always a mistake — construction is not part of a polymorphic contract.
Destructor timing
When the last reference drops, or at script end. Circular references wait for the cycle collector.
new in initializers
PHP 8.1 allows new Foo() as a parameter default — the clean way to default to a NullLogger.
Readonly + clone
PHP 8.3 lets __clone() reassign readonly properties, enabling withX() on value objects.
unset() does not free
It decrements the refcount. Memory is released only when that count hits zero — or when the cycle collector runs.
Copy-on-write
Arrays and strings are shared until one holder writes; only then is a real copy made. Passing a large array by value is cheap.
PSRs are not law
They are recommendations from a member-voted group. The right answer to “must we follow PSR-12?” is “we pick one standard and enforce it in CI”.

  1. $obj instanceof $className — when does this work?

    A variable holding the name works; a literal is a parse error. Alongside it: $obj::class (PHP 8.0) replaces get_class($obj), and abstract final on a class is illegal.

  2. Can a trait declare a constructor?

    It is copied in like any other method, and the class's own declaration takes precedence. Two neighbours worth knowing: interface constants may be overridden by implementing classes since PHP 8.1, and a constructor declared in an interface is legal but almost always a mistake.

  3. Why does unset($x) not necessarily free memory?

    Refcounting again. The same mechanism explains copy-on-write: arrays and strings share storage until one holder writes, which is why passing a large array by value is cheap — and why DateTimeImmutable is preferred, since DateTime::modify() mutates a shared instance under its callers.
