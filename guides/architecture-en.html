Boundaries

5 topics

Every architecture on this page is one idea applied at different scales: put a line somewhere, and control which direction the dependencies cross it. Learn the idea and the named patterns stop needing memorisation.

Layers and the dependency rule

Layered, hexagonal, onion and clean architecture are the same rule drawn four ways: source code dependencies point inward, toward policy, never outward toward detail. The domain must not know that MySQL, HTTP or Symfony exist.

NameIts emphasisWhat it adds
Classic layered (n-tier)Presentation → business → dataNothing stops the top layer reaching the bottom; dependencies flow down to the database
Hexagonal (ports & adapters)Inside vs outsideEvery external interaction is an explicit port with swappable adapters
OnionConcentric rings around the domain modelNames the rings and forbids inward-facing knowledge of outer ones
CleanUse cases at the centreThe dependency rule stated as a rule, plus explicit boundary DTOs

The mechanism that makes an inward-pointing dependency possible when control flows outward is dependency inversion: the domain declares the interface it needs, and infrastructure implements it. That single move — the interface living with its consumer, not its implementation — is what turns a layered app into a hexagonal one.

// Domain/Repository/Orders.php — declared by the domain, implemented outside it.
namespace App\Domain\Order;

interface Orders
{
    public function get(OrderId $id): Order;
    public function save(Order $order): void;
    public function nextIdentity(): OrderId;
}
// Infrastructure/Persistence/DoctrineOrders.php — knows Doctrine; the domain never does.
namespace App\Infrastructure\Persistence;

final class DoctrineOrders implements \App\Domain\Order\Orders
{
    public function __construct(private EntityManagerInterface $em) {}

    public function get(OrderId $id): Order
    {
        return $this->em->find(Order::class, $id->toString())
            ?? throw new OrderNotFound($id);
    }
}

Asked as — “What is the difference between hexagonal and clean architecture?” Very little in substance — both enforce the dependency rule; hexagonal emphasises symmetric ports for every external actor, clean emphasises use cases at the centre. A candidate who says “they are largely the same idea, here is the rule they share” sounds far better than one who recites two diagrams.

Ports and adapters in practice

A port is an interface owned by the inside. An adapter connects it to something real. They come in two directions, and confusing them is the usual mistake.

Driving (primary) adapters

  • The outside calls in
  • HTTP controller, CLI command, queue consumer, cron
  • Depend on the application's use case interface
  • Test by calling the use case directly instead

Driven (secondary) adapters

  • The inside calls out
  • Repository, mailer, payment gateway, clock, event bus
  • Implement an interface the inside declared
  • Test by substituting an in-memory fake
// A driven port and two adapters — production and test — behind one interface.
interface PaymentGateway
{
    public function charge(Money $amount, CardToken $card): ChargeResult;
}

final class StripeGateway implements PaymentGateway { /* HTTP, retries, mapping */ }

final class InMemoryGateway implements PaymentGateway     // lives in tests/
{
    public array $charges = [];
    public function charge(Money $amount, CardToken $card): ChargeResult
    {
        $this->charges[] = $amount;
        return ChargeResult::succeeded('ch_test_1');
    }
}
The tell for a real port. If you cannot write a sensible in-memory implementation of the interface, it is not a port — it is your database's API with a new name. findByQueryBuilder(QueryBuilder $qb) on a repository interface is a leak: the domain now depends on Doctrine through the signature.

Two ports people forget until a test goes flaky: the clock (interface Clock { public function now(): DateTimeImmutable; }) and the id generator. Both are non-determinism entering the domain; both are one-line interfaces that make aggregate tests reproducible.

Asked as — “What does hexagonal architecture actually buy you?” Substitutability at the edges and a domain you can test without booting the framework. The honest cost — more interfaces, more indirection, a jump-to-definition that lands on an interface — is worth naming before they raise it.

The application layer: use cases, not controllers

The application service (or command handler, or interactor) is the thin layer that orchestrates: load an aggregate, call one domain method, persist, dispatch events. It holds no business rules of its own — if it contains an if about money, that rule belongs in the domain.

final class RefundOrder                       // one use case, one class
{
    public function __construct(
        private Orders $orders,               // domain port
        private PaymentGateway $payments,     // domain port
        private UnitOfWork $transaction,      // infrastructure concern, explicit
        private EventDispatcher $events,      // PSR-14
    ) {}

    public function __invoke(RefundOrderCommand $command): void
    {
        $order = $this->orders->get(new OrderId($command->orderId));

        // The rule lives in the aggregate; the service only sequences the steps.
        $refund = $order->refund(Money::fromMinor($command->amountMinor, $command->currency));

        $this->transaction->wrap(function () use ($order, $refund) {
            $this->payments->refund($refund);
            $this->orders->save($order);
        });

        foreach ($order->releaseEvents() as $event) {
            $this->events->dispatch($event);   // after commit — see the outbox topic
        }
    }
}

The controller then shrinks to translation: HTTP in, command object out, result to a response. That is what makes the same use case reachable from a CLI command, a queue worker and a test without duplication — and it is the practical payoff of the whole structure, so lead with it when explaining the layer.

Asked as — “What goes in a service and what goes in an entity?” Orchestration and transaction boundaries in the service; invariants and state transitions in the entity. The smell to name out loud: a service that reads an entity's properties, decides something, and writes them back — that is an anemic model with the logic displaced.

Entities, value objects, aggregates

Building blockIdentityMutabilityExample
Value objectNone — equal by valueImmutableMoney, Email, DateRange
EntityHas an id; equal by idChanges over timeOrder, Customer
AggregateCluster with one root entityChanged only through the rootOrder + its OrderLines
Domain serviceStateless—A rule spanning several aggregates
Repository——Collection-like access to aggregate roots only
 
final class Order                       // aggregate root
{
    private array $lines = [];
    private array $events = [];

    public function addLine(ProductId $product, int $quantity, Money $unitPrice): void
    {
        if ($this->status !== OrderStatus::Draft) {
            throw new OrderNotEditable($this->id);      // the invariant, enforced here
        }
        if ($quantity < 1) {
            throw new InvalidQuantity($quantity);
        }

        $this->lines[] = new OrderLine($product, $quantity, $unitPrice);
        $this->events[] = new LineAdded($this->id, $product, $quantity);
    }

    /** No setters, no public collection. Callers cannot bypass the rules above. */
    public function lines(): array { return $this->lines; }
}

The aggregate boundary is a consistency boundary: everything inside is saved in one transaction and is always valid; anything outside is reached by id and becomes consistent eventually. That gives you the sizing heuristic — keep aggregates small, reference other aggregates by id rather than by object, and if a rule spans two aggregates, either they are one aggregate or the rule is eventually consistent. An Order holding a whole Customer object is the classic oversized aggregate.

Anemic domain model. Entities that are property bags with getters and setters, and all behaviour in services. Fowler named it an anti-pattern because it takes the cost of an object model and returns none of its benefits. It is also the default shape of most framework tutorials, so expect to be asked whether you would keep it — “yes for a CRUD admin panel, no for the pricing engine” is a better answer than dogma in either direction.

Asked as — “How do you decide where the aggregate boundary goes?” By transactional invariant: what must be true at every commit. If two things can be briefly inconsistent without breaking the business, they belong to different aggregates and talk through events.

Bounded contexts and the modular monolith

A bounded context is the scope within which a term has one meaning. “Customer” in billing (a payer with a VAT number) is not “customer” in support (a person with tickets). Forcing one shared Customer class on both is how models become unmaintainable.

RelationshipMeaning
Shared kernelTwo contexts share a small model deliberately. Cheap, and couples release cycles
Customer / supplierDownstream's needs influence upstream's plan
ConformistDownstream accepts upstream's model as-is — no translation budget
Anti-corruption layerDownstream translates at the boundary to keep its own model clean
Published languageA shared, versioned interchange format — events, an API schema

Modular monolith

  • One deployable, hard module boundaries inside
  • In-process calls: no network failure modes
  • Transactions across modules are still possible — which is the temptation
  • Refactoring a boundary is a rename, not a migration

Microservices

  • Independent deploy, scale and technology choice
  • Every call can fail, be slow, or arrive twice
  • No cross-service transactions — sagas and eventual consistency
  • Needs the operational maturity to match: tracing, contracts, CI/CD

The defensible default in 2026, and the one most interviewers are hoping to hear: start as a modular monolith with boundaries you actually enforce (tooling, not discipline), and extract a service when there is a concrete pressure — independent scaling, a different runtime, or team autonomy at a size where the shared codebase is the bottleneck. Distributed systems are a cost you pay for organisational reasons at least as often as technical ones.

Asked as — “Would you use microservices here?” Ask what pressure would justify it, then answer. “Not yet — modular monolith with enforced boundaries, and here is the seam I would extract first if X happens” is a senior answer. “Yes, microservices scale better” is not.

Patterns

5 topics

These are the three acronyms the job ad meant, plus the two mechanisms that make them survivable in production. Each one is genuinely useful and genuinely expensive; the interview is testing whether you know both halves.

CQRS, precisely

Command Query Responsibility Segregation: use different models for writing and for reading. That is all it says. It does not require event sourcing, two databases, a message bus, or eventual consistency — those are options it makes available.

Write model

  • Aggregates, invariants, normalised
  • Loaded by id, never queried for lists
  • Optimised for correctness

Read model

  • Flat DTOs shaped like the screen
  • Plain SQL, joins, no entities
  • Optimised for the query, denormalised freely
// Read side: no ORM, no domain objects, just the shape the page needs.
final class OrderSummaryQuery
{
    public function __construct(private PDO $db) {}

    /** @return list<OrderSummary> */
    public function forCustomer(string $customerId, int $limit): array
    {
        $stmt = $this->db->prepare(
            'SELECT o.id, o.status, o.total_minor, o.currency, c.name AS customer_name,
                    COUNT(l.id) AS line_count
             FROM orders o
             JOIN customers c ON c.id = o.customer_id
             LEFT JOIN order_lines l ON l.order_id = o.id
             WHERE o.customer_id = :customer
             GROUP BY o.id
             ORDER BY o.created_at DESC
             LIMIT :limit'
        );
        // ... execute, map rows to readonly DTOs.
    }
}

The cheapest useful version of CQRS is exactly this: keep Doctrine for writes, drop to SQL for reads, and stop trying to make one entity graph serve both. No extra infrastructure, most of the benefit. The expensive version — a separate read store kept up to date by events — buys independent scaling and query shapes the write store cannot serve, and costs you eventual consistency plus a projection to maintain. Introduce it per use case, never wholesale.

Read-your-own-writes. The moment the read model is asynchronous, a user who saves and is redirected to a list may not see their change. Handle it deliberately: read from the write model immediately after a command, return the created resource in the response, or make the UI optimistic. “The projection is usually fast” is not a design.

Asked as — “What is CQRS and when would you use it?” Separate models for reads and writes; use it when the two have genuinely different shapes or load profiles. Say explicitly that it does not imply two databases — that distinction is what the question is usually checking.

Domain events vs integration events

Domain event

  • Something meaningful happened inside this context
  • Named in the past tense: OrderRefunded
  • Carries domain types, in-process
  • Internal — free to change with the model

Integration event

  • Published across a boundary
  • Serialised, versioned, part of a public contract
  • Primitive fields only — no domain objects
  • Breaking it breaks other teams
// Domain event: recorded by the aggregate, released after a successful save.
final readonly class OrderRefunded
{
    public function __construct(
        public OrderId $orderId,
        public Money $amount,
        public DateTimeImmutable $occurredAt,
    ) {}
}

// Integration event: the translated, versioned shape that leaves the module.
final readonly class OrderRefundedV1
{
    public function __construct(
        public string $eventId,        // for consumer-side idempotency
        public string $orderId,
        public int $amountMinor,
        public string $currency,
        public string $occurredAt,     // RFC 3339
    ) {}
}

Rules that keep event-driven systems from rotting: events are facts about the past, so a handler may not veto them (that is what a command is for); publish only after the transaction commits, or you will announce a refund that got rolled back; consumers must be idempotent, because every real broker is at-least-once; and never assume ordering across streams. Version integration events additively — add optional fields, never repurpose one — exactly as you would an API response.

Asked as — “Why not just call the other service directly?” Coupling and availability: a synchronous call fails when the callee is down and forces you to know who cares. The counter-question to have an answer for is the cost — debugging a flow you cannot read top to bottom, which is what distributed tracing and a well-named event log are for.

  1. What is the difference between a domain event and an integration event?

    The distinction is who is allowed to depend on it. Leaking a domain object into a published event means every consumer now depends on your internal model — and breaking it breaks other teams.

  2. Why may an event handler not veto the thing that happened?

    Past tense is not a naming convention, it is the semantics. OrderRefunded already happened. The neighbouring rules: publish only after the transaction commits, or you will announce a refund that got rolled back.

  3. Why must consumers be idempotent?

    At-least-once is the default you design for. Also never assume ordering across streams, and version integration events additively — add optional fields, never repurpose one — exactly as you would an API response.

The outbox pattern

You must write to the database and publish a message. Two systems, no shared transaction — so either can succeed alone. Doing them naively is the dual-write problem, and it produces orders with no notification, or notifications for orders that do not exist.

// Inside the same transaction as the business change: no broker involved yet.
$this->transaction->wrap(function () use ($order) {
    $this->orders->save($order);

    foreach ($order->releaseEvents() as $event) {
        $this->outbox->add(new OutboxMessage(
            id: Uuid::v7(),
            topic: 'orders.refunded.v1',
            payload: $this->serializer->serialize($event),
            createdAt: $this->clock->now(),
        ));
    }
});

// A separate worker polls (or tails the binlog) and publishes. Crash-safe:
// the row is only marked sent after the broker acknowledges, so the failure
// mode is a duplicate publish - which is why consumers must be idempotent.

The consumer side of the same guarantee is an inbox: record each processed eventId in a table with a unique index, inside the same transaction as the side effect. A redelivered message then hits the unique violation and is skipped. Together these give you effectively-once processing on top of at-least-once delivery — the phrase to use, because “exactly-once delivery” does not exist and interviewers like hearing that said plainly.

Asked as — “How do you keep the database and the message broker consistent?” Transactional outbox plus an idempotent consumer. Naming the dual-write problem before the solution is what makes the answer land.

Event sourcing

Store the sequence of events as the source of truth; current state is a fold over that sequence. Not the same thing as CQRS, though they pair naturally, since an event store is a poor place to run queries.

final class Order
{
    private array $pending = [];
    private int $version = 0;

    public static function reconstitute(iterable $history): self
    {
        $order = new self();
        foreach ($history as $event) {
            $order->apply($event);      // no validation on replay: history is fact
            $order->version++;
        }
        return $order;
    }

    public function refund(Money $amount): void
    {
        if ($amount->greaterThan($this->refundable())) {
            throw new RefundExceedsBalance();     // decisions validate...
        }
        $this->recordThat(new OrderRefunded($this->id, $amount, $this->clock->now()));
    }

    private function apply(object $event): void   // ...applies only mutate
    {
        match (true) {
            $event instanceof OrderRefunded => $this->refunded = $this->refunded->plus($event->amount),
            $event instanceof OrderPlaced   => $this->total = $event->total,
        };
    }
}

What it gives you

  • A complete, non-negotiable audit trail
  • Time travel: state as of any moment
  • New projections over historical data
  • Business questions answerable after the fact

What it costs

  • Event schema versioning, forever — you cannot migrate the past away
  • Snapshots once streams get long
  • Eventual consistency in every read
  • GDPR erasure against an append-only store (crypto-shredding)
  • A team that has to learn it before they can debug it

Concurrency is handled by appending with an expected version — the event store rejects the write if the stream moved, which is optimistic locking again. Use it where the log is the business value: ledgers, payments, compliance-heavy workflows, anything where “why is the balance this number” must be answerable. Do not use it for a CRUD admin panel; that is the most expensive audit table ever built.

Asked as — “When would you not use event sourcing?” Have a concrete answer ready: when the domain has no interesting history, when the team cannot support it, or when GDPR erasure requirements make an append-only log a liability. Being able to argue against a pattern you understand is the strongest signal in this whole section.

  2. How is concurrency handled in an event store?

Sagas, process managers, eventual consistency

A business transaction spanning several services cannot be a database transaction. A saga breaks it into local transactions, each with a compensating action for rollback — because you cannot undo a charge, you can only refund it.

Choreography

  • Each service reacts to events, no coordinator
  • Loosely coupled, easy to start
  • No single place shows the flow
  • Cycles and surprises as the flow grows

Orchestration

  • A process manager holds the state machine and issues commands
  • The flow is explicit, testable, observable
  • The orchestrator is a component to own and deploy
  • Risks becoming a god service if it accretes logic

Sagas have no isolation, and that has consequences you should name unprompted: intermediate states are visible to other readers, so you need semantic locks (an order in pending_payment) rather than database locks, and compensations must be idempotent and able to run out of order. Timeouts are part of the design — every step needs an answer to “what if the reply never comes”, which is usually a scheduled compensation.

Asked as — “How do you handle a transaction across three services?” You do not; you run a saga with compensations, and you say out loud that the system is eventually consistent and that partial states are observable. Reaching for two-phase commit is the wrong answer for exactly the reasons worth explaining: it blocks, and it needs every participant to support it.

Module layout, and enforcing it

Organise by feature, not by technical layer. src/Controller, src/Entity, src/Repository scatters one change across three directories and tells you nothing about what the system does.

src/
  Billing/                        # bounded context, owns its schema
    Domain/                       # entities, VOs, ports, domain events - zero framework imports
      Order.php
      Orders.php                  # the repository interface
    Application/                  # use cases, commands, queries, handlers
      RefundOrder.php
    Infrastructure/               # adapters: Doctrine, HTTP clients, messaging
      DoctrineOrders.php
    Presentation/                 # controllers, CLI commands, message consumers
      RefundOrderController.php
  Support/
    Domain/ ...
  Shared/                         # only genuinely shared kernel: Money, Clock, ids

Convention alone will not hold this. Enforce it mechanically: Deptrac or PHPArkitect in CI with rules like “Billing\Domain may not depend on Doctrine, on Symfony, or on Support\*”. Composer path repositories per module are the heavier option, and they make the boundary impossible to cross by accident since each module has its own composer.json.

// tests/Architecture/LayerTest.php - an architecture rule as an executable test
public function testDomainDoesNotDependOnInfrastructure(): void
{
    $violations = $this->dependenciesOf('App\\Billing\\Domain')
        ->filter(fn (string $dep) => str_starts_with($dep, 'Doctrine')
            || str_starts_with($dep, 'Symfony')
            || str_contains($dep, '\\Infrastructure\\'));

    self::assertSame([], $violations->toArray());
}

Asked as — “How do you stop a modular monolith turning back into a big ball of mud?” Automated boundary checks in CI. Any answer relying on code review discipline invites the follow-up “and when someone is in a hurry on a Friday?”

    Layer-first layout scatters a single change across three directories and tells you nothing about the domain. Feature-first puts the domain, application and infrastructure of one capability together, with the dependency rule enforced inside it.

  2. How do you stop a modular monolith turning back into a big ball of mud?

    Any answer relying on discipline invites the follow-up “and when someone is in a hurry on a Friday?” Composer path repositories per module are the heavier option, and they make the boundary impossible to cross by accident.

  3. What does a rule like “Billing\Domain may not depend on Symfony” actually protect?

    The dependency rule, mechanically enforced. It is also an architecture test in its own right — the layering itself becomes something CI covers rather than something the team remembers.

Trade-offs, fitness functions, ADRs

The senior part of an architecture interview is rarely “do you know CQRS”. It is whether you can say what a choice costs, how you would know it was wrong, and how the decision gets recorded.

A usable framing for any proposal, out loud, in this order: what quality attribute are we optimising (latency? deploy independence? auditability?), what are we giving up, what is the reversal cost if we are wrong, and what would we measure to find out. That last one is the fitness function — an automated check that the property still holds: an architecture test for the dependency rule, a performance budget in CI, an alert on projection lag.

# docs/adr/0007-outbox-for-order-events.md
# Status:   Accepted (2026-09-10)
# Context:  Orders must notify billing; a direct call couples availability, and a
#           naive publish-after-commit loses messages when the broker is down.
# Decision: Transactional outbox in the orders schema, polled by a worker.
# Consequences:
#   + No dual-write inconsistency; broker downtime only delays delivery.
#   - Duplicate publishes are possible: every consumer needs an inbox table.
#   - One more worker to run, monitor and alert on (lag > 60s pages).
# Alternatives: 2PC (rejected: blocking, unsupported by our broker),
#           CDC on the binlog (rejected for now: ops cost, revisit at scale).

An ADR is one page in the repository, immutable once accepted, superseded rather than edited. Its real value is six months later when someone asks why — and the reason a candidate who mentions ADRs stands out is that it signals they expect to be held to decisions rather than to make them and move on.

Asked as — “Tell me about an architectural decision you regret.” Answer with a real one, the signal that revealed it, and what you changed. Naming the reversal cost you failed to consider beats any amount of pattern vocabulary.

Strangler fig, seams, anti-corruption layers

Nobody rewrites a working system. The strangler fig pattern replaces it incrementally: put a façade in front, route one capability at a time to the new implementation, and delete the old path once traffic is gone.

// The seam: one interface, two implementations, routing controlled by a flag.
final class RoutingInvoices implements Invoices
{
    public function __construct(
        private Invoices $legacy,
        private Invoices $rebuilt,
        private FeatureFlags $flags,
    ) {}

    public function issue(InvoiceRequest $request): Invoice
    {
        if (!$this->flags->enabled('invoices.rebuilt', $request->tenantId)) {
            return $this->legacy->issue($request);
        }

        $invoice = $this->rebuilt->issue($request);

        // Optional shadow mode: run both, compare, log divergence, serve the old one
        // until the difference rate is zero. This is how you migrate money code.
        return $invoice;
    }
}

Two supporting ideas do most of the work. A seam is a place where behaviour can be changed without editing the code around it — in PHP, an interface plus constructor injection; finding or creating seams is the first step in any legacy migration. An anti-corruption layer is a translation boundary that stops the legacy model leaking into the new one: the new context speaks its own language and converts at the edge. Without it, the rewrite inherits the shape it was meant to escape.

Asked as — “How would you modernise a ten-year-old PHP application?” Never a big-bang rewrite. Characterisation tests to pin current behaviour, a façade at the boundary, extract one capability with an ACL, migrate traffic behind a flag with shadow comparison, delete the old path. Then: pick the capability with the highest change rate first, because that is where the payback is.

The one-liners worth having ready

Conway's law
System structure mirrors communication structure. The inverse manoeuvre — reshape teams to get the architecture — is a real tactic.
Coupling vs cohesion
Low coupling between modules, high cohesion within one. Every pattern here is a way to buy that.
CAP, honestly
Partitions happen, so the real choice is consistency or availability during one. “CP or AP” is a per-operation decision, not a per-database badge.
Idempotency everywhere
At-least-once delivery is the default for every broker worth using. Design the consumer accordingly.
Two-phase commit
Real, and rarely worth it: blocking, needs participant support, one slow node stalls the lot.
Shared database between services
The classic distributed monolith: independent deploys, coupled schema. Worse than a monolith.
Repository returns aggregates
Not arrays of rows, not query builders. If you need rows, that is the read side.
Anemic model
Getters, setters, logic in services. Sometimes exactly right — say when, rather than reciting the anti-pattern.
DTO vs value object
A DTO is a transport shape with no behaviour; a VO is a domain concept with invariants and equality.
Hexagonal ≠ folders
Renaming directories to Domain/Infrastructure while the entity still extends the ORM base class changes nothing.
Eventual consistency is a product decision
Someone has to accept that a screen can be stale for two seconds. Get that agreed, not assumed.
YAGNI vs the dependency rule
The rule is cheap to follow from day one and expensive to retrofit; a message bus is the opposite. Adopt accordingly.
Distributed tracing
Once flows span services or queues, a correlation id on every message is not optional.
The best answer to “which pattern”
“What is the constraint?” Architecture questions with no context are testing whether you ask.
